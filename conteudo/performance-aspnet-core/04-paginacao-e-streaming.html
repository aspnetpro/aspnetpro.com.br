Paginação, streaming e payloads que não cabem na memória

Existe uma classe inteira de problemas cuja causa é a mesma: a aplicação materializa na memória algo que deveria atravessá-la. Funciona com 500 registros na sua máquina e mata o processo com 800 mil em produção.

ASP.NET Core 10 Leitura: ~7 min Nível: essencial

O endpoint sem limite

Todo sistema tem um. Foi escrito quando a tabela tinha algumas centenas de linhas:

ClientesEndpoints.csC#
app.MapGet("/clientes", async (AppDbContext db, CancellationToken ct) =>
    await db.Clientes.ToListAsync(ct));

Dois anos e 800 mil clientes depois, uma única chamada carrega 800 mil entidades no heap, monta 800 mil objetos JSON e produz uma resposta de centenas de megabytes. E o efeito não fica contido: objetos grandes vão para o Large Object Heap, forçam coleta de geração 2 e travam a aplicação inteira, inclusive as requisições que não têm nada a ver com esse endpoint.

Duas ou três chamadas simultâneas bastam

Não é preciso ataque nem tráfego anormal. Um crawler, um retry automático ou um usuário atualizando a página três vezes derrubam o processo por OutOfMemoryException — ou fazem o orquestrador matar o contêiner por estourar o limite de memória.

A defesa mínima é um limite imposto pelo servidor, não sugerido pelo cliente:

ClientesEndpoints.csC#
app.MapGet("/clientes", async (
    AppDbContext db,
    int pagina = 1,
    int tamanho = 50,
    CancellationToken ct = default) =>
{
    // O cliente pede o que quiser; o teto é seu.
    tamanho = Math.Clamp(tamanho, 1, 200);
    pagina  = Math.Max(pagina, 1);

    return await db.Clientes
        .AsNoTracking()
        .OrderBy(c => c.Id)
        .Skip((pagina - 1) * tamanho)
        .Take(tamanho)
        .Select(c => new ClienteResumo(c.Id, c.Nome, c.Email))
        .ToListAsync(ct);
});
Paginação sem OrderBy não é paginação

Sem ordenação explícita, o banco não garante ordem alguma entre execuções. A página 2 pode repetir itens da 1 e omitir outros — sem erro, sem aviso. A ordenação precisa ainda ser determinística: se ordena por CriadoEm e há empates, desempate por Id.

Por que a página 5.000 é lenta

Skip(n) vira OFFSET n no SQL, e OFFSET não é um salto — o banco precisa localizar e descartar as n primeiras linhas antes de começar a devolver. A página 1 é instantânea; a página 5.000 lê 250 mil linhas para entregar 50.

A alternativa é a keyset pagination (ou seek): em vez de dizer "pule 250 mil", o cliente diz "me dê o que vem depois deste id".

ClientesEndpoints.csC#
app.MapGet("/clientes", async (
    AppDbContext db,
    int? depoisDe,
    int tamanho = 50,
    CancellationToken ct = default) =>
{
    tamanho = Math.Clamp(tamanho, 1, 200);

    var itens = await db.Clientes
        .AsNoTracking()
        .Where(c => depoisDe == null || c.Id > depoisDe)
        .OrderBy(c => c.Id)
        .Take(tamanho)
        .Select(c => new ClienteResumo(c.Id, c.Nome, c.Email))
        .ToListAsync(ct);

    return new
    {
        itens,
        proximoCursor = itens.Count == tamanho ? itens[^1].Id : (int?)null
    };
});

O banco usa o índice para posicionar direto no ponto certo. A página 5.000 custa o mesmo que a página 1. Existem duas contrapartidas: não dá para pular para uma página arbitrária (só avançar e voltar), e o cursor precisa ser baseado em coluna indexada e única.

CenárioAbordagem
Tela administrativa com "ir para a página N"Skip/Take com teto baixo de páginas
Scroll infinito, feed, app mobileKeyset pagination
API pública, exportação, sincronizaçãoKeyset pagination, sempre

E a contagem total?

Devolver total em toda página significa um COUNT(*) com os mesmos filtros a cada requisição — em tabela grande, frequentemente mais caro que a própria página de dados. Três saídas, em ordem de preferência: não devolver o total (o padrão de scroll infinito), devolver apenas temMais buscando tamanho + 1 registros, ou calcular o total uma vez e cachear.

Streaming: entregar sem acumular

Quando o resultado é grande por natureza — exportação, relatório, sincronização —, paginar não resolve. O caminho é não segurar tudo na memória em momento nenhum.

O ASP.NET Core serializa IAsyncEnumerable<T> de forma incremental: cada item é escrito no corpo da resposta e liberado, sem lista intermediária.

ExportacaoEndpoints.csC#
app.MapGet("/pedidos/exportar", (AppDbContext db, CancellationToken ct) =>
    db.Pedidos
      .AsNoTracking()
      .OrderBy(p => p.Id)
      .Select(p => new PedidoResumo(p.Id, p.CriadoEm, p.Total))
      .AsAsyncEnumerable());   // nunca existe uma List na memória
O custo escondido do streaming a partir do banco

A conexão com o banco e o DataReader ficam abertos durante toda a escrita da resposta. Um cliente lento em rede ruim segura uma conexão do pool por minutos. Com várias exportações simultâneas, o pool esgota e a aplicação inteira para — inclusive endpoints que nada têm a ver com exportação. Se o volume é alto, o padrão certo é enfileirar o trabalho, gerar o arquivo em background e entregar um link.

Arquivos: streams em vez de byte[]

Esse é o erro mais direto de todos. File.ReadAllBytesAsync em um vídeo de 500 MB aloca 500 MB de uma vez — direto no Large Object Heap, com todo o custo de GC que isso implica.

ArquivosEndpoints.csC#
// Materializa o arquivo inteiro na memória
app.MapGet("/arquivos/{id}", async (string id) =>
{
    var bytes = await File.ReadAllBytesAsync(Caminho(id));
    return Results.File(bytes, "application/pdf");
});

// Envia em blocos, com suporte a Range e retomada de download
app.MapGet("/arquivos/{id}", (string id) =>
    Results.File(
        Caminho(id),
        contentType: "application/pdf",
        fileDownloadName: "documento.pdf",
        enableRangeProcessing: true));

Na entrada vale o mesmo princípio. Um upload não deve ser copiado para um MemoryStream antes de ir para o destino — copie do stream da requisição direto para o storage:

UploadEndpoints.csC#
app.MapPost("/upload", async (IFormFile arquivo, CancellationToken ct) =>
{
    await using var destino = File.Create(CaminhoDestino(arquivo.FileName));
    await using var origem  = arquivo.OpenReadStream();

    await origem.CopyToAsync(destino, ct);
    return Results.Ok();
})
.DisableAntiforgery();
Limite o tamanho do corpo — é defesa e é performance

O Kestrel já impõe um teto padrão de 30 MB por requisição. Ajuste conscientemente por endpoint com .WithMetadata(new RequestSizeLimitAttribute(...)) em vez de remover o limite globalmente. Sem teto, qualquer cliente decide sozinho quanta memória e quanto disco do seu servidor vai consumir.

Compressão e formato do payload

Antes de otimizar a geração da resposta, verifique se ela precisa ser tão grande. Duas perguntas resolvem muito:

  • Todo campo devolvido é usado pelo cliente? Projeção (item 03) costuma cortar mais bytes do que qualquer compressão.
  • Nulos estão sendo serializados à toa? JsonIgnoreCondition.WhenWritingNull reduz payloads com muitos campos opcionais sem alterar contrato.

Compressão de resposta ajuda — e tem uma armadilha de segurança que o item 09 detalha.

Checklist

  • Nenhum endpoint de listagem sem paginação
  • Tamanho de página com teto imposto pelo servidor
  • OrderBy determinístico em toda consulta paginada
  • Keyset pagination onde há navegação profunda ou API pública
  • COUNT(*) por página evitado ou cacheado
  • Exportações grandes por streaming — ou por processamento em background
  • Arquivos servidos por stream, nunca por byte[]
  • Upload copiado direto para o destino, sem MemoryStream
  • Limite de tamanho de corpo definido por endpoint
