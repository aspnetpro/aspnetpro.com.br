Produção: como a aplicação é publicada, hospedada e observada

Os nove itens anteriores tratam do seu código. Este trata do ambiente que executa esse código — e é onde um build errado, um contêiner sem limite declarado ou um log em Debug jogam fora todo o trabalho anterior.

ASP.NET Core 10 Leitura: ~7 min Nível: intermediário

O ambiente errado custa mais que qualquer otimização

Antes de discutir GC ou AOT, duas variáveis decidem mais sobre o desempenho da aplicação do que qualquer linha de código: a configuração do build e o valor de ASPNETCORE_ENVIRONMENT.

Em Debug, o compilador desliga otimizações, mantém verificações extras e o JIT gera código propositalmente mais simples para permitir depuração. A diferença para Release em caminho quente não é de alguns pontos percentuais — é de fator.

terminalCLI
# Release é o padrão de dotnet publish desde o .NET 8,
# mas seja explícito: pipelines antigos e scripts herdados nem sempre são.
dotnet publish -c Release
Development em produção

Com ASPNETCORE_ENVIRONMENT=Development no servidor, a aplicação ativa a página de exceção detalhada — que expõe stack trace, caminho de arquivo e configuração para qualquer visitante — e desliga comportamentos de cache. É simultaneamente um problema de performance e uma falha de segurança. Confira o valor real da variável no ambiente publicado, não no launchSettings.json, que só vale na sua máquina.

JIT, ReadyToRun e o custo da primeira requisição

O .NET compila para IL e o JIT traduz para código nativo em tempo de execução. Isso significa que os primeiros acessos a cada caminho de código pagam a compilação — o famoso "a primeira requisição é lenta".

O Tiered PGO ataca isso de forma automática: o runtime começa com código rápido de gerar, observa como o método realmente se comporta em produção e recompila os trechos quentes com base nesses dados. Está ligado por padrão desde o .NET 8, e o resultado é código que pode superar o de uma compilação estática, porque considera o comportamento real.

O ReadyToRun ataca o outro lado: pré-compila os assemblies durante o publish, para que o processo já suba com código nativo disponível.

MinhaApi.csprojXML
<PropertyGroup>
  <PublishReadyToRun>true</PublishReadyToRun>
</PropertyGroup>

Publicar com ReadyToRun exige um runtime identifier — dotnet publish -c Release -r linux-x64. O custo é um artefato maior; o ganho é startup mais curto e menos variação nas primeiras requisições. Vale principalmente onde o processo reinicia com frequência: escala automática agressiva, deploys constantes, ambientes serverless.

Se o startup é o problema, meça o startup

Vale a mesma regra do item 01. Compare o tempo até a primeira resposta com e sem ReadyToRun, no seu ambiente. Em aplicação que sobe uma vez e fica no ar por dias, o ganho é irrelevante e o artefato maior é custo puro.

Native AOT: quando faz sentido

O Native AOT vai além: compila tudo para um executável nativo, sem JIT e sem runtime separado. Startup na casa de milissegundos e consumo de memória bem menor.

O preço é rigidez. Sem JIT, não existe geração de código em tempo de execução — e é exatamente disso que dependem reflexão dinâmica, Expression.Compile e boa parte dos ORMs e bibliotecas de serialização por reflexão.

CenárioNative AOT
Minimal API pequena, com JSON via source generatorBoa candidata
Worker / serviço de fila sem dependências reflexivasBoa candidata
Aplicação com EF CoreNão suportado
MVC ou Razor PagesNão suportado
Código com reflexão dinâmica ou plugins carregados em runtimeEvite

Repare que o item 06 é pré-requisito: sem o source generator de System.Text.Json, a serialização por reflexão quebra sob AOT. Habilite a análise antes de tentar publicar — os avisos apontam o que não sobrevive ao recorte de código:

MinhaApi.csprojXML
<PropertyGroup>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>  <!-- avalie: afeta cultura e ordenação -->
</PropertyGroup>

GC e contêiner: o par que costuma estar desalinhado

ASP.NET Core usa Server GC por padrão: múltiplas heaps, uma por núcleo, com coletas paralelas. É a escolha certa para throughput e não precisa ser mexida na maioria dos casos.

O problema aparece no contêiner. O GC dimensiona suas heaps a partir do que enxerga de memória e de CPU. Se o contêiner não declara limites, o runtime vê a máquina inteira — reserva com folga, adia coletas e o orquestrador mata o processo por estourar a memória do pod. O sintoma clássico é OOMKilled em uma aplicação que "não vaza nada".

deployment.yamlYAML
resources:
  requests:
    memory: "512Mi"
    cpu: "500m"
  limits:
    memory: "1Gi"      # o GC respeita este limite e se ajusta a ele
    cpu: "1000m"

Com o limite declarado, o runtime detecta o teto do cgroup e calibra o heap sozinho. Só depois disso faz sentido considerar ajuste fino:

VariávelQuando considerar
DOTNET_GCHeapHardLimitPercentReservar margem para consumo fora do heap gerenciado (buffers nativos, bibliotecas não gerenciadas)
DOTNET_gcServer=0Muitas instâncias pequenas, com pouca CPU cada, onde memória importa mais que throughput
DOTNET_GCConserveMemoryTrocar um pouco de CPU por menor pegada de memória
DOTNET_TieredPGO=0Praticamente nunca. Está ligado por padrão porque compensa
Limite de CPU também é parâmetro do runtime

O thread pool e o número de heaps do Server GC derivam da contagem de processadores visível. Um contêiner com cpu: 500m em um nó de 32 núcleos ainda enxerga 32 — e cria estruturas para uma máquina que não tem. Declare o limite; quando o comportamento continuar estranho, DOTNET_PROCESSOR_COUNT permite informar explicitamente o valor.

Log: o custo que ninguém mede

Log é código que roda em toda requisição. Em nível Debug ou Trace em produção, ele domina o tempo de resposta — e ainda gera custo de armazenamento e ingestão na ferramenta de observabilidade.

appsettings.Production.jsonJSON
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning",
      "Microsoft.EntityFrameworkCore.Database.Command": "Warning"
    }
  }
}

Além do nível, a forma de escrever importa. A chamada convencional a LogInformation recebe object[], o que causa boxing de cada valor de tipo primitivo — mesmo quando o nível está desligado e a mensagem nunca será emitida. O source generator de logging resolve isso em tempo de compilação:

PedidoLogs.csC#
public static partial class PedidoLogs
{
    [LoggerMessage(
        Level = LogLevel.Information,
        Message = "Pedido {PedidoId} confirmado em {Duracao}ms")]
    public static partial void PedidoConfirmado(
        this ILogger logger, Guid pedidoId, long duracao);
}

// no caminho quente, sem boxing e sem alocação quando o nível está desligado
logger.PedidoConfirmado(pedido.Id, cronometro.ElapsedMilliseconds);
Console logger em contêiner

Escrever no console é I/O — e, dependendo do provider e do volume, com sincronização. Em contêiner isso ainda passa pelo driver de log do runtime e vai para disco. Aplicação com log verboso por requisição consegue gastar mais tempo registrando o que fez do que fazendo.

Observabilidade contínua: fechando o ciclo

O item 01 pediu medição antes de otimizar. Este item pede medição depois, para sempre — porque a carga muda, o volume de dados cresce e a consulta que era rápida com 10 mil linhas deixa de ser com 10 milhões.

O .NET expõe métricas nativas via System.Diagnostics.Metrics, e o OpenTelemetry as coleta sem código específico de fornecedor:

Program.csC#
builder.Services.AddOpenTelemetry()
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddRuntimeInstrumentation()      // GC, thread pool, exceções
        .AddOtlpExporter())
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddOtlpExporter());

var app = builder.Build();

app.MapHealthChecks("/health");

Os sinais que valem a pena acompanhar em painel são poucos, e todos já apareceram neste guia:

Duração de comando de bancoN+1 e consulta sem índice (item 03)

O hábito que separa quem resolve de quem apaga incêndio

Depois de cada deploy relevante, compare o p95 dos endpoints principais com o da semana anterior. Regressão de performance quase nunca chega como incidente — chega como uma piora de poucos milissegundos que se acumula por meses, até o dia em que alguém abre um chamado dizendo que "o sistema ficou lento". Quem olha o gráfico toda semana sabe exatamente qual deploy causou.

Checklist

  • Publicação em Release, confirmada no pipeline
  • ASPNETCORE_ENVIRONMENT verificado no ambiente publicado
  • ReadyToRun avaliado onde o tempo de startup importa
  • Native AOT considerado apenas onde as restrições cabem
  • Limites de memória e CPU declarados no contêiner
  • Server GC mantido, salvo motivo medido para mudar
  • Nível de log em Information ou acima em produção
  • [LoggerMessage] nos logs do caminho quente
  • Health check exposto e monitorado pelo orquestrador
  • Métricas de runtime, ASP.NET Core e HttpClient exportadas
  • p95 comparado antes e depois de cada deploy relevante
Chegou ao fim dos 10 itens

Se for aplicar apenas três coisas deste guia, comece por: medir com percentil antes de mexer em qualquer coisa (item 01), eliminar as consultas N+1 do EF Core (item 03) e colocar cache onde o mesmo dado é lido repetidamente (item 05). É onde está a maior parte do ganho, na maioria das aplicações.
