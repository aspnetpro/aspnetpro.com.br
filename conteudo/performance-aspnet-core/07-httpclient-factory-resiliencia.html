HttpClient: socket exhaustion, DNS e o timeout de 100 segundos

Existem duas formas óbvias de usar HttpClient, e ambas estão erradas. Uma esgota as portas do servidor; a outra deixa a aplicação chamando um endereço IP que não existe mais.

ASP.NET Core 10 Leitura: ~7 min Nível: essencial

Armadilha 1: um HttpClient por chamada

Como HttpClient implementa IDisposable, o instinto de todo desenvolvedor C# é embrulhá-lo em using:

CepService.csC#
public async Task<Endereco?> ConsultarAsync(string cep, CancellationToken ct)
{
    using var http = new HttpClient();   // o erro clássico
    return await http.GetFromJsonAsync<Endereco>($"https://api/cep/{cep}", ct);
}

Descartar o HttpClient fecha a conexão TCP subjacente. Mas o socket não é liberado de imediato: ele entra em estado TIME_WAIT e ali permanece por volta de 4 minutos, por exigência do próprio protocolo TCP — é assim que a pilha de rede garante que pacotes atrasados da conexão anterior não sejam confundidos com uma conexão nova.

O sistema operacional dispõe de um intervalo limitado de portas efêmeras. A conta é direta: 200 requisições por segundo × 240 segundos de espera = 48 mil portas presas simultaneamente. Quando o intervalo se esgota, toda tentativa de abrir conexão falha — inclusive as que não têm nada a ver com esse serviço.

O sintoma engana

O erro que aparece é SocketException: Only one usage of each socket address is normally permitted, muitas vezes em um serviço completamente diferente do culpado. E some sozinho depois de alguns minutos de tráfego baixo, o que faz o time concluir que "foi instabilidade da rede" e nunca investigar.

Armadilha 2: um singleton eterno

Sabendo do problema acima, a reação natural é criar um static readonly HttpClient e reaproveitar sempre. Isso elimina o socket exhaustion — e cria um problema mais difícil de diagnosticar.

O HttpClient resolve o DNS quando abre a conexão e mantém a conexão viva. Se o serviço de destino trocar de IP — failover, escala automática, novo deploy, troca de balanceador —, sua aplicação continua conversando com o endereço antigo. Indefinidamente. Até alguém reiniciar o processo.

A solução: IHttpClientFactory

A fábrica resolve os dois problemas ao mesmo tempo. Ela mantém um pool de handlers reutilizáveis (elimina o socket exhaustion) e recicla esses handlers periodicamente (faz o DNS ser resolvido de novo).

Program.csC#
builder.Services.AddHttpClient<CepClient>(client =>
{
    client.BaseAddress = new("https://api.exemplo.com.br/");
    client.Timeout = TimeSpan.FromSeconds(5);   // o padrão é 100s
})
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    // Recicla a conexão e força nova resolução de DNS
    PooledConnectionLifetime = TimeSpan.FromMinutes(2),
    MaxConnectionsPerServer = 100
});

O typed client é a forma mais limpa de consumir: a dependência fica explícita e o cliente é injetado pronto.

CepClient.csC#
public sealed class CepClient(HttpClient http)
{
    public Task<Endereco?> ConsultarAsync(string cep, CancellationToken ct) =>
        http.GetFromJsonAsync<Endereco>($"cep/{cep}", ct);
}
Pode injetar como singleton?

Sim — desde que seja pela fábrica. O HttpClient entregue por typed client tem tempo de vida transient, mas o handler por trás dele é reaproveitado do pool. Descartar o HttpClient não fecha conexão nenhuma. Já um new HttpClient() guardado em campo estático continua sendo o problema de DNS descrito acima.

Timeout: o padrão de 100 segundos é perigoso

Cem segundos é uma eternidade em uma requisição web. Se um serviço externo trava, cada chamada segura uma requisição da sua aplicação por 100 segundos. Com 200 requisições por segundo, isso significa 20 mil requisições acumuladas antes do primeiro timeout — e a sua aplicação cai junto com a dependência.

O timeout precisa ser dimensionado pelo que é útil, não pelo que é possível. Se a resposta demora mais de 3 segundos, o usuário já foi embora: insistir só consome recurso.

Tipo de chamadaTimeout razoável
Consulta síncrona no caminho da resposta2 a 5 segundos
Integração em background / job15 a 30 segundos
Upload ou download de arquivoPor operação, com CancellationToken próprio

Resiliência: útil e perigosa na mesma medida

O pacote Microsoft.Extensions.Http.Resilience traz um pipeline pronto com rate limiter, timeout, retry, circuit breaker e timeout total:

Program.csC#
builder.Services.AddHttpClient<CepClient>()
    .AddStandardResilienceHandler(options =>
    {
        options.Retry.MaxRetryAttempts = 2;
        options.Retry.UseJitter = true;
        options.AttemptTimeout.Timeout = TimeSpan.FromSeconds(3);
        options.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(10);
    });
Retry mal configurado transforma lentidão em queda

O serviço externo está sobrecarregado e responde devagar. Sua aplicação tenta de novo. E de novo. Cada requisição original vira três, e a carga sobre um serviço já em dificuldade triplica — exatamente quando ele precisa de trégua. Três regras que evitam isso: jitter ligado (senão todas as instâncias tentam no mesmo instante), circuit breaker presente (para de bater quando a taxa de erro explode) e retry apenas em operações idempotentes — repetir um POST de cobrança pode cobrar o cliente duas vezes.

Dois erros que sobram em revisão de código

Ler o corpo inteiro antes de precisar dele

ReadAsStringAsync materializa a resposta completa em uma string na memória, para em seguida desserializar. Em respostas grandes, é o dobro de alocação sem motivo:

CepClient.csC#
// String intermediária de vários MB
var json = await resposta.Content.ReadAsStringAsync(ct);
var dados = JsonSerializer.Deserialize<Dados>(json);

// Desserializa direto do stream
var dados = await resposta.Content.ReadFromJsonAsync<Dados>(ct);

Esperar o corpo inteiro quando só o cabeçalho importa

Por padrão, SendAsync só retorna depois de baixar a resposta completa. Para respostas grandes que serão processadas em streaming, peça para retornar assim que os headers chegarem:

ArquivoClient.csC#
using var resposta = await http.SendAsync(
    requisicao,
    HttpCompletionOption.ResponseHeadersRead,
    ct);

await using var stream = await resposta.Content.ReadAsStreamAsync(ct);
await stream.CopyToAsync(destino, ct);
Propague o CancellationToken também aqui

Sem o token, uma chamada externa continua em andamento mesmo depois de o usuário abandonar a requisição. Somando o timeout de 100 segundos padrão, você acumula trabalho inútil justamente sob pressão. O token do HttpContext deve chegar até a última chamada HTTP da cadeia.

Checklist

  • Nenhum new HttpClient() no código
  • Clientes registrados via AddHttpClient, preferencialmente tipados
  • PooledConnectionLifetime configurado para renovar DNS
  • Timeout explícito e curto no caminho da requisição
  • Retry com jitter, limite de tentativas e circuit breaker
  • Retry restrito a operações idempotentes
  • ReadFromJsonAsync no lugar de ReadAsStringAsync
  • ResponseHeadersRead em downloads processados por stream
  • CancellationToken propagado até a chamada externa
