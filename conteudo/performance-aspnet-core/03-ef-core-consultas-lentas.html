EF Core: as consultas que derrubam a aplicação

Na esmagadora maioria dos casos, o problema não é o EF Core ser lento — é a consulta que ele foi instruído a gerar. Cinco padrões respondem por quase todo o tempo perdido no acesso a dados.

EF Core 10 Leitura: ~8 min Nível: essencial

Regra zero: veja o SQL

Discutir performance de EF Core sem olhar o SQL gerado é adivinhação. Ligue o log de comandos em desenvolvimento e a conversa muda de qualidade imediatamente:

Program.csC#
builder.Services.AddDbContext<AppDbContext>(options =>
{
    options.UseSqlServer(cs);

    if (builder.Environment.IsDevelopment())
    {
        options.LogTo(Console.WriteLine, LogLevel.Information);
        options.EnableSensitiveDataLogging();   // NUNCA em produção
    }
});
EnableSensitiveDataLogging fora do Development

Ela coloca os valores dos parâmetros no log — CPF, e-mail, token, o que estiver na consulta. É vazamento de dado pessoal em arquivo de log e problema de LGPD. Deixe sempre dentro do if (IsDevelopment()).

1. N+1: uma consulta vira quinhentas

É o campeão absoluto. O código parece inofensivo porque o acesso ao banco está escondido dentro do laço:

PedidoService.csC#
var pedidos = await _db.Pedidos.ToListAsync(ct);   // 1 consulta

foreach (var p in pedidos)
{
    // +1 consulta POR pedido. Com 500 pedidos, 501 idas ao banco.
    var cliente = await _db.Clientes.FindAsync([p.ClienteId], ct);
    Console.WriteLine(cliente.Nome);
}

Cada ida ao banco custa latência de rede. Mesmo a 2 ms por consulta, 501 consultas viram 1 segundo gasto quase inteiramente em espera. E o efeito é multiplicativo: 100 requisições simultâneas geram 50 mil consultas e saturam o pool de conexões.

A correção é carregar o relacionamento junto:

PedidoService.csC#
var pedidos = await _db.Pedidos
    .Include(p => p.Cliente)
    .ToListAsync(ct);   // 1 consulta, com JOIN
Lazy loading transforma N+1 em algo invisível

Com proxies de lazy loading ativados, o simples pedido.Cliente.Nome dispara uma consulta — sem nada no código que indique acesso a banco. Some isso a um foreach e você tem N+1 que nem aparece em code review. Em aplicação web, o padrão saudável é lazy loading desligado e carregamento explícito.

2. Trazer a entidade inteira quando você quer três campos

Uma listagem que mostra número, data e nome do cliente não precisa de Observacoes, XmlNotaFiscal nem das 30 outras colunas da tabela. Projetar reduz bytes trafegados, memória alocada e — como bônus — elimina o tracking:

PedidoQueries.csC#
// Traz todas as colunas de Pedidos e de Clientes
var lento = await _db.Pedidos
    .Include(p => p.Cliente)
    .ToListAsync(ct);

// Traz exatamente 3 colunas — e não rastreia nada
var rapido = await _db.Pedidos
    .Select(p => new PedidoResumo(
        p.Id,
        p.CriadoEm,
        p.Cliente.Nome))
    .ToListAsync(ct);

Repare que no segundo caso o Include desaparece: dentro de um Select, o EF Core resolve p.Cliente.Nome como um JOIN e traz só a coluna necessária. Include junto de projeção é redundante e, em muitos casos, ignorado.

AsNoTracking, quando a entidade é necessária

Quando você realmente precisa da entidade — e não vai alterá-la —, desligue o rastreamento. Ao rastrear, o EF Core guarda um snapshot de cada entidade para detectar mudanças no SaveChanges. Em uma consulta somente leitura, isso é CPU e memória gastos por nada:

PedidoQueries.csC#
var pedidos = await _db.Pedidos
    .AsNoTracking()
    .Where(p => p.Status == Status.Aberto)
    .ToListAsync(ct);
Padrão global, exceção pontual

Se a maior parte da sua aplicação é leitura, inverta o padrão com options.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking) e chame AsTracking() só onde houver escrita. Assim o comportamento caro passa a ser o explícito, e não o esquecido.

3. Explosão cartesiana: o Include que multiplica linhas

Dois Include de coleções irmãs na mesma consulta produzem um produto cruzado no SQL:

BlogQueries.csC#
var blogs = await _db.Blogs
    .Include(b => b.Posts)
    .Include(b => b.Colaboradores)
    .ToListAsync(ct);

Um blog com 100 posts e 10 colaboradores não devolve 110 linhas: devolve 1.000 — cada post repetido para cada colaborador. Os dados do blog vêm duplicados mil vezes. O EF Core desmonta tudo corretamente na memória, mas a rede já transportou o volume inteiro.

O AsSplitQuery divide em uma consulta por coleção:

BlogQueries.csC#
var blogs = await _db.Blogs
    .Include(b => b.Posts)
    .Include(b => b.Colaboradores)
    .AsSplitQuery()      // 3 SELECTs, sem duplicação
    .ToListAsync(ct);
Split query não é gratuito

São várias idas ao banco em vez de uma — pior quando a latência de rede é alta. E, por não rodarem na mesma consulta, os resultados não são consistentes entre si: um colaborador pode ser inserido entre o primeiro e o segundo SELECT. Se isso importar, use AsSplitQuery dentro de uma transação com nível de isolamento adequado. A regra prática: muitas linhas duplicadas → split; coleção pequena → deixe como está.

4. Carregar para alterar (ou para apagar)

Marcar 10 mil pedidos como cancelados carregando cada um é um desperdício em três camadas: SELECT gigante, 10 mil entidades no change tracker e 10 mil UPDATEs individuais.

PedidoService.csC#
// Carrega tudo na memória para depois atualizar
var antigos = await _db.Pedidos
    .Where(p => p.CriadoEm < limite)
    .ToListAsync(ct);

foreach (var p in antigos) p.Status = Status.Cancelado;
await _db.SaveChangesAsync(ct);
PedidoService.csC#
// Um único UPDATE, executado direto no banco
await _db.Pedidos
    .Where(p => p.CriadoEm < limite)
    .ExecuteUpdateAsync(s => s.SetProperty(p => p.Status, Status.Cancelado), ct);

// E o equivalente para remoção em massa
await _db.Logs
    .Where(l => l.CriadoEm < limite)
    .ExecuteDeleteAsync(ct);

Duas ressalvas importantes: essas operações não passam pelo change tracker — entidades já carregadas na memória ficam desatualizadas — e não disparam interceptors nem lógica de SaveChanges, incluindo auditoria automática e soft delete implementado dessa forma.

5. A consulta que o índice não cobre

Nenhuma otimização de C# compensa um table scan. Se a consulta filtra por Status e CriadoEm e não existe índice para isso, o banco lê a tabela inteira — e o EF Core não tem como saber disso.

AppDbContext.csC#
protected override void OnModelCreating(ModelBuilder b)
{
    b.Entity<Pedido>()
     .HasIndex(p => new { p.Status, p.CriadoEm })
     .HasDatabaseName("IX_Pedidos_Status_CriadoEm");
}

Duas armadilhas comuns de tornar a consulta non-sargable, ou seja, incapaz de usar o índice:

  • Aplicar função sobre a coluna: Where(p => p.Nome.ToLower() == termo). Prefira ajustar o collation da coluna a envolver a coluna em função.
  • Contains no meio da string, que vira LIKE '%termo%' e não usa índice B-tree. Para busca textual de verdade, o caminho é full-text search do banco.

Peças de ajuste fino

DbContext pooling

Criar um DbContext por requisição envolve montar estruturas internas que poderiam ser reaproveitadas. O pooling reutiliza as instâncias, reinicializando o estado:

Program.csC#
builder.Services.AddDbContextPool<AppDbContext>(o => o.UseSqlServer(cs));

O ganho é real, porém modesto perto dos itens anteriores — e existe um requisito: o contexto não pode guardar estado próprio (usuário atual, tenant, campos preenchidos no construtor). Como a instância é reaproveitada entre requisições, esse estado vazaria de um usuário para outro.

Compiled queries

Toda consulta LINQ passa por tradução para SQL. O EF Core mantém um cache dessa tradução, mas ainda há custo em calcular a chave do cache. Em um endpoint executado milhares de vezes por segundo, compilar antecipadamente elimina essa etapa:

PedidoQueries.csC#
private static readonly Func<AppDbContext, int, Task<Pedido?>> _porId =
    EF.CompileAsyncQuery((AppDbContext db, int id) =>
        db.Pedidos.AsNoTracking().FirstOrDefault(p => p.Id == id));

public Task<Pedido?> ObterAsync(int id) => _porId(_db, id);

É otimização de último passo, para caminho quente já identificado no item 01. Aplicar em todo o repositório só adiciona ruído.

A ordem que resolve mais rápido

Elimine N+1 → projete com Select → desligue tracking em leitura → crie o índice que falta → só então avalie pooling e compiled query. Os quatro primeiros costumam entregar ganhos de ordem de grandeza; os dois últimos, alguns pontos percentuais.

Checklist

  • SQL gerado inspecionado nas consultas críticas
  • Nenhum acesso a banco dentro de foreach
  • Lazy loading desligado em aplicação web
  • Listagens usando Select para projetar apenas o necessário
  • AsNoTracking em toda consulta somente leitura
  • AsSplitQuery onde há múltiplos Include de coleções irmãs
  • ExecuteUpdateAsync / ExecuteDeleteAsync nas operações em massa
  • Índices cobrindo os filtros mais frequentes
  • Nenhuma função aplicada sobre coluna filtrada
  • EnableSensitiveDataLogging restrito ao Development
