JSON: source generator e o custo escondido da serialização

Em uma API, serializar é provavelmente a operação mais executada de todo o processo. Ela roda em toda resposta, com CPU do servidor, e quase ninguém olha para ela — até aparecer no profiler ocupando 20% do tempo.

ASP.NET Core 10 Leitura: ~6 min Nível: intermediário

O que acontece quando você serializa

Na primeira vez que o System.Text.Json encontra um tipo, ele usa reflection para descobrir propriedades, atributos, política de nomes e conversores. Com esse levantamento, monta um plano de serialização e o guarda em cache.

O custo, portanto, é pago uma vez por tipo — desde que o cache seja reaproveitado. E é exatamente aí que a maioria das aplicações joga o ganho fora, de duas formas diferentes.

Erro nº 1: criar JsonSerializerOptions a cada chamada

Este é sutil e devastador, porque o código parece limpo:

IntegracaoService.csC#
public string Serializar(Pedido pedido)
{
    // Instância nova a cada chamada = cache de metadados novo a cada chamada
    var options = new JsonSerializerOptions
    {
        PropertyNamingPolicy = JsonNamingPolicy.CamelCase
    };

    return JsonSerializer.Serialize(pedido, options);
}

O cache de metadados vive dentro da instância de JsonSerializerOptions. Uma instância nova significa refazer todo o trabalho de reflection do zero — e alocar tudo de novo. Em um endpoint chamado mil vezes por segundo, é reflection mil vezes por segundo para descobrir sempre as mesmas propriedades.

IntegracaoService.csC#
// Uma instância, criada uma vez, reaproveitada sempre
private static readonly JsonSerializerOptions _json = new()
{
    PropertyNamingPolicy = JsonNamingPolicy.CamelCase,
    DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull
};

public string Serializar(Pedido pedido) =>
    JsonSerializer.Serialize(pedido, _json);
Nas rotas normais isso já está resolvido

Respostas devolvidas por Minimal APIs e controllers usam a instância única configurada na aplicação. O problema aparece em código que serializa manualmente: chamada a API externa, gravação em fila, publicação de evento, escrita em cache distribuído. É lá que a instância descartável costuma nascer.

Erro nº 2: pagar reflection quando dá para não pagar

O source generator resolve o problema na raiz. Em vez de descobrir a estrutura do tipo em tempo de execução, ele gera o código de serialização durante a compilação. Não há reflection, o startup é mais rápido e o custo por chamada cai.

AppJsonContext.csC#
using System.Text.Json.Serialization;

[JsonSourceGenerationOptions(
    PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase,
    DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull)]
[JsonSerializable(typeof(PedidoDto))]
[JsonSerializable(typeof(PedidoDto[]))]
[JsonSerializable(typeof(ProblemDetails))]
internal partial class AppJsonContext : JsonSerializerContext;

Registrado no pipeline, ele passa a atender as respostas da API. A cadeia de resolvers permite manter o comportamento padrão como fallback para tipos não declarados:

Program.csC#
// Minimal APIs
builder.Services.ConfigureHttpJsonOptions(options =>
{
    options.SerializerOptions.TypeInfoResolverChain.Insert(0, AppJsonContext.Default);
});

// Controllers
builder.Services.AddControllers().AddJsonOptions(options =>
{
    options.JsonSerializerOptions.TypeInfoResolverChain.Insert(0, AppJsonContext.Default);
});

E no uso manual, basta passar o tipo gerado — sem JsonSerializerOptions nenhum:

IntegracaoService.csC#
var json = JsonSerializer.Serialize(pedido, AppJsonContext.Default.PedidoDto);

var pedido = JsonSerializer.Deserialize(json, AppJsonContext.Default.PedidoDto);
O source generator tem limites — e eles são o ponto

Ele precisa conhecer os tipos em tempo de compilação. Serialização de object, de hierarquias resolvidas em runtime ou de tipos montados dinamicamente não é coberta. Se você depende disso, mantenha o resolver padrão na cadeia como fallback. E se a meta é Native AOT ou trimming, o source generator deixa de ser otimização e passa a ser obrigatório: sem ele, o trimmer remove os metadados que a reflection procuraria.

O payload também é performance

Serializar rápido resolve CPU. Serializar menos resolve CPU, memória e rede ao mesmo tempo — e costuma render mais.

Devolva um DTO, não a entidade

Serializar a entidade do EF Core arrasta propriedades de navegação, campos internos e colunas que ninguém consome. Em relacionamento bidirecional, ainda corre o risco de referência cíclica. Um record com os campos da tela resolve tudo isso e ainda documenta o contrato da API.

Dtos.csC#
public sealed record PedidoDto(int Id, DateTime CriadoEm, decimal Total);

Corte o que não agrega

AjusteEfeito
DefaultIgnoreCondition = WhenWritingNullRemove campos nulos do payload
WriteIndented = falseÉ o padrão — mantenha assim em produção
[JsonIgnore] em campos internosEvita expor e trafegar o que não é contrato
Enum como número (padrão)Mais compacto que JsonStringEnumConverter
WriteIndented ligado em produção

Formatação com indentação existe para leitura humana em depuração. Ligada em produção, ela infla o payload em 20% a 30% só com espaços em branco — e esse custo é pago em CPU de serialização, banda e tempo de parse do cliente.

Quando nem isso basta: escreva direto em UTF-8

Para respostas de altíssima frequência e formato fixo, dá para pular a camada de objetos e escrever o JSON diretamente, sem alocar strings intermediárias:

MetricasEndpoints.csC#
app.MapGet("/status", async (HttpContext ctx, CancellationToken ct) =>
{
    ctx.Response.ContentType = "application/json";

    await using var writer = new Utf8JsonWriter(ctx.Response.BodyWriter);
    writer.WriteStartObject();
    writer.WriteString("status", "ok");
    writer.WriteNumber("uptimeSegundos", Metricas.UptimeSegundos);
    writer.WriteEndObject();
    await writer.FlushAsync(ct);
});

É verboso e frágil a mudanças de contrato. Reserve para o caso raro em que o profiler apontou a serialização como gargalo real e as opções anteriores já foram aplicadas.

Newtonsoft.Json ainda no projeto?

O System.Text.Json é consideravelmente mais rápido e aloca menos. Se o Newtonsoft.Json segue registrado via AddNewtonsoftJson(), ele passa a atender toda a serialização da aplicação — inclusive endpoints que nunca precisaram dele. Se a dependência existe por um recurso específico (como JSON Patch), isole-a nesse ponto em vez de trocar o serializador global.

Checklist

  • JsonSerializerOptions em campo estático, nunca criado por chamada
  • JsonSerializerContext gerado e registrado na cadeia de resolvers
  • Respostas devolvendo DTO, não entidade de persistência
  • WhenWritingNull ativo em payloads com muitos campos opcionais
  • WriteIndented desligado em produção
  • Source generator obrigatório se o alvo for AOT ou trimming
  • Newtonsoft.Json isolado ou removido
  • Ganho medido com [MemoryDiagnoser] antes de adotar Utf8JsonWriter
