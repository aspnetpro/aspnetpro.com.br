Alocações, GC e strings no caminho quente

Latência que dá picos regulares sem relação com o volume de tráfego costuma ter uma única causa: o coletor de lixo. Ele não é o problema — é o sintoma de código que aloca demais.

ASP.NET Core 10 Leitura: ~7 min Nível: intermediário

Por que alocação vira latência

Alocar no .NET é barato: o ponteiro do heap avança e pronto. O custo não está na alocação — está na coleta. E a coleta acontece na hora que o runtime decidir, não na sua.

O GC organiza objetos em gerações. Objetos novos nascem na gen 0, que é coletada com muita frequência e muito rápido. Quem sobrevive é promovido para gen 1 e depois para gen 2, cuja coleta é cara e pode envolver pausar todas as threads gerenciadas.

Esse desenho pressupõe que a maioria dos objetos morre jovem — e é verdade em uma aplicação web bem escrita: os objetos de uma requisição morrem junto com ela. Duas coisas quebram a premissa:

  • Taxa de alocação alta. A gen 0 enche o tempo todo, coleta o tempo todo, e objetos que ainda estavam sendo usados são promovidos por acidente — passando a exigir coleta cara para morrer.
  • Objetos grandes. Qualquer alocação acima de 85 KB vai direto para o Large Object Heap, que por padrão não é compactado e é coletado apenas junto com a gen 2.
A assinatura no monitoramento

alloc-rate na casa das centenas de MB/s, gen-2-gc-count crescendo continuamente e time-in-gc acima de 10%. Nesse cenário, a latência tem picos que não acompanham a curva de tráfego — porque quem os provoca é a coleta, não o usuário.

De onde vem a alocação

Antes de otimizar, saiba onde procurar. Estas são as fontes que aparecem em quase todo profiler de aplicação .NET:

Strings: a maior fonte de lixo

String em .NET é imutável. Toda operação que "modifica" uma string na verdade cria outra. Em laço, o efeito é quadrático:

RelatorioBuilder.csC#
// 10.000 strings intermediárias; as últimas são enormes e vão para o LOH
var csv = "";
foreach (var linha in linhas)
    csv += $"{linha.Id};{linha.Nome}\n";

// Um buffer que cresce; uma string no final
var sb = new StringBuilder(linhas.Count * 48);   // capacidade estimada
foreach (var linha in linhas)
    sb.Append(linha.Id).Append(';').Append(linha.Nome).Append('\n');

var csv = sb.ToString();

Informar a capacidade inicial evita as realocações internas do StringBuilder — que dobram o buffer e copiam tudo a cada estouro.

StringBuilder para duas strings é pior

Fora de laço, $"{a}-{b}" é mais rápido e aloca menos: o compilador usa o interpolated string handler e resolve tudo em uma passagem. StringBuilder só compensa quando há muitas concatenações ou o número delas é desconhecido.

Span: fatiar sem copiar

ReadOnlySpan<char> é uma janela sobre a memória já existente. Fatiar uma Span não copia nada — apenas ajusta os limites da janela:

DocumentoParser.csC#
// Split aloca um array e uma string por parte
public static string ObterDominio(string email) => email.Split('@')[1];

// Zero alocação: só uma janela sobre a string original
public static ReadOnlySpan<char> ObterDominio(ReadOnlySpan<char> email)
{
    var pos = email.IndexOf('@');
    return pos < 0 ? default : email[(pos + 1)..];
}

Boa parte da BCL já trabalha com Span: int.TryParse, DateTime.TryParse, Encoding.UTF8.GetBytes e vários outros têm sobrecargas que evitam a string intermediária.

Span vive na pilha — e isso restringe onde ela pode ir

Span<T> é um ref struct: não pode ser campo de classe, não pode ser capturada por lambda e não pode atravessar um await. Em método assíncrono, o equivalente é Memory<T>. Essa é a limitação que mais surpreende quem está começando.

ArrayPool: buffers emprestados

Quando o código precisa de um buffer temporário a cada requisição, alugue em vez de alocar:

HashService.csC#
var pool = ArrayPool<byte>.Shared;
var buffer = pool.Rent(8192);   // pode devolver um array MAIOR

try
{
    var lidos = await stream.ReadAsync(buffer.AsMemory(0, 8192), ct);
    Processar(buffer.AsSpan(0, lidos));   // use só o que foi lido
}
finally
{
    pool.Return(buffer);   // SEMPRE, mesmo em exceção
}
Três formas de errar com ArrayPool

Não devolver — o pool esvazia e cada Rent vira uma alocação nova, com toda a complexidade e nenhum ganho. Usar depois de devolver — outra thread já está escrevendo nesse array, e o bug resultante é intermitente e quase impossível de reproduzir. Assumir o tamanho pedido — Rent(8192) pode devolver 16.384 posições, e o conteúdo residual não é limpo. Trabalhe sempre com o comprimento real.

Para buffers pequenos e de vida curtíssima, stackalloc dispensa até o pool:

Formatador.csC#
Span<char> buffer = stackalloc char[32];   // tamanho FIXO e pequeno

if (valor.TryFormat(buffer, out var escritos, "N2"))
    return new string(buffer[..escritos]);

A regra é rígida: tamanho constante e pequeno (algumas centenas de bytes). stackalloc com tamanho vindo de entrada do usuário é StackOverflowException — que não pode ser capturada e derruba o processo inteiro.

Logging: alocação que ninguém percebe

Um _logger.LogDebug(...) com interpolação aloca a string formatada mesmo quando o nível Debug está desligado — a interpolação acontece antes da chamada. Em caminho quente, é lixo puro:

PedidoService.csC#
// Formata a string mesmo se Debug estiver desligado
_logger.LogDebug($"Processando pedido {pedido.Id} do cliente {cliente.Nome}");

// Template + argumentos: só formata se o nível estiver ativo
_logger.LogDebug("Processando pedido {PedidoId} do cliente {Cliente}", pedido.Id, cliente.Nome);

A versão com template ainda causa boxing dos argumentos de tipo valor. O source generator de logging elimina até isso — e o item 10 mostra como.

O que NÃO otimizar

Este item é o que mais gera desperdício de tempo, porque parece produtivo. Três limites úteis:

  • LINQ não é o inimigo. Em uma requisição que faz I/O de 50 ms, o enumerador do Select é irrelevante. Reescrever LINQ como for só se justifica em código executado milhares de vezes por requisição, com medição que comprove.
  • Código que roda pouco não importa. Um método chamado três vezes por dia pode alocar à vontade. Otimize onde o volume está.
  • Legibilidade tem valor mensurável. Span, stackalloc e ArrayPool aumentam a chance de bug de memória. Use onde o profiler apontou, não por padrão.
A ordem de retorno decrescente

Não alocar 100 MB porque a consulta foi paginada (item 04) vale mais do que qualquer Span. A hierarquia é: não buscar o dado → não materializar o dado → não copiar o dado. Micro-otimização de alocação é o último degrau, não o primeiro.

Como confirmar antes de mexer

terminalbash
# Taxa de alocação e tempo em GC sob carga
dotnet-counters monitor -n MinhaApi --counters System.Runtime

# Quem está ocupando o heap agora
dotnet-gcdump collect -n MinhaApi

E no nível do método, o [MemoryDiagnoser] do BenchmarkDotNet (item 01) mostra bytes alocados por operação — o número que prova se a mudança valeu.

Checklist

  • alloc-rate e time-in-gc medidos antes de otimizar
  • StringBuilder com capacidade estimada em concatenação de laço
  • Interpolação simples fora de laço, sem StringBuilder desnecessário
  • Span / ReadOnlySpan em parsing e fatiamento
  • ArrayPool com Return em finally e uso do comprimento real
  • stackalloc apenas com tamanho constante e pequeno
  • Log com template e argumentos, nunca com interpolação
  • Nenhuma micro-otimização sem número de profiler que a justifique
