Async/await sem estrangular o thread pool

Um .Result perdido num método auxiliar não faz diferença nenhuma no seu desenvolvimento local. Sob 200 requisições simultâneas, ele derruba a aplicação inteira — com a CPU parada em 15%.

ASP.NET Core 10 Leitura: ~7 min Nível: essencial

Por que async existe em um servidor

Em aplicação desktop, async serve para não travar a tela. Em servidor, o objetivo é completamente diferente e muito mais concreto: não gastar thread esperando I/O.

Cada requisição HTTP no ASP.NET Core é atendida por uma thread do pool. Quando o código chama o banco de forma assíncrona, a thread é devolvida ao pool durante a espera e atende outra requisição. Os 80 ms que o banco leva para responder não custam thread nenhuma. Quando o resultado chega, uma thread qualquer do pool retoma o método de onde parou.

É por isso que um servidor .NET atende milhares de requisições simultâneas com poucas dezenas de threads. Todo o modelo depende de uma única condição: nenhuma thread pode ficar parada esperando.

Sync-over-async: quebrando exatamente essa condição

É o padrão de chamar código assíncrono e bloquear até ele terminar:

PedidoService.csC#
// TODAS as variações abaixo são a mesma armadilha
var pedido = _repo.ObterAsync(id).Result;
var pedido = _repo.ObterAsync(id).GetAwaiter().GetResult();
_repo.SalvarAsync(pedido).Wait();
var total = Task.Run(() => CalcularAsync()).Result;

A thread do pool que estava atendendo a requisição fica parada até o I/O terminar. Ela não atende mais ninguém, mas continua ocupando o seu lugar.

Com pouco tráfego, isso é invisível: sobram threads. O problema aparece exatamente quando você menos quer — no pico.

A mecânica do colapso

O thread pool começa com um número de threads próximo à contagem de processadores. Quando todas estão ocupadas e ainda há trabalho na fila, ele injeta threads adicionais — mas de forma deliberadamente lenta, na ordem de uma por segundo. Esse ritmo existe para evitar que uma rajada momentânea crie centenas de threads inúteis.

Só que com sync-over-async o cenário não é uma rajada momentânea. Cada requisição nova consome uma thread e a mantém bloqueada. A fila cresce mais rápido do que uma thread por segundo. E aí acontece o efeito dominó:

  1. As threads disponíveis se esgotam.
  2. Requisições novas ficam na fila, sem sequer começar a ser processadas.
  3. A latência sobe para segundos — o tempo de espera na fila, não de processamento.
  4. Clientes atingem timeout e tentam de novo, dobrando a carga.
  5. A aplicação para de responder. E a CPU segue baixa, porque ninguém está computando nada.
A assinatura do problema

Latência altíssima, CPU baixa, threadpool-queue-length crescendo e threadpool-thread-count subindo devagar e sem parar. Se você vê esse conjunto, procure por .Result, .Wait() e .GetAwaiter().GetResult() no caminho da requisição — a causa está lá.

A correção

Async precisa ser assíncrono do controller até o driver do banco. Uma quebra no meio da corrente já basta para reintroduzir o bloqueio.

PedidosEndpoints.csC#
app.MapGet("/pedidos/{id:int}", async (
    int id,
    IPedidoRepository repo,
    CancellationToken ct) =>
{
    var pedido = await repo.ObterAsync(id, ct);
    return pedido is null ? Results.NotFound() : Results.Ok(pedido);
});
Quando a biblioteca de terceiros só oferece API síncrona

Não embrulhe em Task.Run achando que resolveu — isso apenas move o bloqueio para outra thread do mesmo pool, com o custo extra do agendamento. Chame o método síncrono direto e trate a concorrência com SemaphoreSlim ou uma fila dedicada, para que o consumo de threads seja limitado e previsível em vez de ilimitado.

Sequencial quando deveria ser paralelo

Esse é mais sutil, porque o código está corretamente assíncrono — só é lento à toa. Três chamadas independentes, executadas em fila:

CheckoutService.csC#
// 120 ms + 90 ms + 150 ms = 360 ms
var cliente = await _clientes.ObterAsync(id, ct);
var frete   = await _frete.CalcularAsync(cep, ct);
var cupons  = await _cupons.ListarAsync(id, ct);

Nenhuma delas depende do resultado da anterior. Dispare as três e espere pelo conjunto:

CheckoutService.csC#
// max(120, 90, 150) = 150 ms
var clienteTask = _clientes.ObterAsync(id, ct);
var freteTask   = _frete.CalcularAsync(cep, ct);
var cuponsTask  = _cupons.ListarAsync(id, ct);

await Task.WhenAll(clienteTask, freteTask, cuponsTask);

var cliente = await clienteTask;
var frete   = await freteTask;
var cupons  = await cuponsTask;
Task.WhenAll com o mesmo DbContext: exceção na certa

O DbContext do EF Core não é thread-safe e não suporta duas operações simultâneas. Paralelizar consultas sobre a mesma instância lança InvalidOperationException — e se por acaso passar, corrompe o change tracker. Para paralelizar acesso a banco, use um IDbContextFactory<T> e crie um contexto por tarefa.

Vale a ressalva: Task.WhenAll resolve latência, não capacidade. Se cada chamada já consome um recurso escasso — conexão de banco, cota de API externa —, paralelizar tudo só antecipa a saturação. Para colher resultados conforme chegam, ou limitar quantas rodam ao mesmo tempo, existe Task.WhenEach e Parallel.ForEachAsync com MaxDegreeOfParallelism.

CancellationToken: trabalho que ninguém vai receber

Quando o usuário fecha a aba, cancela o download ou o navegador desiste por timeout, a conexão morre. Sem um token propagado, sua aplicação continua consultando o banco, serializando e escrevendo uma resposta que ninguém está lendo. Em um pico de timeouts, isso é carga inútil justamente no momento em que o sistema mais precisa de fôlego.

RelatorioService.csC#
public async Task<Relatorio> GerarAsync(int id, CancellationToken ct)
{
    var itens = await _db.Itens
        .Where(i => i.PedidoId == id)
        .ToListAsync(ct);   // repasse SEMPRE o token

    foreach (var item in itens)
    {
        ct.ThrowIfCancellationRequested();   // em laço longo de CPU
        Processar(item);
    }

    return new Relatorio(itens);
}

Em Minimal APIs e controllers, basta declarar o parâmetro CancellationToken ct — o framework injeta o HttpContext.RequestAborted automaticamente. O trabalho é só não perder o token pelo caminho.

O cancelamento vira exceção — e isso é esperado

Cancelar lança OperationCanceledException. Não trate como erro de aplicação: não registre no log de erro nem devolva 500. Ela indica que o cliente foi embora, o que é comportamento normal e não incidente.

ValueTask: quando o retorno costuma ser síncrono

Toda Task<T> retornada é um objeto alocado no heap. Se o método quase sempre responde de imediato — cache em memória com taxa alta de acerto, por exemplo —, você está alocando milhões de objetos para representar "já está pronto".

CotacaoCache.csC#
public ValueTask<decimal> ObterAsync(string moeda, CancellationToken ct)
{
    if (_cache.TryGetValue(moeda, out decimal valor))
        return ValueTask.FromResult(valor);   // sem alocação

    return new(BuscarNaApiAsync(moeda, ct));    // caminho raro
}
ValueTask tem regras que Task não tem

Uma ValueTask pode ser aguardada apenas uma vez, não deve ser aguardada por mais de um consumidor e não aceita .Result antes de completar. Guardar uma em campo ou aguardar duas vezes gera comportamento indefinido — não é exceção clara, é bug silencioso. Use no caminho quente comprovado; no resto do código, Task é mais seguro.

Dois detalhes que fecham o assunto

async void

Exceção lançada em um método async void não pode ser capturada por quem chamou — ela sobe direto e derruba o processo. Só existe uma exceção legítima à regra: handlers de evento. Em qualquer outro lugar, use async Task.

ConfigureAwait(false)

Herança da era do ASP.NET clássico, quando existia um SynchronizationContext que causava deadlock. ASP.NET Core não tem SynchronizationContext — em código de aplicação, o ConfigureAwait(false) não muda nada e só polui a leitura. Continua valendo em bibliotecas, que podem ser consumidas por WPF, WinForms ou MAUI, onde o contexto existe.

Como confirmar que sua aplicação sofre disso

terminalbash
# Coloque carga e observe estes dois números
dotnet-counters monitor -n MinhaApi --counters System.Runtime

#   ThreadPool Queue Length    → deve oscilar perto de 0
#   ThreadPool Thread Count    → deve estabilizar, não crescer sem fim

Se a fila cresce e não drena, existe bloqueio no caminho. E o modo mais rápido de encontrar a origem é um analisador estático: os pacotes Microsoft.VisualStudio.Threading.Analyzers e AsyncFixer apontam sync-over-async, async void e token não propagado em tempo de compilação, antes de virar incidente.

Checklist

  • Zero .Result, .Wait() e .GetAwaiter().GetResult() no caminho da requisição
  • Cadeia assíncrona íntegra do endpoint até o acesso a dados
  • CancellationToken declarado no endpoint e repassado a todas as chamadas
  • Chamadas independentes agrupadas com Task.WhenAll
  • Nunca paralelizar operações sobre a mesma instância de DbContext
  • async void apenas em handler de evento
  • ValueTask só onde há evidência de retorno síncrono frequente
  • Analisadores de async ligados no projeto
  • threadpool-queue-length observado sob carga
