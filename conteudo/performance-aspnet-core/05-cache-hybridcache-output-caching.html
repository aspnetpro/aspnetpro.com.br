Cache em camadas: HybridCache e output caching

Cache é a otimização de maior retorno que existe — e a que mais gera incidente quando feita no automático. Aqui estão as duas ferramentas certas do ASP.NET Core 10 e os três erros que transformam cache em problema.

ASP.NET Core 10 Leitura: ~7 min Nível: intermediário

Duas perguntas antes de cachear qualquer coisa

Cache troca atualidade por velocidade. Antes de escrever a primeira linha, responda:

  1. Qual atraso é aceitável? Cotação de moeda tolera 30 segundos. Saldo bancário não tolera nada. Se a resposta for "zero", cache não é o caminho — o caminho é otimizar a consulta.
  2. O dado é o mesmo para todo mundo? Se varia por usuário, tenant ou perfil, isso precisa estar na chave. Esse é o erro que vaza dado de um cliente para outro.

O primeiro erro: cache stampede

O código clássico com IMemoryCache, escrito de forma aparentemente correta:

CatalogoService.csC#
public async Task<Produto[]> ObterDestaquesAsync(CancellationToken ct)
{
    if (_cache.TryGetValue("destaques", out Produto[]? itens))
        return itens!;

    itens = await _repo.BuscarDestaquesAsync(ct);   // 900 ms
    _cache.Set("destaques", itens, TimeSpan.FromMinutes(5));
    return itens;
}

Funciona 99,9% do tempo. O problema é o instante da expiração: no pico, 400 requisições chegam nesse método dentro da mesma janela de 900 ms. Todas veem cache vazio. Todas vão ao banco. O banco, que atendia uma consulta a cada 5 minutos, recebe 400 consultas idênticas simultâneas.

Isso se chama cache stampede — ou efeito manada. E ele tem uma característica cruel: quanto mais popular o dado, pior o estrago. O sistema fica mais frágil justamente onde o cache mais ajudava.

O ciclo que se retroalimenta

As 400 consultas simultâneas deixam o banco lento. Cada uma passa a levar 4 segundos em vez de 900 ms. A janela de vulnerabilidade fica maior, mais requisições entram nela, e o cache pode nunca ser preenchido. É assim que uma expiração de cache vira indisponibilidade total.

HybridCache: a resposta pronta

O HybridCache resolve o stampede por padrão. Para uma mesma chave, ele executa a factory uma única vez e faz as demais chamadas aguardarem o resultado. Como bônus, ele unifica duas camadas: L1 em memória local e L2 distribuída (Redis, SQL Server), com serialização automática entre elas.

Program.csC#
builder.Services.AddHybridCache(options =>
{
    options.MaximumPayloadBytes = 1024 * 1024;   // 1 MB por entrada
    options.MaximumKeyLength = 1024;

    options.DefaultEntryOptions = new HybridCacheEntryOptions
    {
        Expiration = TimeSpan.FromMinutes(5),        // validade total (L1 + L2)
        LocalCacheExpiration = TimeSpan.FromMinutes(1) // validade só na memória local
    };
});

// Opcional: sem L2 registrado, o HybridCache funciona só em memória.
builder.Services.AddStackExchangeRedisCache(o =>
    o.Configuration = builder.Configuration.GetConnectionString("Redis"));
CatalogoService.csC#
public ValueTask<Produto[]> ObterDestaquesAsync(CancellationToken ct) =>
    _cache.GetOrCreateAsync(
        "destaques",
        async token => await _repo.BuscarDestaquesAsync(token),
        cancellationToken: ct);

A diferença entre Expiration e LocalCacheExpiration merece atenção: a segunda é sempre menor. Com L1 de 1 minuto e L2 de 5, cada instância da aplicação consulta o Redis no máximo uma vez por minuto — e o banco, uma vez a cada cinco. Em uma frota de 10 instâncias, isso é a diferença entre 10 consultas ao banco e 1.

Invalidação por tag

Chave por chave, invalidar cache vira um trabalho manual que sempre esquece alguma. Tags agrupam entradas relacionadas:

ProdutoService.csC#
var produto = await _cache.GetOrCreateAsync(
    $"produto:{id}",
    async token => await _repo.ObterAsync(id, token),
    new HybridCacheEntryOptions
    {
        Expiration = TimeSpan.FromMinutes(10),
        Tags = ["produtos", $"produto:{id}"]
    },
    cancellationToken: ct);

// Ao salvar, derruba tudo que depende desse produto
await _cache.RemoveByTagAsync($"produto:{id}", ct);
A chave precisa conter tudo que muda o resultado

Uma chave "pedidos" em um endpoint que devolve os pedidos do usuário logado entrega os pedidos do primeiro usuário a todos os demais. Não é bug de performance — é vazamento de dados. Se o resultado varia por usuário, tenant, idioma ou perfil, tudo isso entra na chave: $"pedidos:{tenantId}:{usuarioId}".

Output caching: cachear a resposta inteira

O HybridCache guarda o dado; sua aplicação ainda executa o pipeline, o binding e a serialização. Quando a resposta inteira pode ser reaproveitada, o output caching devolve os bytes prontos, sem sequer chegar ao seu handler.

Program.csC#
builder.Services.AddOutputCache(options =>
{
    options.AddBasePolicy(b => b.Expire(TimeSpan.FromSeconds(10)));

    options.AddPolicy("catalogo", b => b
        .Expire(TimeSpan.FromMinutes(5))
        .SetVaryByQuery("categoria", "pagina")
        .Tag("catalogo"));
});

var app = builder.Build();

app.UseOutputCache();   // depois de UseCors, antes dos endpoints

app.MapGet("/catalogo", ListarCatalogo)
   .CacheOutput("catalogo");

// Invalidação após uma escrita
app.MapPost("/produtos", async (IOutputCacheStore store, CancellationToken ct) =>
{
    // ... grava o produto ...
    await store.EvictByTagAsync("catalogo", ct);
    return Results.Created();
});
Output caching em endpoint autenticado

Por padrão, o output caching só armazena respostas de requisições GET/HEAD anônimas e com status 200 — justamente para não servir a resposta de um usuário a outro. Se você afrouxar essas regras em uma política customizada, a responsabilidade de variar por identidade passa a ser inteiramente sua. Na dúvida, cacheie apenas conteúdo público.

Output caching não é response caching

Nomes parecidos, comportamentos distintos:

RecursoOnde armazenaQuem controla
Output cachingNo seu servidorVocê — inclusive a invalidação por tag
Response cachingNavegador / proxy / CDNHeaders HTTP; não há como invalidar

Os dois se combinam bem: output caching para tirar carga da sua aplicação, Cache-Control para tirar a requisição da rede. Mas lembre que o conteúdo enviado a um cache que você não controla não pode ser retirado de lá antes de expirar.

O terceiro erro: cache sem limite de memória

IMemoryCache sem limite configurado cresce até a pressão de memória disparar a remoção — o que em contêiner com limite rígido pode significar o processo ser morto antes. Cachear por chave dinâmica (um id de usuário, um termo de busca) sem teto é vazamento de memória com outro nome.

Program.csC#
builder.Services.AddMemoryCache(options =>
{
    options.SizeLimit = 10_000;   // unidade que VOCÊ define
});

// Com SizeLimit definido, toda entrada PRECISA declarar Size.
_cache.Set(chave, valor, new MemoryCacheEntryOptions
{
    Size = 1,
    AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
});
Sliding expiration em dado popular nunca expira

Com SlidingExpiration, cada acesso renova o prazo. Um item consultado a cada segundo com janela de 5 minutos jamais é recarregado — a aplicação serve dado velho indefinidamente. Combine sempre com AbsoluteExpirationRelativeToNow para garantir um teto real.

Meça o que o cache está fazendo

Cache sem métrica é fé. Duas informações bastam para saber se ele está valendo a pena: taxa de acerto e memória ocupada. Uma taxa de acerto baixa significa que você está pagando o custo do cache (memória, serialização, complexidade de invalidação) sem receber o benefício — sinal de chave granular demais ou expiração curta demais.

A escolha resumida

HybridCache para dado reaproveitável entre requisições, com proteção contra stampede embutida. Output caching para resposta pública inteira que se repete. IMemoryCache puro apenas para dado estático de configuração, carregado uma vez na inicialização.

Checklist

  • Atraso aceitável definido explicitamente para cada dado cacheado
  • Chave contendo usuário, tenant e qualquer variável que mude o resultado
  • HybridCache no lugar de TryGetValue + Set manual
  • LocalCacheExpiration menor que Expiration
  • Invalidação por tag conectada às operações de escrita
  • Output caching restrito a conteúdo público
  • SizeLimit configurado se usar IMemoryCache diretamente
  • Nunca SlidingExpiration sem expiração absoluta como teto
  • Taxa de acerto e memória do cache monitoradas
