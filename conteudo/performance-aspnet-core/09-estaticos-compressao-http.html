Estáticos, compressão e o que sai pela rede

Boa parte do tempo que o usuário percebe como "site lento" não é processamento — é transferência. E aqui o ASP.NET Core 10 entrega ganho grande de graça, desde que você use a API certa.

ASP.NET Core 10 Leitura: ~6 min Nível: intermediário

MapStaticAssets: troque uma linha, ganhe três otimizações

O UseStaticFiles faz o mínimo: recebe a requisição, encontra o arquivo no disco e envia os bytes como estão. Toda vez, para todo mundo.

O MapStaticAssets, introduzido no .NET 9, muda o momento em que o trabalho acontece: os arquivos são descobertos e otimizados durante o build.

Program.csC#
var app = builder.Build();

app.MapStaticAssets();   // no lugar de app.UseStaticFiles()

app.MapRazorPages().WithStaticAssets();

O que vem junto:

  • Compressão em tempo de compilação — cada asset é comprimido em Gzip e Brotli e armazenado assim. Em runtime o servidor apenas escolhe a versão que o cliente aceita, sem gastar CPU comprimindo a cada requisição. E como o custo é pago no build, dá para usar o nível máximo de compressão, que seria proibitivo em tempo real.
  • Fingerprinting por conteúdo — o nome do arquivo passa a incluir um hash SHA-256 do conteúdo. Se o conteúdo muda, o nome muda; se não muda, o nome permanece.
  • Cache imutável — como o nome identifica o conteúdo, o servidor pode enviar Cache-Control: immutable com validade longa. O navegador nunca revalida — e, no deploy seguinte, baixa o arquivo novo porque a URL é outra.
O fim do "limpa o cache do navegador"

O ciclo clássico — usuário com CSS velho, suporte pedindo Ctrl+F5, alguém colando ?v=2 na mão — desaparece. Em Razor, referencie com <link href="@Assets["css/site.css"]" rel="stylesheet" /> e o nome com hash é resolvido automaticamente.

Só vale para o que existe no build

MapStaticAssets cobre os assets conhecidos em tempo de compilação. Arquivos enviados por usuários ou gerados em runtime continuam precisando de UseStaticFiles — e os dois podem coexistir no mesmo pipeline.

Compressão de conteúdo dinâmico

Resposta de API é gerada na hora, então não dá para comprimir no build. Aqui entra o middleware de compressão:

Program.csC#
builder.Services.AddResponseCompression(options =>
{
    options.EnableForHttps = true;   // leia o alerta abaixo antes
    options.Providers.Add<BrotliCompressionProvider>();
    options.Providers.Add<GzipCompressionProvider>();
});

builder.Services.Configure<BrotliCompressionProviderOptions>(o =>
    o.Level = CompressionLevel.Fastest);   // não use SmallestSize em runtime

var app = builder.Build();

app.UseResponseCompression();   // bem no início do pipeline
Por que EnableForHttps é falso por padrão

Não é conservadorismo — é o ataque BREACH. Comprimir dados dentro de TLS faz o tamanho da resposta vazar informação sobre o conteúdo: se o atacante consegue injetar texto no corpo (um parâmetro refletido, por exemplo) e observar o tamanho, ele descobre por tentativa e erro se o texto injetado coincide com um segredo presente na mesma resposta — token antiforgery, chave de sessão. Só ligue EnableForHttps se a resposta comprimida não misturar segredos com entrada controlada pelo usuário. Em API pública sem token no corpo, é seguro. Em página HTML com token antiforgery, não é.

Duas notas práticas. Primeira: não comprima o que já está comprimido — JPEG, PNG, WebP, MP4, ZIP e PDF só ganham CPU gasto e alguns bytes a mais. Segunda: se houver Nginx, IIS, CDN ou Cloudflare na frente, provavelmente a compressão já acontece lá, com custo fora do seu processo. Comprimir duas vezes é desperdício puro.

ConteúdoComprimir?
JSON, HTML, CSS, JS, SVG, XMLSim — reduções de 60% a 85%
Imagens, vídeo, áudio, ZIP, PDFNão — já comprimidos
Resposta pequena (menos de ~1 KB)Não — o overhead supera o ganho
Streaming / IAsyncEnumerableCom cuidado: pode atrasar o primeiro byte

A requisição mais rápida é a que não acontece

Compressão reduz bytes. Cache HTTP elimina a transferência inteira. Duas ferramentas, aplicadas a situações diferentes:

CenárioHeaderResultado
Asset com hash no nomeCache-Control: max-age=31536000, immutableNenhuma requisição
Conteúdo que muda poucoETag + Cache-Control: no-cache304, sem corpo
Dado por usuárioCache-Control: private, no-storeNunca cacheado

O ETag é um identificador da versão do recurso. O navegador o reenvia em If-None-Match, e o servidor responde 304 Not Modified — sem corpo — quando nada mudou. A transferência do conteúdo desaparece; sobra só o custo do handshake:

CatalogoEndpoints.csC#
app.MapGet("/catalogo", async (HttpContext ctx, ICatalogo catalogo, CancellationToken ct) =>
{
    var versao = await catalogo.ObterVersaoAsync(ct);
    var etag = new EntityTagHeaderValue($"\"{versao}\"");

    if (ctx.Request.Headers.IfNoneMatch.Contains(etag.ToString()))
        return Results.StatusCode(StatusCodes.Status304NotModified);

    ctx.Response.Headers.ETag = etag.ToString();
    return Results.Ok(await catalogo.ListarAsync(ct));
});
Cuidado com dado privado em cache compartilhado

Cache-Control: public autoriza qualquer intermediário — proxy corporativo, CDN — a guardar e reentregar a resposta. Em conteúdo por usuário, isso serve os dados de um cliente a outro. Resposta autenticada leva private; dado sensível leva no-store.

HTTP/2 e HTTP/3

O protocolo também é performance. HTTP/2 multiplexa várias requisições na mesma conexão e comprime headers; HTTP/3, sobre QUIC, elimina o head-of-line blocking da camada TCP — o que mais se nota em rede móvel e com perda de pacote.

appsettings.jsonJSON
{
  "Kestrel": {
    "EndpointDefaults": {
      "Protocols": "Http1AndHttp2AndHttp3"
    }
  }
}

Se houver proxy reverso ou CDN na frente, é lá que essa configuração precisa existir — o cliente conversa com o proxy, não com o seu Kestrel. E vale lembrar que HTTP/2 e HTTP/3 exigem HTTPS na prática.

O ganho de maior alavancagem deste item

Colocar os estáticos atrás de uma CDN. A requisição nem chega ao seu servidor, e o arquivo sai de um ponto geograficamente próximo do usuário. Com fingerprinting já ativo, a invalidação de cache deixa de ser um problema — cada deploy publica URLs novas.

Checklist

  • MapStaticAssets no lugar de UseStaticFiles para assets do build
  • Referências usando @Assets[...] para aproveitar o fingerprint
  • Compressão de resposta ativa para JSON, HTML, CSS e JS
  • EnableForHttps avaliado contra o risco BREACH
  • Nível de compressão em Fastest quando feita em runtime
  • Conteúdo já comprimido fora da lista de tipos
  • Compressão não duplicada entre aplicação e proxy/CDN
  • ETag em endpoints de leitura que mudam pouco
  • Cache-Control com private ou no-store em resposta autenticada
  • HTTP/2 e HTTP/3 habilitados na borda
