Meça antes de otimizar (e olhe o percentil, não a média)

A maior parte do esforço de performance é gasta no lugar errado porque ninguém mediu. Este item é sobre descobrir onde está o gargalo em minutos — e sobre a métrica que faz um sistema lento parecer saudável no dashboard.

ASP.NET Core 10 Leitura: ~6 min Nível: essencial

A história que se repete

A API está lenta. O time se reúne, alguém aponta o EF Core, e duas semanas depois metade das consultas foi reescrita em Dapper. O resultado: nada mudou. O gargalo era uma chamada HTTP a um serviço externo, feita com .Result, que travava threads do pool e fazia todo o resto da aplicação esperar.

Isso não é falta de competência técnica — é falta de medição. Performance é a área em que a intuição mais erra, porque o custo real está distribuído entre camadas que você não vê no código: I/O, garbage collector, contenção de lock, latência de rede, pool de conexões.

A regra que não tem exceção

Otimização sem medição é reescrita com sorte. Se você não consegue dizer qual número vai melhorar e quanto, você ainda não sabe o que está fazendo.

A média mente. Sempre.

Suponha 1.000 requisições: 950 respondem em 20 ms e 50 respondem em 3 segundos. A média dá 169 ms — um número que passa em qualquer SLA e não gera alerta nenhum. Mas 5% dos seus usuários esperaram 3 segundos, e num carrinho de compras isso é abandono.

Por isso a unidade de medida em produção é o percentil:

MétricaO que respondePara que serve
p50 (mediana)Como é o dia normal do usuário típicoPercepção geral de velocidade
p95Como é o dia ruim de 1 em cada 20É a meta que a maioria dos times persegue
p99Onde o sistema começa a quebrarExpõe GC, timeout, contenção e cache miss

Uma observação que muda a leitura: numa tela que faz 10 chamadas de API em paralelo, a experiência do usuário é definida pela mais lenta das 10. Ou seja, o p99 de uma requisição vira o p90 da página. Cauda longa importa muito mais do que parece.

Primeiro diagnóstico: dotnet-counters

Antes de abrir profiler, capture os contadores. É a ferramenta mais barata que existe, roda em processo vivo e não exige alterar uma linha do seu código.

terminalbash
# Instalação (uma vez)
dotnet tool install --global dotnet-counters

# Monitorar a aplicação em execução
dotnet-counters monitor -n MinhaApi \
  --counters System.Runtime,Microsoft.AspNetCore.Hosting

Os contadores que respondem quase todas as perguntas iniciais:

ContadorSinal de alertaSuspeito
threadpool-queue-lengthCresce e não volta a zeroSync-over-async (item 02)
threadpool-thread-countSobe devagar e sem pararThread pool starvation
alloc-rateCentenas de MB/sAlocação em caminho quente (item 08)
gc-heap-size / gen-2-gc-countHeap cresce sem estabilizarVazamento, cache sem limite (item 05)
time-in-gcAcima de ~10%Pressão de memória
current-requestsAlto com CPU baixaBloqueio em I/O, não falta de CPU
O diagnóstico mais revelador do .NET

Latência alta com CPU baixa praticamente nunca é problema de algoritmo. É bloqueio: thread pool estrangulado, pool de conexões esgotado ou espera por serviço externo. Antes de otimizar qualquer for, confira a CPU.

Segundo passo: onde o tempo é gasto

Com o suspeito identificado, o dotnet-trace mostra a distribuição real do tempo, e o dotnet-gcdump mostra o que está ocupando a memória.

terminalbash
# Amostragem de CPU — abre no Visual Studio ou no PerfView
dotnet-trace collect -n MinhaApi --profile cpu-sampling

# Foto do heap gerenciado (quem está segurando memória)
dotnet-gcdump collect -n MinhaApi

# Travou? Dump completo para inspeção posterior
dotnet-dump collect -n MinhaApi

Esses três comandos funcionam também dentro de contêiner, desde que as ferramentas estejam disponíveis na imagem e o processo seja alcançável. Vale deixar isso preparado antes do incidente — na hora do fogo, ninguém instala tooling com calma.

Terceiro passo: BenchmarkDotNet, no lugar certo

Quando o gargalo já está isolado num método, aí sim vale medir com precisão. O Stopwatch no meio do código não serve: ele não aquece o JIT, não isola o GC e não repete o suficiente para ter significância estatística.

Benchmarks/SerializacaoBenchmark.csC#
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]
public class SerializacaoBenchmark
{
    private readonly Pedido[] _pedidos = Fake.Pedidos(500);

    [Benchmark(Baseline = true)]
    public string ComReflection() =>
        JsonSerializer.Serialize(_pedidos);

    [Benchmark]
    public string ComSourceGenerator() =>
        JsonSerializer.Serialize(_pedidos, AppJsonContext.Default.PedidoArray);
}

// Program.cs do projeto de benchmark
BenchmarkRunner.Run<SerializacaoBenchmark>();

O [MemoryDiagnoser] é o atributo que mais entrega valor: além do tempo, ele mostra bytes alocados por operação e quantas coletas de cada geração aconteceram. Em servidor, reduzir alocação costuma valer mais que reduzir nanossegundos, porque alocação vira pausa de GC lá na frente.

Benchmark em Debug não mede nada

O BenchmarkDotNet recusa rodar em Debug justamente por isso. Sem otimização do compilador e com tiered compilation em estado diferente, os números não têm relação com produção. O mesmo vale para medir com o depurador anexado.

Teste de carga: o único jeito de ver o comportamento real

Microbenchmark mede um método isolado. Ele não enxerga contenção de pool, fila de thread, cache miss ou saturação de conexão — que é onde as aplicações web realmente quebram. Para isso é preciso carga concorrente.

terminalbash
# bombardier: 200 conexões simultâneas por 30 segundos
bombardier -c 200 -d 30s -l https://localhost:5001/api/pedidos

# k6, quando você precisa de rampa e critério de aprovação
k6 run --vus 200 --duration 30s carga.js

O que observar durante o teste não é só o número final da ferramenta — é o dotnet-counters rodando em paralelo. É a combinação dos dois que conta a história: throughput estagnou enquanto a fila do thread pool subia? A resposta está no item 02.

Ambiente de teste que engana

Carga contra localhost, com banco vazio e latência de rede zero, mede o cenário mais favorável possível. Volume de dados realista e latência de rede realista mudam completamente qual é o gargalo — normalmente para pior.

Defina a meta antes de começar

"Deixar mais rápido" não é meta, porque não tem critério de parada. Escreva o alvo em uma frase mensurável antes da primeira linha de otimização:

  • p95 do GET /api/pedidos abaixo de 200 ms com 200 usuários simultâneos.
  • Consumo de memória estável abaixo de 500 MB após 1 hora de carga.

Com uma meta assim você sabe quando parar — e evita o outro extremo do problema, que é passar três semanas ganhando microssegundos num endpoint chamado quatro vezes por dia.

Checklist

  • Meta escrita em número, com percentil e nível de concorrência
  • Baseline capturado antes de qualquer mudança
  • p95 e p99 monitorados, não apenas a média
  • dotnet-counters rodado sobre a aplicação sob carga
  • Relação CPU × latência conferida antes de suspeitar de algoritmo
  • BenchmarkDotNet em Release, com [MemoryDiagnoser]
  • Teste de carga com volume de dados e latência realistas
  • Medição repetida depois da mudança, para provar o ganho
