Erros, logs e dependências vulneráveis

Os nove itens anteriores tratam do que o atacante tenta fazer com a sua aplicação. Este trata do que a sua aplicação conta sobre si mesma sem ser perguntada — na página de erro, no arquivo de log e na lista de pacotes que ela carrega.

ASP.NET Core 10 Leitura: ~13 min Nível: essencial

Reconhecimento: a fase que antecede o ataque

Nenhum ataque sério começa pela exploração. Começa por entender o que está do outro lado: qual framework, qual versão, qual ORM, quais bibliotecas, como o servidor se comporta quando alguma coisa quebra. Quanto mais barato for esse reconhecimento, mais viável fica o resto.

Os três itens deste capítulo são justamente as fontes gratuitas dessa informação:

  • a página de erro, que descreve sua arquitetura por dentro;
  • o log, que acumula dado sensível num lugar com menos controle de acesso do que o banco;
  • a lista de dependências, que diz exatamente qual CVE público se aplica a você.

Nenhum deles é uma falha de código. Os três são configuração — e é por isso que passam batido em code review.

O stack trace é a planta baixa do seu sistema

A página de exceção do ambiente de desenvolvimento é excelente: mostra o trecho de código que falhou, a cadeia de exceções internas, os headers da requisição, as variáveis de ambiente do processo. Em produção, cada um desses blocos é uma entrega:

O que apareceO que o atacante conclui
Namespaces e nomes de classeComo o sistema é organizado, onde estão as camadas que interessam
Caminho absoluto dos arquivosEstrutura do build, usuário do agente, às vezes o nome interno do projeto
Versão do runtime e dos pacotesQuais CVEs conhecidos se aplicam — sem precisar testar nada
Mensagem de SqlExceptionNome do servidor, do banco, da tabela e da coluna
SQL gerado pelo EF CoreO schema, de graça (e o item 04 explica o que fazer com ele)
Variáveis de ambienteConnection strings, chaves de API, segredos do item 03

Não é um vazamento hipotético: em muitos incidentes o atacante descobre a versão vulnerável de um pacote justamente forçando um erro — um id com letra onde se espera número costuma bastar.

Como isso chega em produção

Quase sempre por uma destas três portas:

Program.csC#
// 1. chamada incondicional — "só pra debugar aquele bug em homologação"
app.UseDeveloperExceptionPage();

// 2. endpoint de migrations exposto fora de dev
app.UseMigrationsEndPoint();

// 3. erro detalhado ligado no Blazor Server
builder.Services.AddRazorComponents()
    .AddInteractiveServerComponents(o => o.DetailedErrors = true);

Existe uma quarta, mais silenciosa: a variável de ambiente. Quando ASPNETCORE_ENVIRONMENT não está definida, o ASP.NET Core assume Production — o padrão é seguro. O problema é quando alguém define Development no App Service, no Dockerfile ou no manifesto do Kubernetes para investigar um incidente, e a linha nunca é removida. Nada no código muda, o comportamento inteiro muda.

Você não precisa da chamada explícita

Desde o modelo de hosting mínimo, o WebApplicationBuilder já adiciona a página de exceção de desenvolvimento automaticamente quando o ambiente é Development. Ou seja: a linha UseDeveloperExceptionPage() escrita à mão é, na melhor das hipóteses, redundante — e na pior, é ela que está ligando o recurso em produção. Se encontrar uma, o caminho é remover, não envolver em um if.

A forma correta

Uma resposta de erro em produção precisa de duas coisas: ser genérica para quem chamou e ser rastreável para você. ProblemDetails (RFC 9457) resolve o formato, e o identificador de correlação resolve o suporte.

Program.csC#
builder.Services.AddProblemDetails();

var app = builder.Build();

if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler();   // sem argumento: usa o ProblemDetails
    app.UseHsts();               // item 01
}

app.UseStatusCodePages();       // 404 e afins também com corpo padronizado

Repare que a condição é negativa: o que se protege é o caminho de produção. Escrever if (app.Environment.IsDevelopment()) e deixar o else vazio é como a proteção some sem ninguém notar.

Para logar e correlacionar em um só lugar, o IExceptionHandler é o gancho recomendado:

GlobalExceptionHandler.csC#
public sealed class GlobalExceptionHandler(ILogger<GlobalExceptionHandler> logger)
    : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext ctx, Exception ex, CancellationToken ct)
    {
        var traceId = Activity.Current?.Id ?? ctx.TraceIdentifier;

        // detalhe completo vai para o log — nunca para a resposta
        logger.LogError(ex, "Falha não tratada em {Path} ({TraceId})",
            ctx.Request.Path, traceId);

        ctx.Response.StatusCode = StatusCodes.Status500InternalServerError;
        await ctx.Response.WriteAsJsonAsync(new ProblemDetails
        {
            Title = "Não foi possível concluir a operação.",
            Status = StatusCodes.Status500InternalServerError,
            Extensions = { ["traceId"] = traceId }
        }, ct);

        return true;
    }
}
Program.csC#
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
builder.Services.AddProblemDetails();

O traceId é o que torna a resposta genérica viável na prática. O usuário abre um chamado com um código curto, você acha a exceção inteira no log — ninguém precisa do stack trace na tela para dar suporte.

Devolver ex.Message é o meio-termo que não existe

Parece inofensivo: "não mando o stack trace, só a mensagem". Só que a mensagem é escrita pela biblioteca que falhou, e ela não sabe que vai virar resposta HTTP. SqlException nomeia servidor, banco e coluna. FileNotFoundException entrega o caminho absoluto. Exceção de deserialização descreve o formato esperado do seu contrato interno. Ou o texto foi escrito por você para aquele usuário, ou ele não sai da aplicação.

Log: dado sensível num lugar de baixo controle

O banco de dados tem controle de acesso, criptografia em repouso, auditoria e alguém responsável. O log costuma ter: um índice pesquisável, retenção longa e acesso liberado para o time inteiro — às vezes para um SaaS de observabilidade fora do país. Todo dado que sai do banco e cai no log muda de regime de proteção sem passar por decisão nenhuma.

É por isso que log é um assunto de LGPD, não só de segurança: registrar CPF, e-mail ou endereço em log é tratamento de dado pessoal, sujeito a finalidade, minimização e prazo de retenção. Um log de acesso guardado "para sempre por garantia" é uma base de dados pessoais informal que ninguém mapeou.

Nunca vai para o logPor quê
Senha, mesmo em tentativa falhaErro de digitação de senha é quase sempre a senha certa de outro sistema
Token, JWT, cookie de autenticação, header AuthorizationVale como credencial até expirar — e o log dura mais
Corpo bruto de requisição de login, pagamento ou cadastroCarrega senha e dado de cartão sem que você perceba
Cartão, CVV, chave PIXRegra de PCI-DSS, além do óbvio
CPF, RG, dado de saúde, biometriaDado pessoal — e parte dele é sensível pela LGPD
Connection string, chave de APIÉ o item 03 vazando pela porta dos fundos

Os três vazamentos mais comuns

O primeiro é o log de diagnóstico que ninguém revisou:

AuthController.csC#
// o objeto inteiro, incluindo a senha em texto puro
_logger.LogInformation("Tentativa de login: {@Request}", request);

// e-mail vira campo indexado e pesquisável para sempre
_logger.LogWarning("Senha inválida para {Email}", request.Email);

A correção não é apagar o log — é logar o suficiente para investigar e nada além. Um identificador interno resolve; o e-mail, não:

AuthController.csC#
_logger.LogWarning("Falha de autenticação para {UserId} de {IP}",
    user?.Id, HttpContext.Connection.RemoteIpAddress);

O segundo é do EF Core, e é sério porque o desenvolvedor liga de propósito — para ver os parâmetros da query — e esquece ligado:

Program.csC#
builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(cs)
     .EnableSensitiveDataLogging()      // valores reais no log
     .EnableDetailedErrors());

Com isso, cada consulta registra os valores dos parâmetros: o CPF pesquisado, o e-mail filtrado, o hash comparado. Se precisar do recurso, prenda-o ao ambiente:

Program.csC#
builder.Services.AddDbContext<AppDbContext>(o =>
{
    o.UseSqlServer(cs);
    if (builder.Environment.IsDevelopment())
    {
        o.EnableSensitiveDataLogging();
        o.EnableDetailedErrors();
    }
});

O terceiro é a injeção de log. Quando você concatena entrada do usuário em uma string de mensagem, um \n no meio do texto cria uma linha nova no arquivo — e o atacante escreve o que quiser no seu registro de auditoria, inclusive uma linha falsa de "login bem-sucedido do administrador":

interpolação em logC#
_logger.LogInformation($"Busca por: {termo}");   // termo controla o arquivo

O logging estruturado — template fixo, valores como parâmetro — resolve porque o valor vira campo de um objeto, não texto solto. É o mesmo raciocínio do item 04: separar o comando dos dados. E ainda vale o cuidado de sempre: se o destino é um dashboard HTML, o item 05 continua se aplicando na hora de exibir.

Quem enxerga o log e por quanto tempo

Duas perguntas que valem mais que qualquer configuração. Quem tem acesso? Se o time inteiro consulta o painel de observabilidade, o log é um banco de produção com permissão de leitura ampla. Por quanto tempo fica? Retenção indefinida transforma um log de baixo risco hoje em um vazamento grande daqui a três anos. Para quem precisa manter o campo e proteger o conteúdo, o .NET oferece o pacote Microsoft.Extensions.Compliance.Redaction, que aplica ofuscação por classificação de dado no momento em que o log é escrito.

A aplicação que se apresenta nos headers

Por padrão, o Kestrel envia Server: Kestrel em toda resposta. Hospedado no IIS, aparecem também X-Powered-By e, em configurações antigas, X-AspNet-Version. Nada disso é uma vulnerabilidade — é sinalização. Serve para o scanner automatizado decidir que vale a pena testar o seu host com o arsenal de .NET em vez de seguir adiante.

Program.csC#
builder.WebHost.ConfigureKestrel(o => o.AddServerHeader = false);

No IIS, o X-Powered-By sai pelo web.config, em <httpProtocol><customHeaders><remove name="X-Powered-By" />. Se houver CDN ou gateway na frente, o mais prático é remover na borda, de uma vez para todos os serviços.

Isso é redução de ruído, não defesa

Esconder a versão não corrige nada — se o pacote é vulnerável, ele continua vulnerável. O ganho é real, mas modesto: você deixa de aparecer na varredura em massa que filtra alvos por header. Trate como higiene de dois minutos, jamais como substituto de atualizar dependência.

Dependências: a maior parte do seu código não é sua

Uma API .NET típica tem algumas dezenas de milhares de linhas escritas pelo time e alguns milhões vindas de pacotes. A superfície de ataque segue a mesma proporção. E o detalhe que mais pega: a maior parte das dependências você nunca escolheu — vieram como transitivas, arrastadas por outro pacote.

O ponto que torna isso urgente é a assimetria de informação. Uma vulnerabilidade em pacote público vem com CVE, versão afetada e, muitas vezes, prova de conceito publicada. Do lado do atacante, é uma consulta. Do seu lado, se ninguém verifica, é um ponto cego permanente.

O NuGet audit já vem ligado — só não vem sendo lido

Desde o .NET 8, todo restore consulta a base de vulnerabilidades do NuGet e emite avisos. Em projetos que miram .NET 10, o modo padrão passou a ser all, ou seja, transitivas incluídas. Os códigos são graduados por severidade:

AvisoSeveridadePostura sugerida
NU1904CríticaQuebrar o build
NU1903AltaQuebrar o build
NU1902ModeradaAvisar e tratar no ciclo
NU1901BaixaAvisar

Aviso que não quebra nada vira ruído em log de build. Torne o que é grave impossível de ignorar, no Directory.Build.props da raiz, para valer no repositório inteiro:

Directory.Build.propsXML
<Project>
  <PropertyGroup>
    <NuGetAudit>true</NuGetAudit>
    <!-- padrão no .NET 10; explícito para não depender do TFM -->
    <NuGetAuditMode>all</NuGetAuditMode>
    <NuGetAuditLevel>low</NuGetAuditLevel>
    <!-- alta e crítica derrubam o build -->
    <WarningsAsErrors>$(WarningsAsErrors);NU1903;NU1904</WarningsAsErrors>
  </PropertyGroup>
</Project>

A varredura sob demanda complementa, e é o que você roda hoje mesmo:

terminalbash
# o comando que importa: transitivas incluídas
dotnet list package --vulnerable --include-transitive

# pacotes abandonados pelo autor — sem correção futura
dotnet list package --deprecated

# quem, afinal, trouxe esse pacote para o projeto?
dotnet nuget why ./MinhaApi.sln System.Text.Json
A transitiva que você não pode atualizar

O relatório aponta uma versão vulnerável de um pacote que não está no seu .csproj. Atualizar o pacote-pai é o certo — quando existe versão nova. Quando não existe, a saída é declarar uma PackageReference direta na versão corrigida, forçando a resolução para cima. Funciona, mas é dívida: escreva um comentário dizendo por que aquela referência existe, ou daqui a seis meses alguém a remove por parecer sobrando.

Fazer isso sozinho não escala

Rodar o comando manualmente cobre o dia em que você lembrou. O que muda o jogo é a automação:

  • No pipeline, um passo dedicado de auditoria — separado do build, com falha explícita, para que a causa apareça no relatório em vez de se perder entre avisos de compilação.
  • Dependabot ou Renovate, que abrem PR de atualização sozinhos. O ganho maior não é o alerta: é manter a distância entre a sua versão e a mais recente pequena o suficiente para que atualizar de emergência seja viável. Quem está quatro versões maiores atrás não consegue corrigir um zero-day em um dia.
  • Lock file (RestorePackagesWithLockFile) com --locked-mode no CI, para que o build seja reproduzível e nenhuma versão entre sem passar por um commit revisado.
  • Central Package Management (Directory.Packages.props), que concentra as versões em um arquivo só — atualizar deixa de ser uma caçada por vinte .csproj.
Vulnerável não é o mesmo que explorável

Um CVE só te afeta se o caminho de código vulnerável for realmente alcançado pela sua aplicação — e é comum que não seja. Isso não é motivo para ignorar o aviso; é motivo para priorizar com critério. O que decide a urgência é a exposição: um pacote de parsing usado no endpoint público que recebe upload é outra conversa em relação a uma dependência de uma ferramenta de build. Trate crítico e alto como incidente; o resto, no ciclo normal — mas sempre com prazo, nunca como "depois a gente vê".

Como verificar

Comece pelas configurações que abrem o vazamento:

terminalbash
# página de erro de dev e endpoints de diagnóstico fora de dev
grep -rn "UseDeveloperExceptionPage\|UseMigrationsEndPoint\|DetailedErrors" --include="*.cs" .

# o tratamento global existe mesmo?
grep -rn "UseExceptionHandler\|AddProblemDetails\|IExceptionHandler" --include="*.cs" .

# detalhe de exceção virando resposta HTTP
grep -rn "ex.Message\|ex.ToString()\|StackTrace" --include="*.cs" .

# log sensível do EF Core
grep -rn "EnableSensitiveDataLogging" --include="*.cs" .

# ambiente forçado em Dockerfile, YAML e manifestos
grep -rn "ASPNETCORE_ENVIRONMENT" --include="*.yml" --include="*.yaml" --include="Dockerfile*" .

Depois force um erro em um ambiente que espelha produção e olhe o que voltou:

PowerShellPOWERSHELL
# um id inválido costuma bastar para provocar a exceção
$r = Invoke-WebRequest -Uri https://localhost:5001/api/pedidos/abc `
        -SkipHttpErrorCheck

$r.Headers["Server"]           # esperado: vazio
$r.Content                      # esperado: ProblemDetails com traceId

A resposta não pode conter nome de classe, caminho de arquivo, nome de tabela nem a palavra Exception. Deve conter o traceId — e esse mesmo identificador precisa aparecer no seu log, com a exceção completa. Se estiver na resposta e não no log, você piorou os dois lados: escondeu do usuário e perdeu para você.

Por fim, o inventário:

terminalbash
dotnet restore --force-evaluate
dotnet list package --vulnerable --include-transitive
dotnet list package --deprecated

Um resultado limpo hoje não vale nada amanhã: a base de vulnerabilidades muda sem que uma linha do seu código mude. Por isso o comando pertence ao pipeline, não à sua memória.

Checklist

  • Nenhum UseDeveloperExceptionPage() escrito à mão no código
  • UseMigrationsEndPoint e afins restritos ao ambiente de desenvolvimento
  • AddProblemDetails registrado e UseExceptionHandler ativo fora de dev
  • Condição de ambiente escrita na forma negativa — if (!IsDevelopment())
  • Resposta de erro genérica, sem ex.Message, stack trace ou nome de tipo
  • traceId devolvido na resposta e presente no log correspondente
  • ASPNETCORE_ENVIRONMENT conferido em Dockerfile, pipeline e configuração do host
  • Nenhuma senha, token, cookie ou header Authorization em log
  • Log identifica o usuário por id interno, não por e-mail ou CPF
  • Logging estruturado com template fixo — sem interpolação de entrada do usuário
  • EnableSensitiveDataLogging ausente ou preso a IsDevelopment()
  • Retenção de log definida, com prazo e responsável — não indefinida
  • AddServerHeader = false e X-Powered-By removido
  • NuGetAudit ligado, NuGetAuditMode em all, NU1903/NU1904 como erro
  • dotnet list package --vulnerable --include-transitive rodando no pipeline
  • Dependabot ou Renovate ativo no repositório
  • Pacotes deprecados mapeados e com plano de substituição

Fechando o guia

Se houver uma linha para levar dos dez itens, é esta: quase nenhuma delas era uma falha de código. Foram um lockoutOnFailure: false, um KnownProxies.Clear(), um AllowAnyOrigin, uma variável de ambiente errada — decisões de configuração que passam em todo teste, não aparecem em nenhum code review e continuam ali por anos.

Por isso o formato de cada item terminou em duas coisas práticas: um comando de verificação e um checklist. Segurança em aplicação real não vem de saber a teoria; vem de conferir, com alguma regularidade, coisas que já deveriam estar certas. Rode os greps deste guia no seu projeto ainda esta semana. A parte incômoda é que você vai achar alguma coisa — e a parte boa é exatamente a mesma.
