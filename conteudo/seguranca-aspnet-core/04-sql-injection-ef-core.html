SQL Injection: o EF Core não te salva sozinho

Usar ORM virou sinônimo de "estou protegido". Mas o EF Core só protege o que passa pelo LINQ — e basta uma string interpolada no método errado para abrir o banco inteiro, sem nenhum aviso do compilador.

ASP.NET Core 10 · EF Core 10 Leitura: ~9 min Nível: essencial

Por que o LINQ é seguro

Quando você escreve uma consulta em LINQ, o EF Core não monta uma string. Ele traduz a árvore de expressão para SQL e transforma todo valor variável em parâmetro, sem exceção:

ClientesService.csC#
var clientes = await _db.Clientes
    .Where(c => c.Nome == nome)
    .ToListAsync();
SQL geradoSQL
SELECT c.Id, c.Nome, c.Email
FROM Clientes AS c
WHERE c.Nome = @__nome_0

O valor de nome viaja separado do comando, num parâmetro. O banco recebe a instrução já compilada e o dado como dado — não como texto a ser interpretado. Não existe payload capaz de virar SQL aqui, porque o valor nunca chega a ser SQL.

É por isso que a esmagadora maioria do código EF é segura por construção. O problema começa exatamente onde o LINQ não alcança.

A armadilha: interpolação dentro de FromSqlRaw

Toda aplicação tem aquela consulta que o LINQ não expressa bem — um relatório pesado, uma função específica do banco, uma query que o time otimizou na mão. Aí alguém alcança o FromSqlRaw:

RelatoriosService.cs — SQL Injection abertaC#
var clientes = await _db.Clientes
    .FromSqlRaw($"SELECT * FROM Clientes WHERE Nome = '{nome}'")
    .ToListAsync();

Esse código compila sem aviso, funciona nos testes e passa no code review — porque parece com a versão segura. Mas repare no que acontece na ordem de execução: a interpolação é resolvida pelo C#, antes da chamada. O FromSqlRaw recebe um string já concatenado. Do ponto de vista do EF, aquilo é uma consulta escrita à mão — e ele executa exatamente o que recebeu.

Com nome = "Maria", roda o esperado. Agora com nome valendo ' OR 1=1 --:

SQL que chega no bancoSQL
SELECT * FROM Clientes WHERE Nome = '' OR 1=1 --'

A aspa fecha o literal, o OR 1=1 torna a condição sempre verdadeira e o -- comenta o resto. A base de clientes inteira volta na resposta. E isso é só o aquecimento — o passo seguinte do atacante é um UNION SELECT para ler outra tabela:

payload de extraçãoSQL
-- nome = ' UNION SELECT Id, Email, SenhaHash FROM Usuarios --

SELECT * FROM Clientes WHERE Nome = ''
UNION SELECT Id, Email, SenhaHash FROM Usuarios --'
A regra

Todo método com Raw no nome aceita string. Se você escrever uma string interpolada ali, o compilador converte silenciosamente e a proteção evapora. O sufixo Raw é o aviso: você assumiu a responsabilidade pela parametrização.

A correção: FromSql com FormattableString

A diferença entre a versão vulnerável e a segura é literalmente o tipo do parâmetro do método. O FromSql recebe um FormattableString — ou seja, ele acessa o template e os valores separadamente, e converte cada buraco da interpolação em um DbParameter:

RelatoriosService.csC#
var clientes = await _db.Clientes
    .FromSql($"SELECT * FROM Clientes WHERE Nome = {nome}")
    .ToListAsync();

// Vira: SELECT * FROM Clientes WHERE Nome = @p0

Visualmente quase idêntico ao código vulnerável — e completamente diferente na execução. Note também que não há aspas em volta do {nome}. Colocar aspas ali é um erro comum: o valor vira parte de um literal de string em vez de parâmetro.

MétodoRecebeParametriza?
FromSqlFormattableStringSim — use este
FromSqlInterpolatedFormattableStringSim — nome antigo, mesmo comportamento
FromSqlRawstring + paramsSó o que você passar como parâmetro
ExecuteSql / AsyncFormattableStringSim — para UPDATE, DELETE, procs
ExecuteSqlRawstring + paramsMesmo risco do FromSqlRaw
Database.SqlQuery<T>FormattableStringSim — para escalares e tipos não-entidade
Database.SqlQueryRaw<T>string + paramsMesmo risco

A regra prática é curta: prefira sempre a versão sem Raw. Só recorra à variante crua quando alguma parte da consulta precisar ser montada dinamicamente — e, nesse caso, os valores continuam indo por parâmetro:

quando o FromSqlRaw é legítimoC#
// A coluna vem de uma allowlist (próxima seção). O VALOR vai por parâmetro.
var filtro = new SqlParameter("filtro", valorDoUsuario);

var clientes = await _db.Clientes
    .FromSqlRaw($"SELECT * FROM Clientes WHERE {coluna} = @filtro", filtro)
    .ToListAsync();

O que o banco não deixa parametrizar

Existe um limite técnico importante: parâmetro só substitui valor. Nome de tabela, nome de coluna e direção de ordenação fazem parte da estrutura da consulta e precisam estar no texto do comando. Por isso ordenação dinâmica é o segundo lugar onde a injeção mais aparece:

ProdutosController.cs — ?ordenarPor= vira SQLC#
public async Task<IActionResult> Listar(string ordenarPor, string direcao)
{
    var produtos = await _db.Produtos
        .FromSqlRaw($"SELECT * FROM Produtos ORDER BY {ordenarPor} {direcao}")
        .ToListAsync();

    return Ok(produtos);
}

A tentação aqui é "sanitizar": remover aspas, bloquear a palavra DROP, filtrar --. Não faça isso. Blocklist é um jogo que você perde — o atacante tem comentários alternativos, codificação hexadecimal, CHAR(), espaço em branco exótico e mais criatividade do que a sua lista tem entradas.

A solução é inverter: em vez de tentar adivinhar o que é perigoso, aceite apenas o que você reconhece. E o jeito mais limpo de fazer isso no EF é nem sair do LINQ:

ProdutosController.csC#
private static readonly Dictionary<string, Expression<Func<Produto, object>>> Ordenacoes =
    new(StringComparer.OrdinalIgnoreCase)
    {
        ["nome"]  = p => p.Nome,
        ["preco"] = p => p.Preco,
        ["data"]  = p => p.CriadoEm,
    };

public async Task<IActionResult> Listar(string? ordenarPor, string? direcao)
{
    // Chave desconhecida cai no padrão. Nada do usuário entra no SQL.
    if (!Ordenacoes.TryGetValue(ordenarPor ?? "nome", out var seletor))
    {
        seletor = Ordenacoes["nome"];
    }

    var query = direcao?.ToLowerInvariant() == "desc"
        ? _db.Produtos.OrderByDescending(seletor)
        : _db.Produtos.OrderBy(seletor);

    return Ok(await query.ToListAsync());
}
Allowlist, nunca blocklist

O usuário não escolhe a coluna — ele escolhe uma chave, e você decide o que aquela chave significa. Um valor fora do dicionário não é "limpo", é simplesmente ignorado. Esse padrão vale para ordenação, filtros dinâmicos, nome de tabela por tenant e qualquer outro pedaço de estrutura que venha de fora.

Escrita e escalares: ExecuteSql e SqlQuery

A mesma dupla existe do lado da escrita. Para comandos que não retornam linhas, use ExecuteSqlAsync — que também recebe FormattableString:

PedidosService.csC#
var afetadas = await _db.Database.ExecuteSqlAsync(
    $"UPDATE Pedidos SET Status = {novoStatus} WHERE Id = {pedidoId}");

E para trazer um valor escalar ou um tipo que não é entidade do modelo, o SqlQuery<T> evita ter que descer para DbCommand na mão:

PedidosService.csC#
var total = await _db.Database
    .SqlQuery<decimal>($"SELECT SUM(Valor) FROM Pedidos WHERE ClienteId = {clienteId}")
    .SingleAsync();

Dapper: parâmetro é obrigação sua

O Dapper não tem LINQ para te proteger — todo SQL ali é escrito à mão. Em compensação, a forma segura é mais curta que a insegura, o que ajuda:

nuncaC#
var sql = $"SELECT * FROM Clientes WHERE Email = '{email}'";
var clientes = await conn.QueryAsync<Cliente>(sql);
sempreC#
var clientes = await conn.QueryAsync<Cliente>(
    "SELECT * FROM Clientes WHERE Email = @Email",
    new { Email = email });

Repare que a string do SQL é literal, sem $. Adotar "nenhuma query do Dapper começa com $" como regra de time é simples de aplicar e fácil de checar num diff.

O caso de lista, que costuma ser a desculpa para concatenar, o Dapper já resolve — ele expande a coleção em múltiplos parâmetros sozinho:

cláusula IN com listaC#
var ids = new[] { 10, 42, 77 };

var pedidos = await conn.QueryAsync<Pedido>(
    "SELECT * FROM Pedidos WHERE Id IN @Ids",   // sem parênteses
    new { Ids = ids });

// Dapper reescreve para: ... WHERE Id IN (@Ids1, @Ids2, @Ids3)
Limite o tamanho da lista

Como cada item vira um parâmetro, uma lista vinda do usuário sem limite pode estourar o teto do banco (o SQL Server para em 2.100 parâmetros) e derrubar a requisição. Valide o tamanho da coleção antes — é validação de entrada, tema do item 07, mas o sintoma aparece aqui.

Stored procedure não é blindagem

"Migramos para procedures, então estamos protegidos" é uma das crenças mais persistentes do assunto. Procedure protege quando os parâmetros são usados como parâmetros. Se ela monta SQL dinâmico por concatenação lá dentro, a injeção só mudou de camada:

sp_BuscarClientes — vulnerável dentro do bancoSQL
CREATE PROCEDURE sp_BuscarClientes @Nome NVARCHAR(100)
AS
BEGIN
    DECLARE @sql NVARCHAR(MAX);
    SET @sql = 'SELECT * FROM Clientes WHERE Nome = ''' + @Nome + '''';
    EXEC(@sql);
END
sp_BuscarClientes — sp_executesql com parâmetroSQL
CREATE PROCEDURE sp_BuscarClientes @Nome NVARCHAR(100)
AS
BEGIN
    DECLARE @sql NVARCHAR(MAX) =
        N'SELECT * FROM Clientes WHERE Nome = @p_Nome';

    EXEC sp_executesql @sql, N'@p_Nome NVARCHAR(100)', @p_Nome = @Nome;
END

E do lado do C#, chamar a procedure também precisa de parâmetro — concatenar o argumento na chamada é injeção antes mesmo de entrar no banco:

ClientesService.csC#
var clientes = await _db.Clientes
    .FromSql($"EXEC sp_BuscarClientes @Nome = {nome}")
    .ToListAsync();

Defesa em profundidade

Parametrizar resolve a causa. Mas segurança boa assume que uma camada vai falhar um dia — e trabalha para que a falha custe pouco. Três medidas mudam radicalmente o desfecho de uma injeção que passou:

MedidaO que muda quando a injeção acontece
Usuário do banco com menor privilégioSem DROP, sem ALTER, sem acesso a tabelas de sistema, o estrago fica limitado ao que a aplicação já faria. Nunca use sa nem db_owner
Conexão separada e somente-leitura para relatóriosJustamente onde mais aparece SQL cru, o atacante não consegue escrever nada
Erro genérico na respostaSem a mensagem do banco, o atacante perde o retorno que guia o ataque e cai no lento e barulhento blind SQL injection
O detalhe que mais entrega o banco

Devolver ex.Message numa resposta de erro transforma cada tentativa numa aula gratuita: nome da tabela, tipo da coluna, versão do servidor. A injeção cega leva dias; com mensagem de erro detalhada, leva minutos. Isso é o item 10 do guia — e é a dupla natural deste aqui.

Como verificar

Comece por um inventário. Toda ocorrência de método Raw no projeto merece uma olhada individual:

terminalbash
grep -rn "FromSqlRaw\|ExecuteSqlRaw\|SqlQueryRaw" --include="*.cs" .

# E o padrão realmente perigoso: interpolação junto do método cru
grep -rnE '(FromSqlRaw|ExecuteSqlRaw|SqlQueryRaw)\(\$"' --include="*.cs" .

O segundo comando é o que importa: Raw com $" na mesma linha é, na prática, sempre um bug. Depois de zerar a lista, trave o resultado com o analisador de APIs banidas para que ninguém reintroduza o padrão:

BannedSymbols.txtTEXT
# dotnet add package Microsoft.CodeAnalysis.BannedApiAnalyzers
M:Microsoft.EntityFrameworkCore.RelationalQueryableExtensions.FromSqlRaw``1(...); use FromSql
M:Microsoft.EntityFrameworkCore.RelationalDatabaseFacadeExtensions.ExecuteSqlRaw(...); use ExecuteSql

Para confirmar que uma consulta específica está mesmo parametrizada, ligue o log do EF em desenvolvimento e leia o SQL emitido. Se o valor aparece inline em vez de @p0, você achou o problema:

Program.cs — só em DevelopmentC#
options.UseSqlServer(cs)
       .LogTo(Console.WriteLine, LogLevel.Information)
       .EnableSensitiveDataLogging();   // JAMAIS em produção
EnableSensitiveDataLogging fica em Development

Ela existe para mostrar os valores dos parâmetros durante o diagnóstico. Ligada em produção, joga dado pessoal e credencial direto no log — vira incidente de LGPD sem ninguém ter sido atacado.

Checklist

  • Nenhuma ocorrência de $" dentro de FromSqlRaw, ExecuteSqlRaw ou SqlQueryRaw
  • SQL cru escrito com FromSql / ExecuteSql / SqlQuery (versões FormattableString)
  • Sem aspas em volta dos placeholders — = {valor}, não = '{valor}'
  • Ordenação e filtros dinâmicos resolvidos por allowlist, nunca por sanitização de string
  • Queries do Dapper com string literal e objeto de parâmetros, sem interpolação
  • Tamanho de coleção validado antes de ir para cláusula IN
  • Stored procedures sem EXEC(@sql) concatenado — sp_executesql com parâmetros
  • Usuário do banco sem db_owner, sem DDL, com permissão mínima
  • Relatórios em conexão somente-leitura separada
  • EnableSensitiveDataLogging restrito a Development
  • Analisador de APIs banidas travando os métodos Raw
