Rate limiting e proteção contra brute force

Um endpoint de login sem limite não é atacado por alguém tentando adivinhar sua senha. É atacado por um script que testa dez milhões de pares e-mail/senha vazados de outro site — e só precisa acertar um punhado deles para o dia valer a pena.

ASP.NET Core 10 Leitura: ~12 min Nível: essencial

O ataque mudou; a defesa da maioria não

A imagem mental de "força bruta" é antiga: um atacante fixa um usuário e tenta senha após senha até acertar. Contra isso, bloquear a conta depois de cinco erros resolve. E é por isso que quase todo sistema tem exatamente essa defesa, e só ela.

O que realmente acontece hoje são dois padrões que a proteção por conta não enxerga:

AtaqueComo funcionaO lockout pega?
Credential stuffingUsa pares e-mail/senha reais vazados de outros serviços. Uma tentativa por conta, milhões de contas.Não — nunca chega a 5 erros na mesma conta
Password sprayingFixa uma senha provável (Brasil@2026) e varre a lista de usuários da empresa.Não — um erro por conta, e segue
Brute force clássicoUma conta, muitas senhas.Sim

A conta do lado do atacante é simples. Se 1% das pessoas reaproveita a senha de um vazamento antigo — e a taxa real costuma ser maior —, cem mil tentativas viram mil contas legítimas. Nenhuma delas exigiu quebrar criptografia, achar bug ou enganar validação. Foi só o seu endpoint respondendo educadamente, milhões de vezes, o mais rápido que o servidor conseguiu.

Daí a estrutura da defesa: lockout limita o ataque por conta; rate limiting limita o ataque por origem. São camadas diferentes e você precisa das duas.

O lockout do Identity vem desarmado

Este é o achado mais comum em revisão de código .NET. As opções de lockout estão configuradas, o campo LockoutEnd está lá na tabela, tudo parece certo — e a proteção nunca dispara, por causa de um argumento:

Login.cshtml.csC#
var result = await _signInManager.PasswordSignInAsync(
    Input.Email,
    Input.Password,
    Input.RememberMe,
    lockoutOnFailure: false);   // nenhuma tentativa é contabilizada

Com false, o Identity autentica normalmente e não incrementa o contador de falhas. As opções de lockout continuam configuradas e continuam inúteis: é um alarme instalado, ligado na tomada, com o sensor desconectado. A correção é de uma palavra:

Login.cshtml.csC#
var result = await _signInManager.PasswordSignInAsync(
    Input.Email, Input.Password, Input.RememberMe,
    lockoutOnFailure: true);

if (result.IsLockedOut)
{
    _logger.LogWarning("Conta bloqueada por tentativas: {Email}", Input.Email);
    return RedirectToPage("./Lockout");
}

Se você autentica fora do fluxo de SignInManager — uma API que emite JWT, por exemplo — o contador não anda sozinho. Aí a checagem precisa ser explícita, e a ordem importa:

AuthService.csC#
var user = await _userManager.FindByEmailAsync(email);
if (user is null) return Resultado.CredenciaisInvalidas;

// 1. bloqueado? nem tenta validar a senha
if (await _userManager.IsLockedOutAsync(user))
    return Resultado.CredenciaisInvalidas;

// 2. CheckPasswordSignInAsync já cuida do contador
var check = await _signInManager.CheckPasswordSignInAsync(
    user, senha, lockoutOnFailure: true);

if (!check.Succeeded) return Resultado.CredenciaisInvalidas;

Os padrões e o que mexer neles

Os valores que vêm de fábrica são razoáveis para a maioria dos sistemas:

OpçãoPadrãoComentário
MaxFailedAccessAttempts5Abaixo de 3 gera suporte; acima de 10 dá margem demais
DefaultLockoutTimeSpan5 minutosCurto de propósito — veja o porquê abaixo
AllowedForNewUserstrueNunca desligue para "facilitar o onboarding"
Program.csC#
builder.Services.Configure<IdentityOptions>(o =>
{
    o.Lockout.MaxFailedAccessAttempts = 5;
    o.Lockout.DefaultLockoutTimeSpan = TimeSpan.FromMinutes(15);
    o.Lockout.AllowedForNewUsers = true;
});
Lockout longo é um DoS que você mesmo instalou

Se o bloqueio dura horas ou exige intervenção do suporte, o atacante inverte a arma: ele erra a senha de propósito, cinco vezes, na conta de cada diretor da empresa — e trava todo mundo. Bloqueio temporário e curto resolve o problema real (tornar a força bruta lenta demais para valer a pena) sem entregar um botão de negação de serviço. O detalhe crucial: uma autenticação bem-sucedida zera o contador, então o usuário legítimo que lembra a senha nunca acumula falhas.

Rate limiting nativo: o teto por origem

Desde o .NET 7 existe middleware de rate limiting na caixa, sem pacote externo. São quatro algoritmos, e a escolha muda conforme o que você está protegendo:

AlgoritmoComportamentoUse quando
Fixed windowN requisições por janela; o contador zera de uma vezTeto geral simples. Aceita uma rajada na virada da janela
Sliding windowJanela dividida em segmentos que expiram aos poucosLogin e endpoints sensíveis — sem o pico da virada
Token bucketSaldo que reabastece continuamenteUso legítimo em rajada: sincronização, importação
ConcurrencyLimita requisições simultâneas, não por tempoEndpoint caro: relatório, exportação, chamada a terceiro

Na prática você quer duas camadas: um teto global folgado, que serve de rede de contenção, e políticas estreitas nos endpoints que doem.

Program.csC#
builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    // teto geral por IP — rede de contenção, não proteção fina
    o.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(ctx =>
        RateLimitPartition.GetFixedWindowLimiter(
            partitionKey: ctx.Connection.RemoteIpAddress?.ToString() ?? "desconhecido",
            factory: _ => new FixedWindowRateLimiterOptions
            {
                PermitLimit = 300,
                Window = TimeSpan.FromMinutes(1),
                QueueLimit = 0
            }));

    // política estreita para autenticação
    o.AddPolicy<string>("login", ctx =>
        RateLimitPartition.GetSlidingWindowLimiter(
            partitionKey: ctx.Connection.RemoteIpAddress?.ToString() ?? "desconhecido",
            factory: _ => new SlidingWindowRateLimiterOptions
            {
                PermitLimit = 8,
                Window = TimeSpan.FromMinutes(5),
                SegmentsPerWindow = 5,
                QueueLimit = 0       // tentativa de login não entra em fila
            }));
});
Program.csC#
app.UseRateLimiter();

app.MapPost("/login", Autenticar).RequireRateLimiting("login");
app.MapPost("/senha/recuperar", Recuperar).RequireRateLimiting("login");

Em controllers, os equivalentes são [EnableRateLimiting("login")] e [DisableRateLimiting].

O padrão de rejeição é 503, não 429

Sem configurar nada, requisições recusadas voltam como 503 Service Unavailable — o código que significa "estou fora do ar". O efeito colateral é caro: seu monitoramento passa a acusar indisponibilidade quando na verdade o limitador está funcionando, e clientes bem-comportados não sabem que deveriam recuar. Sempre defina RejectionStatusCode como 429.

Responder direito à rejeição

Um 429 sem Retry-After convida o cliente a tentar de novo imediatamente. O lease carrega essa informação, e é aqui também que você registra o sinal de ataque:

Program.csC#
o.OnRejected = async (context, ct) =>
{
    if (context.Lease.TryGetMetadata(MetadataName.RetryAfter, out var espera))
        context.HttpContext.Response.Headers.RetryAfter =
            ((int)espera.TotalSeconds).ToString(CultureInfo.InvariantCulture);

    context.HttpContext.RequestServices.GetRequiredService<ILoggerFactory>()
        .CreateLogger("RateLimit")
        .LogWarning("Limite excedido em {Path} para {IP}",
            context.HttpContext.Request.Path,
            context.HttpContext.Connection.RemoteIpAddress);

    await context.HttpContext.Response.WriteAsJsonAsync(
        new ProblemDetails { Title = "Muitas requisições.", Status = 429 }, ct);
};

Esse log vale mais do que parece. Ele é frequentemente o primeiro sinal visível de que alguém está varrendo seu sistema — e o item 10 trata de como não afogar esse sinal em ruído.

A chave de partição é a parte difícil

O algoritmo é detalhe. O que decide se o rate limiting funciona é por qual chave você agrupa as requisições. E é aí que mora um erro grave.

IP atrás de proxy

Se a aplicação está atrás de load balancer, CDN ou Application Gateway — e ela quase sempre está —, RemoteIpAddress é o IP do proxy. Todo o tráfego do mundo cai em uma única partição: o limitador ou bloqueia todo mundo junto, ou é folgado demais para servir de alguma coisa. A correção é ler o header encaminhado:

Program.csC#
builder.Services.Configure<ForwardedHeadersOptions>(o =>
{
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
    o.KnownProxies.Add(IPAddress.Parse("10.0.0.4"));   // só o seu proxy
});

var app = builder.Build();
app.UseForwardedHeaders();   // bem no início do pipeline

E aqui a variação que circula como "solução", quando o header não é reconhecido:

o mesmo padrão do item 08C#
o.KnownProxies.Clear();
o.KnownNetworks.Clear();   // aceita X-Forwarded-For de qualquer um

Com as duas listas vazias, qualquer cliente pode declarar o próprio IP de origem. Para o atacante, isso transforma o rate limiting em enfeite: ele manda um X-Forwarded-For aleatório por requisição, cada uma cai numa partição nova, e nenhuma jamais atinge o limite. O padrão se repete pelo guia inteiro — a linha que "faz funcionar" é a linha que desliga a proteção.

Quando você não conhece o IP do proxy antecipadamente (comum em PaaS), a saída é restringir por rede conhecida com KnownNetworks, ou usar o header proprietário da sua CDN, que ela sobrescreve e você sabe ser confiável — nunca esvaziar as duas listas.

Particionar por usuário exige atenção à ordem

Usar ctx.User.Identity?.Name como chave só funciona se UseRateLimiter vier depois de UseAuthentication. Antes disso, User está vazio e todo mundo cai na mesma partição anônima — sem erro, sem aviso, com o limitador silenciosamente inútil. O trade-off é real: limitar depois da autenticação significa pagar o custo de validar o token antes de recusar. Um teto global por IP antes da autenticação, mais políticas por usuário depois dela, resolve os dois lados.

Por que não particionar o login por e-mail

Parece a chave ideal — e tem dois problemas. O primeiro é técnico: o e-mail está no corpo da requisição, e lê-lo no middleware exige bufferizar o body antes do model binding. O segundo é que essa é exatamente a proteção que o lockout do Identity já oferece, com estado persistido no banco em vez de memória do processo.

Divida o trabalho: rate limiting cuida da origem, lockout cuida da conta. Juntos, cobrem tanto o ataque concentrado quanto o espalhado.

Em memória significa por instância

Os limitadores nativos guardam o estado no processo. Com três réplicas atrás de um balanceador, o limite efetivo é três vezes o que você configurou — e se o balanceamento for round-robin, o atacante nem precisa fazer nada de especial para se beneficiar disso. Para limite realmente global, o estado precisa ser compartilhado (Redis) ou aplicado na borda, no gateway ou na CDN. Configure sabendo qual dos dois você tem.

Não é só o login

A conversa começa em autenticação e costuma parar ali. Os endpoints abaixo apanham pelo mesmo motivo e quase nunca têm limite:

EndpointO que o abuso causa
Recuperação de senhaInunda a caixa de entrada da vítima; queima reputação do seu domínio de envio
Envio de OTP por SMSCusto financeiro direto — cada tentativa é uma mensagem paga
Validação de OTPCódigo de 6 dígitos sem limite é força bruta em minutos
CadastroCriação em massa de contas; poluição de base e de métricas
Busca, relatório, exportaçãoConsulta cara repetida derruba o banco sem precisar de volume
UploadConsome disco e banda (item 07 trata do tamanho)
Qualquer coisa que chame API paga de terceiroSua fatura vira o alvo do ataque

Repare no padrão: os piores casos não derrubam nada. Eles geram custo. Um endpoint de SMS sem limite é o tipo de incidente que aparece primeiro na fatura, não no monitoramento.

A resposta não pode entregar quem existe

Limitar tentativas ajuda pouco se a sua API confirma, de graça, quais e-mails estão cadastrados. Com a lista de contas válidas em mãos, o password spraying fica muito mais eficiente:

enumeração de usuáriosC#
if (user is null)
    return Results.BadRequest("E-mail não cadastrado.");      // entrega
if (!senhaOk)
    return Results.BadRequest("Senha incorreta.");           // entrega

Uma mensagem única para os dois casos — "e-mail ou senha inválidos" — fecha a porta óbvia. Mas sobram três vazamentos sutis que valem conferir:

  • Tempo de resposta. Se o usuário não existe, você retorna antes de calcular o hash da senha, e a resposta volta bem mais rápido. Dá para medir. CheckPasswordSignInAsync ajuda aqui, mas o caminho do "usuário inexistente" precisa de atenção deliberada.
  • A mensagem de bloqueio. "Conta temporariamente bloqueada" só pode acontecer com conta que existe.
  • O cadastro e o "esqueci minha senha". "Este e-mail já está em uso" é a mesma informação, por outra porta. O fluxo de recuperação deve responder sempre igual e mandar o e-mail só se a conta existir.

O que rate limiting não resolve

Vale ser honesto sobre o limite da técnica. Um ataque distribuído por dezenas de milhares de IPs residenciais faz duas ou três tentativas por endereço — abaixo de qualquer limite que você consiga configurar sem barrar gente de verdade. Rate limiting encarece e desacelera; não elimina.

Em conta que importa, as camadas que mudam o jogo são outras:

  • MFA, e melhor ainda passkeys: com um segundo fator, a senha vazada deixa de ser suficiente — que é o pressuposto do credential stuffing inteiro.
  • Recusar senha sabidamente vazada no cadastro e na troca. O serviço Pwned Passwords permite essa checagem com k-anonimato: você envia só os cinco primeiros caracteres do hash SHA-1 e compara o resto localmente, sem nunca transmitir a senha.
  • Escalonar o atrito em vez de bloquear: liberar as primeiras tentativas, exigir desafio a partir de um limiar suspeito. Preserva o usuário legítimo e encarece o script.
  • Proteção na borda — WAF, CDN, gateway — que enxerga o padrão distribuído que uma instância isolada da sua aplicação nunca vai ver.

Como verificar

Três greps mostram se as duas camadas existem e se alguma delas está desarmada:

terminalbash
# O erro nº 1: lockout desligado no ponto de uso
grep -rn "lockoutOnFailure" --include="*.cs" .

# O rate limiter está registrado e no pipeline?
grep -rn "AddRateLimiter\|UseRateLimiter\|RejectionStatusCode" --include="*.cs" .

# Quais endpoints realmente aplicam alguma política?
grep -rn "RequireRateLimiting\|EnableRateLimiting\|DisableRateLimiting" --include="*.cs" .

# Confiança cega em header encaminhado
grep -rn "KnownProxies.Clear\|KnownNetworks.Clear\|X-Forwarded-For" --include="*.cs" .

Depois, o teste. Dispare mais tentativas do que o limite permite e conte o que voltou:

PowerShellPOWERSHELL
$codigos = 1..25 | ForEach-Object {
    (Invoke-WebRequest -Uri https://localhost:5001/login `
        -Method POST -SkipHttpErrorCheck `
        -ContentType "application/json" `
        -Body '{"email":"teste@exemplo.com","senha":"errada"}').StatusCode
}

$codigos | Group-Object | Select-Object Name, Count

O resultado esperado é uma faixa de 400/401 seguida de 429 — nunca 25 respostas iguais. Se aparecer 503, o RejectionStatusCode ficou no padrão. Vale repetir o teste variando o header X-Forwarded-For a cada requisição: se o limite deixar de ser atingido, a configuração de proxy está confiando em quem não devia.

Por fim, o teste do lockout: erre a senha de uma conta de teste seis vezes e confira a coluna AccessFailedCount na tabela de usuários. Se ela continuar zerada, o lockoutOnFailure está em false em algum caminho de autenticação — e a resposta da API não vai te contar isso.

Checklist

  • lockoutOnFailure: true em todos os pontos de autenticação, incluindo APIs que emitem token
  • result.IsLockedOut tratado com resposta que não revela a existência da conta
  • Bloqueio temporário e curto — sem trava permanente que dependa do suporte
  • AllowedForNewUsers em true
  • AddRateLimiter registrado e UseRateLimiter no pipeline
  • RejectionStatusCode definido como 429
  • OnRejected devolve Retry-After e registra log do evento
  • Política estreita e sem fila nos endpoints de login, recuperação de senha e OTP
  • Endpoints com custo por chamada — SMS, e-mail, API paga de terceiro — limitados
  • Chave de partição reflete o cliente real, não o IP do proxy
  • KnownProxies / KnownNetworks configurados com os proxies que você conhece, nunca esvaziados
  • Se a partição usa o usuário autenticado, UseRateLimiter vem depois de UseAuthentication
  • Limite dimensionado considerando o número de réplicas, ou aplicado na borda
  • Mensagem de erro de login idêntica para usuário inexistente e senha errada
  • Cadastro e recuperação de senha não confirmam se um e-mail existe na base
  • MFA disponível — e obrigatório para contas administrativas
