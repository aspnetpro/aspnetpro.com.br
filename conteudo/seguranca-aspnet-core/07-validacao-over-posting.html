Validação de entrada e over-posting

O model binder não sabe quais campos você quis expor. Ele preenche tudo que casar por nome — inclusive as propriedades que nunca apareceram no formulário. Esse é o buraco que transforma um cadastro comum em escalada de privilégio.

ASP.NET Core 10 Leitura: ~12 min Nível: essencial

O ataque em três linhas

Você tem uma entidade de domínio, um formulário de cadastro e uma action que recebe a entidade direto. Código que existe em praticamente todo projeto:

Usuario.cs + UsuariosController.csC#
public class Usuario
{
    public int Id { get; set; }
    public string Nome { get; set; } = "";
    public string Email { get; set; } = "";
    public bool IsAdmin { get; set; }          // nunca aparece no formulário
    public decimal LimiteCredito { get; set; }   // nem esse
}

[HttpPost]
public async Task<IActionResult> Criar(Usuario usuario)
{
    _db.Usuarios.Add(usuario);
    await _db.SaveChangesAsync();
    return RedirectToAction("Index");
}

A view mostra dois campos: nome e e-mail. O atacante abre o DevTools, ou simplesmente monta a requisição na mão, e envia mais dois:

requisição do atacanteHTTP
POST /usuarios/criar
Content-Type: application/x-www-form-urlencoded

Nome=Fulano&Email=fulano@evil.tld&IsAdmin=true&LimiteCredito=999999

O model binder faz o trabalho dele: procura, para cada propriedade pública com set, um valor de mesmo nome na requisição. Achou IsAdmin? Preenche. Não existe lista de campos permitidos em lugar nenhum — o contrato da sua API é a forma da classe, não o HTML que você renderizou.

O formulário não é o contrato

A view é sugestão, não fronteira. Qualquer proteção baseada em "esse campo não aparece na tela", "o botão está desabilitado" ou "o JavaScript valida antes de enviar" não é proteção — é decoração. A única fronteira real é o que o servidor aceita vincular.

Onde isso costuma aparecer

Não é só o IsAdmin didático. Na prática, os campos que mais causam estrago são os que ninguém pensa como "sensíveis":

CampoO que o atacante consegue
Id / chave primáriaSobrescrever o registro de outra pessoa em vez de criar o dele
TenantId, EmpresaIdGravar dados dentro de outro cliente em sistema multi-tenant
Preco, Desconto, TotalComprar por um valor que ele mesmo definiu
Status, AprovadoPular etapas do workflow — pedido nasce aprovado
CriadoEm, CriadoPorForjar auditoria
Propriedades de navegaçãoInserir entidades relacionadas em cascata pelo SaveChanges

Por que [Bind] não é a resposta

A correção que aparece primeiro em qualquer busca é restringir o binding por atributo:

protege hoje, vaza no próximo commitC#
[HttpPost]
public IActionResult Criar([Bind("Nome,Email")] Usuario usuario)

Funciona, e é infinitamente melhor que nada. Mas repare no formato: uma lista de campos, em string mágica, dentro de um atributo. Ela não é verificada pelo compilador, não acompanha refatoração de nome de propriedade e vive longe da classe que ela descreve. No dia em que alguém adicionar um campo novo na entidade, nada avisa que existem sete actions com listas para revisar.

É o mesmo padrão furado do item 02 e do item 06: segurança por enumeração. Você está listando o que proteger, quando deveria estar listando o que expor.

DTO por caso de uso: a correção de verdade

Inverta. Em vez de bloquear campos da entidade, crie um tipo que só tem o que aquela operação aceita. O que não existe na classe não pode ser vinculado — a proteção passa a ser estrutural, garantida pelo compilador:

CriarUsuarioRequest.csC#
public sealed record CriarUsuarioRequest
{
    [Required, StringLength(120, MinimumLength = 2)]
    public required string Nome { get; init; }

    [Required, EmailAddress, StringLength(254)]
    public required string Email { get; init; }
}
UsuariosController.csC#
[HttpPost]
public async Task<IActionResult> Criar(CriarUsuarioRequest req)
{
    if (!ModelState.IsValid) return View(req);

    var usuario = new Usuario
    {
        Nome = req.Nome,
        Email = req.Email,
        IsAdmin = false,                          // decisão do servidor
        LimiteCredito = Politica.LimiteInicial      // idem
    };

    _db.Usuarios.Add(usuario);
    await _db.SaveChangesAsync();
    return RedirectToAction("Index");
}

O mapeamento manual parece trabalho repetido, e é justamente esse o valor: cada campo que sai da requisição e entra no domínio passa por uma linha que alguém escreveu de propósito. Um campo novo na entidade não vira uma porta aberta por omissão — ele simplesmente não é preenchido até que alguém decida preenchê-lo.

AutoMapper reabre o buraco se você deixar

Trocar o mapeamento manual por _mapper.Map<Usuario>(req) é comum e razoável — mas se um dia o DTO ganhar uma propriedade IsAdmin (por exemplo, para uma tela de administração que reaproveitou a classe), o mapeamento por convenção volta a copiá-la sem aviso. Se usar AutoMapper em caminho sensível, mantenha DTOs separados por caso de uso e ligue a validação de configuração no startup.

Update é mais perigoso que create

No cadastro, o pior caso é um registro novo com dados errados. Na edição, o alvo pode ser o registro de outra pessoa. Duas coisas precisam acontecer, e a segunda quase sempre é esquecida:

UsuariosController.csC#
[HttpPost]
public async Task<IActionResult> Editar(int id, EditarUsuarioRequest req)
{
    if (!ModelState.IsValid) return View(req);

    // 1. carrega do banco já filtrando pelo escopo de quem está logado
    var usuario = await _db.Usuarios
        .FirstOrDefaultAsync(u => u.Id == id && u.EmpresaId == _contexto.EmpresaId);

    if (usuario is null) return NotFound();

    // 2. aplica só o que essa operação permite mudar
    usuario.Nome = req.Nome;
    usuario.Email = req.Email;

    await _db.SaveChangesAsync();
    return RedirectToAction("Index");
}

O id vem da rota, o escopo vem do usuário autenticado, e o corpo da requisição só contribui com nome e e-mail. O anti-padrão correspondente é este:

o update que confia no clienteC#
_db.Usuarios.Update(usuario);   // entidade montada pelo binding, com Id vindo do corpo
await _db.SaveChangesAsync();

Aqui o atacante escolhe o Id e sobrescreve qualquer linha da tabela. E note que nenhum [Bind] resolveria a parte do escopo: mesmo com a lista de campos certa, sem o filtro por EmpresaId na consulta você continua editando dados de outro tenant.

Form vence rota no desempate

A ordem padrão dos value providers no MVC é form → rota → query string. Numa action Editar(int id, ...) mapeada em /usuarios/{id}/editar, um campo oculto id enviado no corpo sobrescreve o valor da rota. Se sua autorização confia no id do parâmetro achando que ele veio da URL, ela pode estar validando o número que o atacante escolheu. Sempre carregue do banco com o filtro de escopo, como no exemplo acima.

Validação: quem checa o ModelState?

DTO resolve quais campos entram. Validação resolve o que pode vir dentro deles. E aqui o comportamento muda conforme o tipo de controller — mais uma vez, a inconsistência é a fonte do bug:

ContextoRejeita entrada inválida sozinho?
Controller com [ApiController]Sim — devolve 400 com ProblemDetails
Controller MVC sem [ApiController]Não — você precisa checar ModelState.IsValid
Razor PagesNão — checagem manual no handler
Minimal API (padrão)Não — até você registrar AddValidation()

O caso mais traiçoeiro é o do meio: as anotações [Required] e [Range] estão lá, o ModelState é populado corretamente com os erros — e a action segue em frente porque ninguém perguntou. A validação roda e o resultado é ignorado.

Nunca suprima o filtro do [ApiController]

Se você encontrar SuppressModelStateInvalidFilter = true em um ConfigureApiBehaviorOptions, investigue. Quase sempre foi adicionado para "resolver" um 400 chato durante o desenvolvimento, e o efeito colateral é que toda a API passou a aceitar corpo inválido silenciosamente.

Nullable reference types já valem como [Required]

Com NRT habilitado (padrão em projetos novos), uma propriedade string não-anulável é tratada como obrigatória pelo model binding, mesmo sem o atributo. É um bom padrão — mas significa que trocar string por string? numa refatoração remove uma validação sem que ninguém perceba. Quando a obrigatoriedade for uma regra de negócio, escreva o [Required] explicitamente.

Minimal APIs: validação nativa no .NET 10

Historicamente, Minimal APIs não validavam nada — as anotações eram puramente decorativas e você precisava chamar um validador na mão em cada handler. No .NET 10 isso mudou: existe validação embutida, ligada por um registro no container.

Program.csC#
builder.Services.AddValidation();

var app = builder.Build();

app.MapPost("/usuarios", (CriarUsuarioRequest req) =>
{
    // só chega aqui se o DTO passou nas anotações
    return TypedResults.Created();
});

Um gerador de código descobre os tipos usados nos handlers e um endpoint filter aplica a validação antes do seu delegate rodar; a resposta de falha sai como 400 com ProblemDetails. Para os casos legítimos em que a validação atrapalha, a isenção é explícita e por endpoint:

Program.csC#
app.MapPost("/webhook", (Payload p) => TypedResults.Accepted("/"))
   .DisableValidation();
O mesmo princípio dos itens anteriores

Repare no padrão que se repete no guia inteiro: ligar globalmente e isentar de forma explícita. Autorização com FallbackPolicy, antiforgery com filtro global, validação com AddValidation(). A isenção vira uma linha visível em code review — o esquecimento, não.

Quando as anotações não dão conta

DataAnnotations resolvem formato: obrigatório, tamanho, faixa, regex. Regra de negócio — "a data final precisa ser depois da inicial", "esse CNPJ não pode se repetir dentro da mesma empresa" — pede algo com mais expressividade. FluentValidation continua sendo a escolha natural:

CriarPedidoValidator.csC#
public sealed class CriarPedidoValidator : AbstractValidator<CriarPedidoRequest>
{
    public CriarPedidoValidator()
    {
        RuleFor(x => x.Itens)
            .NotEmpty()
            .Must(i => i.Count <= 200).WithMessage("Máximo de 200 itens por pedido.");

        RuleForEach(x => x.Itens).ChildRules(item =>
        {
            item.RuleFor(i => i.Quantidade).InclusiveBetween(1, 999);
            item.RuleFor(i => i.ProdutoId).GreaterThan(0);
        });

        RuleFor(x => x.EntregaEm)
            .GreaterThan(x => x.CriadoEm)
            .WithMessage("A entrega precisa ser posterior à criação.");
    }
}

Note o que não está nesse DTO: preço. Quantidade e produto vêm do cliente; valor unitário, desconto e total são calculados no servidor a partir do catálogo. Aceitar preço na requisição e validar que ele é "um decimal positivo" é validar a coisa errada com muito capricho.

Validar formato não é validar autorização

Este é o ponto que mais escapa em revisão de código. Considere um campo perfeitamente validado:

validado e vulnerávelC#
public sealed record CriarNotaRequest
{
    [Range(1, int.MaxValue)]
    public required int ClienteId { get; init; }   // é um int positivo. e daí?
}

ClienteId = 4271 passa em qualquer validação de formato. A pergunta que importa é outra: esse cliente pertence a quem está fazendo a requisição? Toda referência a identificador que chega de fora precisa ser reconferida contra o escopo do usuário autenticado, no banco:

NotasService.csC#
var cliente = await _db.Clientes
    .FirstOrDefaultAsync(c => c.Id == req.ClienteId
                           && c.EmpresaId == _contexto.EmpresaId);

if (cliente is null) return Results.NotFound();

Devolver 404 em vez de 403 é intencional: evita confirmar para o atacante que o identificador existe em outro tenant.

Limites: a validação que ninguém escreve

Entrada válida em formato pode derrubar a aplicação pelo tamanho. Um JSON de 40 MB, um array com um milhão de elementos ou um objeto aninhado mil níveis são requisições "bem formadas" que consomem CPU e memória antes de a sua regra de negócio sequer rodar.

Program.csC#
builder.Services.Configure<MvcOptions>(o =>
{
    o.MaxModelBindingCollectionSize = 500;    // padrão: 1024
    o.MaxModelBindingRecursionDepth = 16;     // padrão: 32
});

builder.Services.ConfigureHttpJsonOptions(o =>
{
    o.SerializerOptions.MaxDepth = 16;
});

builder.WebHost.ConfigureKestrel(o =>
{
    o.Limits.MaxRequestBodySize = 1 * 1024 * 1024;   // padrão: ~28 MB
});

Aperte o limite global e libere pontualmente onde o upload é o propósito do endpoint:

UploadController.csC#
[HttpPost("documentos")]
[RequestSizeLimit(20 * 1024 * 1024)]
public async Task<IActionResult> Enviar(IFormFile arquivo) { ... }
Extensão de arquivo não é validação

Em upload, checar o nome terminado em .pdf não diz nada sobre o conteúdo. Valide os bytes iniciais contra a assinatura esperada do formato, gere você mesmo o nome do arquivo no servidor (nunca reaproveite o FileName enviado, que pode conter ../) e guarde fora da pasta servida como estática. O item 10 volta a esse assunto pelo lado do vazamento de informação.

Como verificar

Comece pela pergunta mais direta: alguma entidade do EF está sendo usada como parâmetro de action? Esse grep dá o mapa do risco em segundos:

terminalbash
# Actions que recebem tipos do namespace de domínio/entidades
grep -rn "public.*IActionResult.*(\(Usuario\|Pedido\|Cliente\|Produto\) " --include="*.cs" .

# Update/Add direto com objeto vindo do binding
grep -rn "\.Update(\|\.Attach(" --include="*.cs" .

# O filtro de ModelState foi desligado em algum lugar?
grep -rn "SuppressModelStateInvalidFilter\|DisableValidation" --include="*.cs" .

Depois, o teste que prova. Pegue um endpoint de cadastro e envie um campo que a tela não mostra:

PowerShellPOWERSHELL
# Campo que não existe no formulário — deve ser ignorado ou recusado
Invoke-RestMethod -Uri https://localhost:5001/usuarios `
    -Method POST `
    -ContentType "application/json" `
    -WebSession $sessao `
    -Body '{"nome":"Teste","email":"t@exemplo.com","isAdmin":true}'

# Agora confirme no banco: o registro criado tem IsAdmin = false?

O detalhe importante: a resposta 201 não prova nada. O over-posting é silencioso por natureza — a requisição é aceita normalmente e o campo extra entra junto. A verificação só termina quando você olha o dado gravado.

Vale transformar isso em teste de integração para os campos sensíveis de cada agregado. É o tipo de proteção que regride sem barulho no dia em que alguém "simplifica" a action trocando o DTO pela entidade.

Checklist

  • Nenhuma entidade do EF Core aparece como parâmetro de action, page handler ou delegate de Minimal API
  • DTO específico por caso de uso — criar e editar não compartilham a mesma classe
  • Mapeamento DTO → entidade explícito, sem cópia por convenção em caminho sensível
  • Campos de decisão do servidor (IsAdmin, Status, Preco, TenantId) nunca vêm da requisição
  • Update carrega a entidade do banco filtrando por rota e escopo do usuário autenticado
  • ModelState.IsValid checado em todo controller MVC e Razor Page sem [ApiController]
  • SuppressModelStateInvalidFilter não aparece no projeto
  • builder.Services.AddValidation() registrado nas Minimal APIs
  • Cada DisableValidation() tem justificativa registrada
  • Regras de negócio em FluentValidation, não espalhadas dentro do handler
  • Todo identificador recebido do cliente é reconferido contra o escopo do usuário no banco
  • Limites de corpo, tamanho de coleção e profundidade de JSON configurados abaixo dos padrões
  • Upload valida assinatura de bytes e gera o nome do arquivo no servidor
  • Teste de integração que envia campo extra e verifica o valor gravado no banco
