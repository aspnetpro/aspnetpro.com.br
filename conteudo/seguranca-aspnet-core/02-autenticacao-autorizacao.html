Autenticação e autorização com deny by default

Proteger endpoint por endpoint é uma estratégia que falha em silêncio: o dia que alguém esquecer um [Authorize], nada quebra, nenhum teste fica vermelho e o endpoint simplesmente nasce aberto. Inverta a lógica.

ASP.NET Core 10 Leitura: ~8 min Nível: essencial

Por que a abordagem opt-in falha

O modelo padrão de quase todo projeto é o opt-in: tudo nasce público, e você anota [Authorize] no que precisa proteger. O problema não é técnico, é humano — essa abordagem depende de lembrar, toda vez, para sempre, por toda a vida do projeto.

E o custo de esquecer é assimétrico. Se você anotar um endpoint público com [Authorize] por engano, alguém reclama em minutos: o recurso parou de funcionar. Mas se esquecer o [Authorize] num endpoint privado, nada acontece. Os testes passam. O code review não pega, porque a ausência de uma linha é invisível no diff. O endpoint funciona perfeitamente — inclusive para quem não deveria acessá-lo. Você só descobre no pentest. Ou no vazamento.

A regra

Toda decisão de segurança que depende de alguém lembrar de adicionar algo vai falhar. Configure o padrão para que esquecer resulte em bloqueio, não em exposição.

Deny by default com FallbackPolicy

A FallbackPolicy é a política aplicada a qualquer endpoint que não tenha nenhuma outra regra de autorização. Configurando-a para exigir usuário autenticado, você inverte o padrão do projeto: tudo nasce fechado, e você abre o que precisa ser público — de forma explícita e visível no diff.

Program.csC#
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie();

builder.Services.AddAuthorizationBuilder()
    .SetFallbackPolicy(new AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser()
        .Build());

var app = builder.Build();

app.UseRouting();

app.UseAuthentication();   // quem é você
app.UseAuthorization();    // o que você pode fazer

app.MapControllers();

app.Run();

Feito isso, o endpoint que alguém criar amanhã e esquecer de anotar responde 401 em vez de servir dados. O esquecimento agora é barulhento.

Para liberar o que é legitimamente público, use [AllowAnonymous]. A grande vantagem é que agora a exceção fica escrita, aparece no code review e alguém pode questionar:

AuthController.csC#
[AllowAnonymous]
[HttpPost("/login")]
public async Task<IActionResult> Login(LoginRequest request) { /* ... */ }

Na prática, a lista de endpoints que precisam de [AllowAnonymous] é curta e previsível: login, registro, recuperação de senha, confirmação de e-mail, health check, webhooks de terceiros e a home pública.

DefaultPolicy não é a mesma coisa

A DefaultPolicy é o que roda quando alguém escreve [Authorize] sem parâmetros. Ela só age onde já existe o atributo. A FallbackPolicy age justamente onde não existe atributo nenhum — é ela que fecha o buraco do esquecimento. Configure a fallback.

Os três pontos cegos da FallbackPolicy

Ativar a fallback resolve a maior parte do problema, mas não é uma cerca perfeita. Existem três lugares por onde ela não passa — e é exatamente neles que a falsa sensação de segurança machuca.

1. Arquivos estáticos não passam por autorização

O UseStaticFiles() roda antes do roteamento e da autorização no pipeline. Ele serve o arquivo e encerra a requisição ali mesmo. Nenhuma política — fallback, default ou qualquer outra — chega a ser avaliada.

Tudo que estiver em wwwroot é público, ponto final. Aquele wwwroot/uploads/contrato-cliente.pdf está acessível para quem souber a URL. E URL não é segredo: vaza em log de proxy, em histórico de navegador, no header Referer, no print que o usuário manda no WhatsApp.

DocumentosController.csC#
// Arquivo privado fica FORA do wwwroot e é servido por um endpoint.
[HttpGet("/documentos/{id:int}")]
public async Task<IActionResult> Baixar(int id)
{
    var usuarioId = User.FindFirstValue(ClaimTypes.NameIdentifier);

    var doc = await _db.Documentos
        .FirstOrDefaultAsync(d => d.Id == id && d.UsuarioId == usuarioId);

    if (doc is null) return NotFound();

    // Caminho montado no servidor. Nunca concatene nome vindo do usuário.
    var caminho = Path.Combine(_storageRoot, doc.NomeFisico);

    return PhysicalFile(caminho, doc.ContentType, doc.NomeOriginal);
}

2. AllowAnonymous ganha de tudo, em qualquer nível

O [AllowAnonymous] não "empata" com o [Authorize] — ele vence. E vence mesmo quando está num nível acima. Um [AllowAnonymous] na classe do controller anula o [Authorize] das actions individuais:

RelatoriosController.cs — todas as actions estão abertasC#
[AllowAnonymous]   // alguém colocou aqui pra liberar UMA action pública...
public class RelatoriosController : Controller
{
    [AllowAnonymous]
    public IActionResult Publico() => View();

    [Authorize(Roles = "Admin")]   // ...e este [Authorize] é IGNORADO.
    public IActionResult Faturamento() => View();
}

Mantenha o [AllowAnonymous] sempre no método, nunca na classe. Aplicado na classe, ele abre por engano tudo que for adicionado ali no futuro.

3. Ordem do middleware muda o resultado

Autorização precisa acontecer depois do roteamento, porque é o roteamento que descobre qual endpoint foi escolhido e quais políticas ele carrega. Fora de ordem, a autorização avalia uma requisição sem endpoint definido e não aplica nada.

OrdemMiddlewareO que acontece se estiver fora do lugar
1UseRouting()Sem ele antes, o endpoint ainda não foi resolvido e nenhuma política é encontrada
2UseAuthentication()Depois do UseAuthorization, o User chega vazio e todo mundo vira anônimo
3UseAuthorization()É aqui que a fallback policy é aplicada
4MapControllers()Executa o endpoint já autorizado

O erro que a FallbackPolicy não pega

Agora a parte mais importante deste item. Você ativou deny by default, todo endpoint exige login, o pentest de autenticação passou. E mesmo assim existe uma falha aberta — a que mais aparece em aplicação corporativa real.

O [Authorize] responde a pergunta "esse usuário está autenticado?". Ele não responde "esse registro pertence a esse usuário?". Repare:

FaturasController.cs — qualquer usuário logado lê a fatura de qualquer outroC#
[Authorize]
[HttpGet("/faturas/{id:int}")]
public async Task<IActionResult> Get(int id)
{
    var fatura = await _db.Faturas.FindAsync(id);

    return fatura is null ? NotFound() : Ok(fatura);
}

O atacante não precisa de nenhuma ferramenta sofisticada. Ele cria uma conta legítima, acessa a própria fatura em /faturas/4021, troca o número para /faturas/4020 e lê a fatura do cliente anterior. Depois roda um laço de 1 a 50000. Isso se chama IDOR (ou BOLA, em API) e lidera o ranking de falhas de API da OWASP.

A correção: filtre pelo dono na própria consulta

Na maior parte dos casos a solução é simples e não precisa de infraestrutura nenhuma — basta o dono entrar na cláusula Where:

FaturasController.csC#
[Authorize]
[HttpGet("/faturas/{id:int}")]
public async Task<IActionResult> Get(int id)
{
    var usuarioId = User.FindFirstValue(ClaimTypes.NameIdentifier);

    var fatura = await _db.Faturas
        .FirstOrDefaultAsync(f => f.Id == id && f.UsuarioId == usuarioId);

    // NotFound, não Forbid: não confirme que o id existe.
    return fatura is null ? NotFound() : Ok(fatura);
}
Por que NotFound e não Forbid

Responder 403 confirma que o recurso existe e que o id é válido — é um oráculo de enumeração. O atacante mapeia quais ids existem só pela diferença entre 403 e 404. Devolver 404 nos dois casos não entrega nada. A exceção é quando o usuário legitimamente precisa entender que não tem permissão sobre algo que ele sabe que existe: aí o 403 é a resposta correta e honesta.

Quando a regra é complexa: autorização baseada em recurso

Filtrar na query resolve "é meu". Mas regras reais costumam ser mais ricas: o dono edita, o gestor da área aprova, o auditor lê tudo mas não altera nada. Espalhar esses if pelos controllers vira dívida técnica rapidamente. É o caso de usar o IAuthorizationService, que recebe o recurso já carregado:

FaturaOwnerHandler.csC#
public class SameOwnerRequirement : IAuthorizationRequirement { }

public class FaturaOwnerHandler
    : AuthorizationHandler<SameOwnerRequirement, Fatura>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        SameOwnerRequirement requirement,
        Fatura fatura)
    {
        var usuarioId = context.User.FindFirstValue(ClaimTypes.NameIdentifier);

        if (usuarioId is not null && fatura.UsuarioId == usuarioId)
        {
            context.Succeed(requirement);
        }

        return Task.CompletedTask;
    }
}
Program.cs + FaturasController.csC#
// Registro
builder.Services.AddAuthorizationBuilder()
    .SetFallbackPolicy(new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build())
    .AddPolicy("PodeVerFatura", p => p.Requirements.Add(new SameOwnerRequirement()));

builder.Services.AddScoped<IAuthorizationHandler, FaturaOwnerHandler>();

// Uso
var fatura = await _db.Faturas.FindAsync(id);
if (fatura is null) return NotFound();

var resultado = await _authorization.AuthorizeAsync(User, fatura, "PodeVerFatura");

return resultado.Succeeded ? Ok(fatura) : NotFound();
Cuidado com o tempo de vida do handler

Se o handler injeta DbContext ou qualquer serviço com escopo de requisição, registre-o como Scoped. Boa parte dos exemplos na internet usa Singleton — o que funciona apenas para handlers sem dependência nenhuma e, com DbContext, gera erro de escopo ou corrupção de estado entre requisições.

Papéis versus políticas

Existe uma diferença de manutenção enorme entre estas duas linhas:

espalhado em 40 arquivosC#
[Authorize(Roles = "Admin,Gerente,Supervisor")]
a regra mora em um lugar sóC#
[Authorize(Policy = "PodeAprovarPedido")]

A primeira amarra o código à estrutura organizacional. Quando o negócio criar o papel "Coordenador", você vai caçar string em 40 arquivos — e vai esquecer de algum. A segunda amarra o código à capacidade, que é o que o endpoint realmente se importa. Mudou quem pode aprovar? Uma linha no Program.cs:

Program.csC#
builder.Services.AddAuthorizationBuilder()
    .SetFallbackPolicy(new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build())
    .AddPolicy("PodeAprovarPedido", p =>
        p.RequireRole("Admin", "Gerente", "Supervisor", "Coordenador"));

Em Minimal APIs a mesma política se aplica direto no endpoint ou no grupo inteiro — e aplicar no grupo é a forma mais segura, porque o endpoint novo herda a proteção:

Program.csC#
var pedidos = app.MapGroup("/pedidos")
    .RequireAuthorization("PodeAprovarPedido");

pedidos.MapPost("/{id:int}/aprovar", AprovarPedido);
pedidos.MapPost("/{id:int}/rejeitar", RejeitarPedido);

Como verificar

O teste manual é o mais rápido: chame um endpoint sem credencial nenhuma e confirme o 401.

terminalbash
curl -si https://seusite.com.br/api/faturas/1 | head -n 1
#   HTTP/1.1 401 Unauthorized

# E o teste de IDOR: autentique como o usuário A e peça o recurso do B.
curl -si -H "Authorization: Bearer $TOKEN_USUARIO_A" \
     https://seusite.com.br/api/faturas/4020 | head -n 1
#   HTTP/1.1 404 Not Found   ← correto
#   HTTP/1.1 200 OK          ← você tem um IDOR

Melhor ainda é travar isso num teste automatizado. Dá para varrer todos os endpoints registrados e falhar o build quando alguém abrir um novo sem passar por revisão:

EndpointsSecurityTests.csC#
[Fact]
public void Somente_endpoints_aprovados_sao_publicos()
{
    var publicos = _factory.Services
        .GetRequiredService<EndpointDataSource>()
        .Endpoints
        .Where(e => e.Metadata.GetMetadata<IAllowAnonymous>() is not null)
        .Select(e => e.DisplayName)
        .Order()
        .ToArray();

    // Endpoint público novo quebra o teste e força a conversa no PR.
    Assert.Equal(EndpointsPublicosEsperados, publicos);
}
O valor real desse teste

Ele não impede ninguém de abrir um endpoint — impede que isso aconteça sem alguém perceber. Quem precisar de um endpoint público vai ter que editar a lista esperada, e essa edição aparece no diff do PR.

Checklist

  • SetFallbackPolicy com RequireAuthenticatedUser() configurada
  • UseAuthentication() antes de UseAuthorization(), ambos depois de UseRouting()
  • [AllowAnonymous] apenas em métodos, nunca na classe do controller
  • Nenhum arquivo privado dentro de wwwroot — download passa por endpoint autorizado
  • Toda consulta por id filtra pelo dono, ou passa por IAuthorizationService
  • Recurso de outro usuário responde 404, não 403
  • Autorização expressa em políticas por capacidade, não em Roles espalhados
  • Grupos de Minimal API com RequireAuthorization() no grupo, não endpoint a endpoint
  • Teste automatizado fixando a lista de endpoints públicos
