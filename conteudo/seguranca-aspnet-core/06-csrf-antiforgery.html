CSRF: antiforgery em formulários e APIs

O navegador anexa o cookie de sessão em toda requisição para o seu domínio — inclusive na que partiu do site do atacante. O antiforgery existe para provar que aquele POST saiu da sua página, e é exatamente aí que MVC e Minimal APIs deixam a porta encostada.

ASP.NET Core 10 Leitura: ~11 min Nível: essencial

O ataque em uma tela

Seu usuário está logado no sistema. Noutra aba, ele abre uma página qualquer — um resultado de busca, um link do WhatsApp, um anúncio. Essa página contém:

página do atacanteHTML
<form action="https://app.suaempresa.com.br/usuarios/promover" method="post">
  <input type="hidden" name="email" value="atacante@evil.tld">
  <input type="hidden" name="perfil" value="Administrador">
</form>
<script>document.forms[0].submit();</script>

O formulário envia sozinho, o navegador vê uma requisição para app.suaempresa.com.br e faz o que sempre faz: anexa o cookie de autenticação. Do lado do servidor, chega um POST perfeitamente autenticado, com a identidade real do usuário. Sua aplicação promove o atacante a administrador e devolve um redirect.

Aqui está o detalhe que costuma confundir: a Same-Origin Policy impede o atacante de ler a resposta. Ele nunca vê o resultado. E isso não atrapalha em nada — CSRF é um ataque de escrita. Transferir, promover, excluir, trocar e-mail de recuperação: nenhuma dessas ações precisa que o atacante leia o retorno.

Quem está exposto

A pergunta certa é: o navegador anexa a credencial automaticamente? Se sim, existe CSRF.

Forma de autenticaçãoVulnerável a CSRF?
Cookie (Identity, AddCookie)Sim — é o caso clássico
JWT guardado em cookieSim — o formato do token é irrelevante
Windows / NegotiateSim — a credencial vai sozinha
HTTP BasicSim — o navegador reenvia após o primeiro desafio
Authorization: Bearer montado pelo JavaScriptNão — nada é anexado automaticamente
"Usamos JWT, então não temos CSRF"

Essa frase só é verdadeira se o token for lido de algum lugar pelo seu próprio código e colocado no header a cada chamada. No momento em que você guarda o JWT num cookie — decisão comum e legítima, porque protege contra roubo por XSS — o navegador volta a enviá-lo sozinho, e o CSRF volta junto. Cookie é cookie, não importa o que esteja dentro.

Como o antiforgery resolve

A ideia é exigir uma prova que o atacante não consegue produzir. O ASP.NET Core gera dois valores emparelhados a cada requisição de página:

  • um cookie (.AspNetCore.Antiforgery.*), HttpOnly, que o navegador guarda;
  • um token de requisição, embutido na página como campo oculto __RequestVerificationToken.

Na validação, o servidor exige os dois e confere se combinam entre si e com o usuário logado. O site do atacante consegue fazer o navegador enviar o cookie — mas não consegue ler a sua página para descobrir o campo oculto, porque a Same-Origin Policy bloqueia essa leitura. Sem o par, o POST morre com 400.

E como o token é criptograficamente amarrado à identidade autenticada, também não adianta o atacante pegar um token válido da própria conta dele e reaproveitar na sessão da vítima.

Onde você já está protegido — e onde não

Esta é a parte que mais gera falsa sensação de segurança, porque o comportamento muda conforme o modelo de programação:

ModeloGera o token?Valida sozinho?
Razor PagesSimSim — para todo verbo inseguro
MVC com Tag Helper <form>SimNão — precisa do atributo
MVC com <form> HTML puroNãoNão
Minimal API com [FromForm]—Só com UseAntiforgery()
Minimal API com corpo JSON—Não — nem com o middleware
Blazor Web AppSimSim — via UseAntiforgery()

A linha do MVC é a mais traiçoeira. O Tag Helper <form> injeta o campo oculto automaticamente, então você vê o token no HTML e conclui que está protegido. Gerar não é validar: sem o atributo na action, o servidor recebe o POST sem token e processa normalmente.

Atenção ao asp-action em form HTML puro

O Tag Helper só entra em ação quando a tag <form> tem algum atributo asp-* ou é processada pelo Tag Helper de formulário. Um <form action="/x" method="post"> escrito na mão, ou com asp-antiforgery="false", sai sem campo nenhum — e aí o formulário legítimo passa a falhar assim que você ligar a validação. É o bug número um logo depois de endurecer isso.

MVC: ligue globalmente, não action por action

O padrão que a maioria dos projetos usa é decorar cada POST:

UsuariosController.cs — protege o que você lembrouC#
[HttpPost]
[ValidateAntiForgeryToken]
public IActionResult Promover(PromoverModel model) { ... }

É a mesma lógica furada do item 02: proteção por enumeração. Um dia alguém adiciona uma action e esquece o atributo, e não existe teste que acuse. Inverta — ligue a validação como filtro global e trate a exceção como exceção:

Program.csC#
builder.Services.AddControllersWithViews(options =>
    options.Filters.Add(new AutoValidateAntiforgeryTokenAttribute()));

A diferença entre os dois atributos importa:

AtributoComportamento
[ValidateAntiForgeryToken]Valida sempre, inclusive em GET — por isso não serve como filtro global
[AutoValidateAntiforgeryToken]Valida POST, PUT, PATCH e DELETE; ignora GET, HEAD, OPTIONS e TRACE
[IgnoreAntiforgeryToken]Isenta um endpoint específico, sobrepondo o filtro global
O F maiúsculo que quebra o build

Repare: é ValidateAntiForgeryToken, mas AutoValidateAntiforgeryToken e IgnoreAntiforgeryToken. A inconsistência é do próprio framework e sobrevive por compatibilidade. Se o IntelliSense não achou o que você digitou, é quase sempre isso.

Com o filtro global no lugar, os endpoints que legitimamente não podem exigir token — webhook de gateway de pagamento, callback de provedor, API consumida por serviço com Bearer — passam a declarar isso de forma explícita e revisável:

WebhookController.csC#
[ApiController]
[Route("api/webhook")]
[IgnoreAntiforgeryToken]   // autenticado por assinatura HMAC, não por cookie
public class WebhookController : ControllerBase
{
    [HttpPost]
    public IActionResult Post([FromBody] Payload payload) => Accepted();
}
Isenção só faz sentido com credencial não-ambiente

Um endpoint pode dispensar antiforgery quando ele não confia em cookie para autenticar — assinatura HMAC, Bearer, mTLS. Se a autenticação vem do cookie e você isentou "porque estava dando erro no Postman", você não corrigiu nada: reabriu o buraco.

Minimal APIs: o middleware cobre menos do que parece

Minimal APIs não têm filtros de MVC, então [ValidateAntiForgeryToken] simplesmente não existe ali. O que existe é um middleware:

Program.cs — a ordem importaC#
app.UseAuthentication();
app.UseAuthorization();
app.UseAntiforgery();   // depois da autenticação: o token é amarrado ao usuário

app.MapPost("/perfil", ([FromForm] PerfilDto dto) => Results.Ok());

Agora o ponto crítico, e é onde muita gente se engana: esse middleware valida apenas requisições que enviam formulário — multipart/form-data ou application/x-www-form-urlencoded. Um MapPost que recebe JSON passa direto por ele, sem validação nenhuma.

Para esses casos, a validação é explícita, via serviço:

Program.csC#
app.MapDelete("/itens/{id}", async (int id, IAntiforgery antiforgery, HttpContext ctx) =>
{
    await antiforgery.ValidateRequestAsync(ctx);
    // segue o fluxo
    return Results.NoContent();
});

Repetir isso em trinta endpoints é convite ao esquecimento. Um endpoint filter aplicado no grupo resolve de uma vez e mantém o princípio de fechar por padrão:

Program.csC#
var api = app.MapGroup("/api")
    .AddEndpointFilter(async (ctx, next) =>
    {
        var metodo = ctx.HttpContext.Request.Method;

        if (!HttpMethods.IsGet(metodo) && !HttpMethods.IsHead(metodo)
            && !HttpMethods.IsOptions(metodo))
        {
            var antiforgery = ctx.HttpContext.RequestServices
                .GetRequiredService<IAntiforgery>();

            try
            {
                await antiforgery.ValidateRequestAsync(ctx.HttpContext);
            }
            catch (AntiforgeryValidationException)
            {
                return Results.Problem(statusCode: 400, title: "Token antiforgery inválido");
            }
        }

        return await next(ctx);
    });

api.MapPost("/itens", (ItemDto dto) => Results.Created());
api.MapPost("/webhook", (Payload p) => Results.Accepted()).DisableAntiforgery();

DisableAntiforgery() é o equivalente Minimal API do [IgnoreAntiforgeryToken] — e vale a mesma regra: só para endpoints que não autenticam por cookie.

SPA e AJAX: o token vai no header

Campo oculto só existe em formulário renderizado. Para chamadas fetch, configure o antiforgery para aceitar um header:

Program.csC#
builder.Services.AddAntiforgery(options => options.HeaderName = "X-CSRF-TOKEN");

Se o front é servido por uma página Razor, o caminho mais curto é publicar o token num <meta> do layout:

_Layout.cshtmlCSHTML
@inject IAntiforgery Antiforgery
@{ var tokens = Antiforgery.GetAndStoreTokens(Context); }

<meta name="csrf-token" content="@tokens.RequestToken">
wwwroot/js/api.jsJS
const token = document.querySelector('meta[name="csrf-token"]').content;

await fetch("/api/itens", {
    method: "POST",
    headers: {
        "Content-Type": "application/json",
        "X-CSRF-TOKEN": token
    },
    body: JSON.stringify(item)
});

Quando o SPA é totalmente separado (React ou Angular servidos como estáticos, sem Razor), não há onde injetar o meta. O padrão então é entregar o token de requisição num cookie legível e o JavaScript copiá-lo para o header:

Program.csC#
builder.Services.AddAntiforgery(options => options.HeaderName = "X-XSRF-TOKEN");

app.Use(async (context, next) =>
{
    if (context.Request.Path == "/")
    {
        var antiforgery = context.RequestServices.GetRequiredService<IAntiforgery>();
        var tokens = antiforgery.GetAndStoreTokens(context);

        context.Response.Cookies.Append("XSRF-TOKEN", tokens.RequestToken!,
            new CookieOptions { HttpOnly = false, Secure = true });
    }

    await next();
});
Dois cookies, papéis diferentes

O HttpOnly = false acima parece um erro, mas é intencional: esse cookie carrega o token de requisição, que precisa ser lido pelo JavaScript. O segredo de verdade continua no cookie .AspNetCore.Antiforgery.*, que permanece HttpOnly. A proteção vem de o atacante não conseguir ler cookies de outro domínio — não de o valor ser secreto no seu próprio front.

SameSite ajuda, mas não substitui

Navegadores modernos tratam cookie sem SameSite declarado como Lax, o que já bloqueia o POST cross-site do primeiro exemplo. É uma camada excelente — e é por isso que muita gente conclui que antiforgery virou dispensável. Não virou:

  • Same-site não é same-origin. blog.suaempresa.com.br é same-site em relação a app.suaempresa.com.br. Um XSS ou um WordPress desatualizado num subdomínio derruba a proteção inteira.
  • Lax permite navegação GET de topo. Se algum endpoint muda estado via GET, o ataque continua trivial.
  • Cenários legítimos exigem None. App embarcado em iframe, checkout de terceiro, fluxo OIDC com form_post — todos precisam afrouxar, e aí só resta o antiforgery.
  • Você não controla o cliente. Navegador antigo, WebView customizada e proxies corporativos se comportam de formas variadas.

Configure o cookie corretamente — e mantenha o antiforgery ligado:

Program.csC#
builder.Services.ConfigureApplicationCookie(options =>
{
    options.Cookie.SameSite = SameSiteMode.Lax;
    options.Cookie.HttpOnly = true;
    options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
});

CORS não é defesa contra CSRF

"Minha política de CORS não libera o domínio do atacante, então ele não consegue chamar minha API." Essa frase inverte o que o CORS faz. O CORS controla se o navegador entrega a resposta ao script que pediu — não se a requisição é enviada. A requisição sai, chega no servidor e é processada; o bloqueio acontece depois, na leitura. Para CSRF, que é escrita, isso é irrelevante.

Existe uma proteção acidental, e vale entendê-la para não confiar demais nela: um POST com Content-Type: application/json não é uma "requisição simples", então o navegador dispara um preflight OPTIONS antes — e sua política de CORS reprova. Só que o atacante contorna isso usando os content types que dispensam preflight:

Content-TypePreflight?Consequência
application/x-www-form-urlencodedNãoFormulário HTML puro já ataca
multipart/form-dataNãoIdem
text/plainNãoBasta a API aceitar JSON com esse content type
application/jsonSimBarreira acidental — não é uma defesa projetada

Ou seja: uma API que só aceita application/json e recusa os demais tem uma dificuldade a mais no caminho do atacante. Isso é endurecimento, não proteção. O CORS mal configurado, por sua vez, é um problema por si só — assunto do item 08.

Três detalhes que quebram em produção

Token inválido depois de escalar o container

O antiforgery é assinado pelo Data Protection. Sem um repositório de chaves compartilhado, cada instância gera o seu — o formulário renderizado pelo pod A falha ao ser validado pelo pod B, e reiniciar o serviço invalida todos os formulários abertos. O sintoma é clássico: "às vezes dá erro ao salvar".

Program.csC#
builder.Services.AddDataProtection()
    .PersistKeysToFileSystem(new DirectoryInfo("/var/chaves"))
    .SetApplicationName("MinhaApp");

O SetApplicationName precisa ser idêntico em todas as instâncias — é ele que define o escopo de derivação das chaves.

Página de formulário em cache

Se um proxy ou CDN cacheia uma página que contém token, usuários diferentes recebem o mesmo valor e a validação falha. Páginas autenticadas com formulário devem sair com Cache-Control: no-store.

A tela de login também precisa de token

O login CSRF é pouco conhecido: o atacante força a vítima a se autenticar na conta dele. A partir daí, tudo que a vítima fizer — cadastrar um cartão, salvar um documento — fica registrado numa conta controlada pelo atacante. Razor Pages já protege o login por padrão; se você escreveu a sua, confira.

Como verificar

Primeiro, o inventário das isenções. Toda linha aqui é uma decisão que precisa de justificativa:

terminalbash
grep -rn "IgnoreAntiforgeryToken\|DisableAntiforgery\|asp-antiforgery" --include="*.cs" --include="*.cshtml" .

# O filtro global está mesmo registrado?
grep -rn "AutoValidateAntiforgeryTokenAttribute\|UseAntiforgery" --include="*.cs" .

Depois, o teste que realmente prova. Abra um formulário logado no navegador, copie a requisição do DevTools como cURL, remova o campo __RequestVerificationToken e reenvie. O resultado esperado é 400:

PowerShellPOWERSHELL
# Sem o token, com o cookie de sessão válido — deve falhar
Invoke-WebRequest -Uri https://localhost:5001/usuarios/promover `
    -Method POST `
    -WebSession $sessao `
    -Body @{ email = "teste@exemplo.com"; perfil = "Administrador" }

Se voltar 302 ou 200, o endpoint está desprotegido. Vale transformar isso num teste de integração para cada endpoint sensível — é barato e não deixa a proteção regredir silenciosamente.

Checklist

  • AutoValidateAntiforgeryTokenAttribute registrado como filtro global no MVC
  • app.UseAntiforgery() presente, depois de UseAuthentication e UseAuthorization
  • Endpoints Minimal API com corpo JSON validados por filtro de grupo ou IAntiforgery
  • Cada IgnoreAntiforgeryToken / DisableAntiforgery justificado por credencial não-ambiente
  • Nenhum endpoint que altera estado responde a GET
  • Formulários usam o Tag Helper (ou @Html.AntiForgeryToken() explícito)
  • Chamadas AJAX enviam o token via header configurado em AddAntiforgery
  • Cookie de autenticação com SameSite=Lax, HttpOnly e Secure
  • Data Protection com chaves persistidas e SetApplicationName igual entre instâncias
  • Páginas autenticadas com formulário saem com Cache-Control: no-store
  • Formulário de login também exige token
  • Teste de integração que reenvia POST sem token e espera 400
