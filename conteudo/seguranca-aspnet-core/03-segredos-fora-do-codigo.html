Segredos fora do código-fonte

Connection string no appsettings.json versionado não é um risco futuro — é um vazamento que já aconteceu no momento do git push. E apagar a linha depois não desfaz nada.

ASP.NET Core 10 Leitura: ~8 min Nível: essencial

O problema não é o arquivo. É o histórico.

Todo mundo entende, no abstrato, que senha não deveria estar no repositório. O que engana é achar que dá para corrigir depois — abrir o arquivo, apagar a linha, commitar "remove segredo" e seguir a vida.

Não funciona assim. O Git é um banco de dados append-only: aquele commit antigo continua ali, acessível por hash, em cada clone que alguém já fez, no cache do seu servidor de CI, no fork que um ex-colega abriu, no espelho do GitHub que indexa código público. O segredo não está no arquivo, está no histórico — e o histórico já saiu da sua máquina.

A regra

A partir do instante em que um segredo entra num commit que saiu da sua máquina, ele deve ser tratado como comprometido. A única correção real é rotacionar o valor. Limpar o histórico é higiene, não remediação.

E "repositório privado" não é proteção. Um repo privado tem, tipicamente, dezenas de pessoas com acesso de leitura, mais todos os tokens de CI, mais integrações de terceiros, mais o notebook de cada uma dessas pessoas. Um segredo em repo privado não vazou publicamente — mas o raio de exposição continua sendo grande demais para uma credencial de produção.

Como a configuração realmente se resolve

Antes de mover qualquer segredo, vale entender a mecânica: o IConfiguration não lê um arquivo, ele empilha várias fontes. Cada fonte adicionada depois sobrescreve a chave de mesmo nome das anteriores. É essa sobreposição que permite ter o valor de dev fora do valor de produção sem nenhum if no código.

Esta é a ordem que o CreateBuilder monta por padrão, da menor para a maior precedência:

#FontePapel
1appsettings.jsonValores não sensíveis, versionados
2appsettings.{Environment}.jsonAjustes por ambiente — também versionados
3User SecretsSó em Development, fora do repositório
4Variáveis de ambienteO que produção realmente usa
5Argumentos de linha de comandoSobrepõe tudo

Repare no item 3: o provedor de User Secrets é registrado apenas quando o ambiente é Development. Isso é o que impede um segredo de dev de vazar para o servidor por acidente — e também o que explica por que a mesma chave precisa vir de outro lugar em produção.

Na prática, a chave sensível fica no appsettings.json apenas como declaração de que ela existe, com valor vazio:

appsettings.json — versionado, sem valorJSON
{
  "ConnectionStrings": {
    "Default": ""
  },
  "Pagamentos": {
    "BaseUrl": "https://api.gateway.com.br",
    "ApiKey": ""
  }
}

Isso documenta o formato esperado para quem clonar o projeto, sem entregar nada. O valor entra por fora, em cada ambiente.

Desenvolvimento: User Secrets

O Secret Manager guarda os valores num arquivo dentro do seu perfil de usuário, fora da pasta do projeto. Não tem como commitar por acidente, porque o arquivo simplesmente não está lá.

terminal — na pasta do projetobash
# Gera um UserSecretsId no .csproj e vincula o projeto ao seu perfil
dotnet user-secrets init

dotnet user-secrets set "ConnectionStrings:Default" "Server=...;Password=..."
dotnet user-secrets set "Pagamentos:ApiKey" "sk_test_..."

dotnet user-secrets list
#   ConnectionStrings:Default = Server=...
#   Pagamentos:ApiKey = sk_test_...

O init adiciona um GUID ao arquivo de projeto. Esse GUID é versionado — ele não é o segredo, é só o identificador da pasta onde seus segredos locais moram:

MinhaApi.csprojXML
<PropertyGroup>
  <TargetFramework>net10.0</TargetFramework>
  <UserSecretsId>8f3d1c6a-...-b21e</UserSecretsId>
</PropertyGroup>

O arquivo físico fica em:

  • Windows: %APPDATA%\Microsoft\UserSecrets\<id>\secrets.json
  • Linux / macOS: ~/.microsoft/usersecrets/<id>/secrets.json
User Secrets não é criptografia

O secrets.json é texto puro. Quem tiver acesso ao seu perfil de usuário lê tudo. O objetivo da ferramenta é tirar o segredo do repositório, não protegê-lo em disco. Por isso ela só serve para desenvolvimento — nunca aponte uma credencial de produção para lá.

No código, nada muda. Você lê a chave normalmente e o provedor certo responde conforme o ambiente:

Program.csC#
var connectionString = builder.Configuration.GetConnectionString("Default")
    ?? throw new InvalidOperationException(
        "ConnectionStrings:Default não configurada.");

Produção: variável de ambiente e cofre gerenciado

Fora da sua máquina, User Secrets não existe. A fonte passa a ser o ambiente — e a sintaxe de chave aninhada muda: o separador : não é portável entre sistemas operacionais, então use dois underscores.

terminal / docker-compose / painel do hostbash
# ConnectionStrings:Default  →  ConnectionStrings__Default
ConnectionStrings__Default="Server=...;Password=..."
Pagamentos__ApiKey="sk_live_..."

Variável de ambiente resolve o problema do repositório, mas empurra a pergunta para o lado: agora o segredo mora na configuração do host, sem versionamento, sem auditoria de quem leu, e rotacionar significa editar um painel e reiniciar. Para uma aplicação pequena, é aceitável. Para produção séria, o passo seguinte é um cofre.

Azure Key Vault

O ganho aqui não é só guardar o valor: é ter controle de acesso, log de auditoria e rotação sem tocar no deploy. E, principalmente, resolver o paradoxo do "segredo para acessar os segredos" — com identidade gerenciada, a aplicação se autentica pela própria identidade da infraestrutura, sem nenhuma credencial em lugar nenhum.

Program.csC#
// dotnet add package Azure.Extensions.AspNetCore.Configuration.Secrets
// dotnet add package Azure.Identity

var builder = WebApplication.CreateBuilder(args);

if (!builder.Environment.IsDevelopment())
{
    builder.Configuration.AddAzureKeyVault(
        new Uri($"https://{builder.Configuration["KeyVault:Name"]}.vault.azure.net/"),
        new DefaultAzureCredential());
}

Adicionado por último, o provedor do cofre tem a maior precedência — os valores vazios do appsettings.json são preenchidos e a aplicação nem percebe a diferença.

Nome de segredo não aceita dois-pontos

O Key Vault não permite : no nome. A convenção do provedor é o hífen duplo: o segredo Pagamentos--ApiKey chega na aplicação como a chave Pagamentos:ApiKey. Errar isso gera um valor nulo silencioso — que é exatamente o tipo de falha que a validação da próxima seção transforma em erro de boot.

Se sua stack é AWS ou GCP, o desenho é idêntico: AWS Secrets Manager com IAM role da task, ou Secret Manager do GCP com service account. O que importa é o princípio — a aplicação prova quem é pela identidade da infraestrutura, não por uma senha que alguém precisou digitar em algum lugar.

Consuma com Options, e falhe no boot

Injetar IConfiguration pelos serviços e ler _config["Pagamentos:ApiKey"] espalhado funciona, mas cria dois problemas: a string mágica não tem verificação nenhuma, e um segredo ausente só aparece na primeira requisição que usar aquele trecho — possivelmente semanas depois do deploy.

O Options pattern com validação resolve os dois de uma vez:

PagamentosOptions.csC#
public class PagamentosOptions
{
    public const string Secao = "Pagamentos";

    [Required]
    public required string BaseUrl { get; init; }

    [Required(AllowEmptyStrings = false)]
    public required string ApiKey { get; init; }
}
Program.csC#
builder.Services.AddOptions<PagamentosOptions>()
    .Bind(builder.Configuration.GetSection(PagamentosOptions.Secao))
    .ValidateDataAnnotations()
    .ValidateOnStart();   // sem isso, a validação só roda no primeiro uso
Por que ValidateOnStart importa tanto

Sem ele, esquecer um segredo em produção vira um erro intermitente, na hora errada, para um usuário aleatório. Com ele, a aplicação não sobe — o deploy falha, o health check não passa, o rollback é automático e ninguém chega a ver a tela de erro. Falhar cedo e alto é o comportamento seguro.

No consumo, injete IOptions<PagamentosOptions> e o serviço passa a depender de um objeto tipado, não de uma string de configuração:

GatewayPagamentoService.csC#
public class GatewayPagamentoService(IOptions<PagamentosOptions> options)
{
    private readonly PagamentosOptions _cfg = options.Value;
    // ...
}

Os vazamentos que não estão no appsettings

Limpar o appsettings.json dá uma sensação de dever cumprido que costuma ser prematura. Na prática, o segredo se espalha para muito mais lugares — e estes cinco são os que mais aparecem em auditoria:

OndePor que vaza
launchSettings.jsonFica em Properties/, é versionado por padrão e quase sempre tem environmentVariables com valores reais
docker-compose.ymlSenha do banco em texto puro no mesmo repo — o alvo mais fácil de todos
ENV / ARG no DockerfileO valor fica gravado na layer da imagem. Quem faz docker history lê tudo, mesmo que você sobrescreva depois
Log de exceçãoSqlException e clientes HTTP costumam incluir a connection string ou o header de autorização na mensagem
Log de CI/CDUm echo de debug, ou um passo que imprime o ambiente inteiro, e o token fica no log público do pipeline
O endpoint de diagnóstico

Nunca exponha um endpoint que devolva a configuração — nem "só em staging", nem "só para admin". Aquele /debug/config criado para resolver um incidente de madrugada vira permanente, e entrega em uma requisição tudo o que este item inteiro tenta proteger.

Detectar antes do push

Revisão humana não pega segredo — o olho passa batido por uma string longa no meio de um diff de 400 linhas. Automatize:

terminalbash
# Varre TODO o histórico, não só o working tree
gitleaks detect --source . --verbose

# Confirma que sua config local está fora do repo
dotnet user-secrets list

Coloque o gitleaks como hook de pre-commit e como passo obrigatório no pipeline. Se o repositório está no GitHub, ative também o push protection do secret scanning: ele bloqueia o push no momento em que detecta um padrão de credencial conhecida, antes do segredo existir no remoto. É a única defesa que age antes do dano.

E garanta o básico no .gitignore:

.gitignoregitignore
appsettings.*.Local.json
*.pfx
*.env
.env.*

O segredo já vazou. E agora?

A reação instintiva é errada. Quase todo mundo corre para o git filter-repo primeiro, force-push, respira aliviado — e continua exposto, porque reescrever histórico não revoga credencial nenhuma. A chave que vazou segue válida no gateway de pagamento, e o atacante que a copiou há três semanas não se importa com o seu histórico.

A ordem correta é:

  1. Rotacione imediatamente. Gere a nova credencial, publique no cofre, revogue a antiga. Isto é o que encerra a exposição — tudo depois é limpeza.
  2. Investigue o uso. Vá aos logs de acesso do recurso e procure origem, horário e volume anômalos desde a data do commit que vazou. Sem isso você não sabe se foi só um susto.
  3. Aí sim limpe o histórico, com git filter-repo ou BFG. É uma reescrita destrutiva: quebra todos os clones existentes e exige coordenação com o time inteiro.
  4. Feche a porta. Adicione o hook de detecção e a checagem no pipeline, para que a próxima tentativa não passe.
Reescrever histórico não alcança tudo

Forks, clones locais, caches de CI e os refs de pull request do GitHub podem manter o commit acessível mesmo depois do force-push. Trate a limpeza como redução de superfície, não como remoção. A rotação é a única etapa que realmente resolve.

Checklist

  • Nenhum valor sensível em appsettings.json ou appsettings.{Env}.json — apenas a chave declarada, vazia
  • dotnet user-secrets init feito, e todo segredo de dev vivendo lá
  • launchSettings.json e docker-compose.yml revisados — sem senha real
  • Nenhum ENV ou ARG com segredo no Dockerfile
  • Produção lendo de cofre gerenciado com identidade gerenciada, ou no mínimo de variável de ambiente
  • Configuração consumida via IOptions<T> com ValidateDataAnnotations() e ValidateOnStart()
  • gitleaks rodando como pre-commit e no pipeline
  • Push protection do secret scanning ativado no repositório
  • Nenhum endpoint que devolva configuração, em nenhum ambiente
  • Todo segredo que já esteve num commit foi rotacionado
